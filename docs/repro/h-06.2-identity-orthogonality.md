## Defect found + fixed during this repro

The first live screenshot showed `wez tab icon node` + `wez tab title api` rendering as **`💚 bash`**,
not `💚 api`. Root cause: the `format-tab-title` handler sourced the label from the pane
`WEZTERM_TAB_TITLE` user var → pane **process** title → cwd basename, and **never read
`tab.tab_title`** (what `wez tab title` writes via `set-tab-title`). So an explicit `wez tab title`
was invisible in the bar. Pre-existing (the 6.1 handler also fell through to the pane title for a
plain title; 6.2 only removed the legacy `color:title` parse), surfaced here for the first time.

**Fix** (`fix(06.2-03): render explicit wez tab title (tab.tab_title) in tab bar`): inserted
`tab.tab_title` into the title precedence — **below** the pane user var (active-pane title still
wins) and **above** the pane process title. Purely additive; existing behavior unchanged.
Covered by render tests 16a/16b/16c (RED → GREEN) and re-verified live (`🦀 api` renders).

## Conclusion

All Phase 6.2 behaviors confirmed at both the byte/render layer (headless) and the actual GUI
paint (live): icon as its own attribute composed left of a literal title, split tab/pane color
carriers with explicit-tab-color-wins precedence and the opt-in `--follow-pane-color` follow,
the empty-title cwd fallback, and the legacy parse-and-warn. One latent rendering defect for
explicit `wez tab title` was found and fixed in the same pass.
