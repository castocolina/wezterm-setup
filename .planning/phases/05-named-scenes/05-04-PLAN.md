<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| recipe basenames -> shell completion output | names read from the scenes dir are emitted as Tab-time candidates into the shell |
| `__complete` hook -> shell process | the completion hook runs during Tab expansion; a failure or metacharacter could disrupt the shell |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-12 | Tampering (code injection via completion) | `scene-names` candidate emission | mitigate | candidates are PLAIN tokens emitted one-per-line by the shared run() loop (T-07-02) — recipe basenames are file stems; the generated arms consume them via `compadd`/`compgen -W` so the shell treats them as DATA, never code. A basename with a shell metacharacter is offered as a literal candidate, not executed. |
| T-05-13 | DoS (Tab-time hook fails the shell) | `wez __complete scene-names` on a missing/empty dir | mitigate | `list_recipe_names` returns `{}` for a missing/empty dir and run() no-ops on unknown context — the hook always exits 0, so Tab expansion never errors (the established `__complete` discipline). The `2>/dev/null` in the generated arms further suppresses any stderr from reaching the prompt. |
| T-05-14 | Spoofing (completion/launch drift) | scenes-dir resolution in the provider | mitigate | `scene_names` calls the SAME `scene.scenes_dir()` + `scene.list_recipe_names` launch uses — completion can never advertise a recipe launch resolves differently (Pitfall 6). |
</threat_model>
