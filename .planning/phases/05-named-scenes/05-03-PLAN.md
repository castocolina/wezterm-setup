<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `<name>` argument -> filesystem path | the recipe name is interpolated into `<dir>/<name>.toml` (the path-traversal surface) |
| recipe file bytes -> parser | the read file content is untrusted until parsed under pcall by recipe.lua |
| recipe command -> pane PTY | recipe commands run in panes via the inherited run_new path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-08 | Tampering / Info Disclosure | `M.run_launch` name handling (path traversal) | mitigate | `recipe.guard_name(args.name)` is called BEFORE `io.open` — rejects `/` and `..` (T-05-01 from 05-01); the resolved path is always `<scenes_dir>/<name>.toml`. A name with a separator never reaches `io.open`. Verified by the unknown/guard test paths. |
| T-05-09 | DoS / crash | malformed recipe file at launch | mitigate | the raw string goes through `recipe.load_and_map` (pcall'd tinytoml — 05-01 T-05-02); a crafted file yields exit 1 + the UI-SPEC invalid-recipe copy, never a traceback. validate-before-emit builds ZERO panes. |
| T-05-10 | Tampering / EoP | recipe command execution in panes | accept | commands flow through the inherited `M.run_new` path which sends them as DISTINCT trailing `send-text` lines (never concatenated into escapes — T-04-02) and shquotes every payload. A recipe file is the user's own data (same trust as typing the command). No NEW execution surface — launch composes the existing, already-mitigated path. |
| T-05-11 | Spoofing (completion/launch drift) | scenes-dir resolution | mitigate | one shared `M.scenes_dir()` resolver used by launch, completion (05-04), and the seeder (05-02) — completion can never advertise a recipe launch resolves to a different dir (Pitfall 6). |
</threat_model>
