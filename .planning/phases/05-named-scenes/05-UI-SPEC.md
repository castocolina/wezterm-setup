# Phase 5 — UI Design Contract

> Visual and interaction contract for Named Scenes (`wez scene launch <name>`, dynamic recipe-name
> tab completion, and the seeded `ai`/`docker`/`dev` example recipes). This is NOT a web/GUI phase —
> there is no HTML/CSS/component library, no fonts in the browser sense. The "UI" surface is the
> companion CLI (`wez`) running in a terminal: (1) the **command-line textual surface** of
> `wez scene launch` (success/feedback lines on stdout/stderr, error copywriting, exit codes), (2)
> the **shell tab-completion behavior** for `wez scene launch <Tab>` (dynamically read from recipe
> files), and (3) the **install-time messaging** when the three example recipes are seeded. The
> terminal-visual output of the launched scene (pane geometry, colors, titles) is NOT re-specified
> here — `wez scene launch` is contractually equivalent to an equivalent `wez scene new` call
> (SCEN-04), so the visual contract is inherited verbatim from `04-UI-SPEC.md`. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.
>
> No upstream `CONTEXT.md` / `RESEARCH.md` exists for this phase; this contract is pre-populated
> from `REQUIREMENTS.md` (SCEN-03..06), `ROADMAP.md` Phase 5 success criteria, `README.md` (the
> documented recipe shape + launch invocation), and the locked conventions in the shipped CLI
> (`cli/commands/scene.lua`, `cli/commands/complete.lua`, `cli/commands/completions.lua`,
> `cli/spec.lua`) plus the `04-UI-SPEC.md` precedent.

## Spacing Scale

**Not applicable — terminal CLI.** Pixel/8-point spacing does not translate to command output. The
only "spacing" surface in this phase is the textual layout of CLI output lines, governed by these
terminal conventions (not px values):

| Convention | Rule |
|------------|------|
| Indentation unit | **2 spaces** per nesting level in any multi-line output (e.g. an indented list of available recipe names under an error). Never tabs (column drift across terminals). |
| List item prefix | `  - <item>` (two-space indent + dash + space) for the "available recipes" hint list. |
| Vertical rhythm | One blank line MAX between a stanza and its following hint block; never two consecutive blank lines (matches Phase 4's "clean output" discipline). |
| Trailing newline | Every emitted line (stdout or stderr) ends in exactly one `\n`; no trailing blank line. |

Exceptions: the launched scene's own pane geometry is governed by the Layout Geometry Contract in
`04-UI-SPEC.md`, inherited verbatim via SCEN-04 — not re-specified here.

## Typography

**Not applicable — terminal CLI.** There is no font-size/weight system. Terminal text rendering is
entirely the user's WezTerm font config. The closest equivalent contracts are:

| Role (terminal mapping) | Contract |
|-------------------------|----------|
| Emphasis | No bold/ANSI-bold in `wez scene launch` output by default — feedback lines are plain text. (Bold/indicator styling is reserved for the GUI tab bar, owned by Phase 3, not this CLI surface.) |
| Token / literal | Command names, recipe names, and paths referenced in copy are wrapped in single backticks ONLY in docs/README — in actual terminal output they appear as bare tokens (e.g. `wez scene list`), since the terminal cannot render markdown. |
| Casing | Error/feedback copy is lowercase-leading (`error: ...`), matching the shipped Phase 4 convention (`error: wez scene new requires ...`). No sentence-case banners. |

## Color

**Not applicable as a web 60/30/10 surface — terminal CLI.** Color in this phase comes from the
**ANSI/terminal palette**, never CSS hex. `wez scene launch` is near-silent on success (see
Copywriting Contract), so its own color footprint is minimal. The contract below reserves ANSI
semantic color to specific output elements only — never "everything":

| Role (ANSI semantic) | Reserved for |
|----------------------|--------------|
| Default / no color | The normal path. Success is silent; any incidental stdout uses the terminal's default foreground. **No decorative color on the happy path.** |
| Error (ANSI red, or bare `error:` prefix if `NO_COLOR` / non-TTY) | The leading `error:` token of a failure line ONLY — recipe-not-found, malformed-recipe, missing-name. The rest of the error line (the explanation + hint) stays default foreground. |
| Dim / secondary (ANSI dim, optional) | The "available recipes" hint list and the `try: wez scene launch <name>` suggestion line — visually subordinate to the error itself. Optional; falling back to plain default foreground is acceptable and preferred under `NO_COLOR` / non-TTY. |

Color rules:
- **v1 implementation status (documented decision — review finding M-3):** the shipped
  `scene launch` / `seed-scenes` / completion paths emit **NO ANSI at all** — output is always
  plain text. The `error:` token coloring + dim hints described here are an **intentionally
  deferred** affordance, not a regression. Because no ANSI is emitted, `NO_COLOR`/non-TTY is
  honored by construction. **A future contributor adding color MUST also add the `NO_COLOR` +
  `isatty` guard at the same time** — the guard is currently absent only because the feature is.
- **Honor `NO_COLOR`** (env var) and **non-TTY stdout/stderr**: emit no ANSI escapes in either case
  — bare `error:` prefix, plain hint text. Color is a TTY-only affordance, never required to parse
  the message.
- **Never** color the success path, recipe names in completion output, or the seed-install
  messaging. Accent/color is reserved strictly for the error-prefix and (optionally) dim hints.
- The launched scene's pane background / tab accent colors come from the recipe's `color` field and
  are rendered by the inherited `wez scene new` path (the 10-profile OSC palette in `04-UI-SPEC.md`)
  — NOT re-defined here.

## Copywriting Contract

*(THIS IS THE PRIMARY DELIVERABLE for this CLI phase. CLI-textual mappings: "Primary CTA" = the
canonical `wez scene launch` invocation shape; "Empty state" = the no-recipes-present and
no-name-given cases; "Error state" = recipe-not-found / malformed-recipe with a recovery path;
"Destructive confirmation" = N/A, this phase has no destructive actions.)*

All copy below is **prescriptive and exact** — the executor implements these strings verbatim.
Placeholders in `<angle brackets>` are interpolated at runtime; everything else is literal.

| Element | Copy / Contract |
|---------|------|
| **Primary CTA (canonical invocation)** | `wez scene launch <name>` — `<name>` is the recipe basename without extension (e.g. `dev`, not `dev.toml`). Recipes resolve from `~/.config/wezterm/wezterm-setup/scenes/` as `<name>.toml` — recipes are **TOML only** (SCEN-03; one `.toml` per scene, parsed by the Lua engine). On success the command is **contractually equivalent to the matching `wez scene new` call** (SCEN-04) — same layout, pane count, per-pane commands, tab color, tab title. |
| **Success output (stdout)** | **Silent on stdout**, inheriting Phase 4 D-09 — `wez scene launch` prints nothing beyond what the recipe's own pane commands produce; no `Launched scene 'dev'!`-style banner. The terminal stays clean. Exit code `0`. (If a non-TTY/CI confirmation affordance is ever wanted, that is a new decision, not this phase's default — matches the `wez scene new` precedent.) |
| **Empty state — no `<name>` given** (`wez scene launch` with no argument) | Usage error to **stderr**, exit non-zero (`2`): `error: wez scene launch requires a recipe name (got none)` — followed, when at least one recipe exists, by the available-recipes hint block (see below). When NO recipes exist, append **only** the indented seed-hint guidance line `  run: wez seed-scenes to restore the seeded examples (ai, docker, dev)` — **NOT** a second `error: no scene recipes found` line. **Exactly ONE `error:` token per invocation** (resolved from review finding I-1): the usage error is the single failure; the missing recipes are guidance, not a second error. Validate-before-emit: exits before any mux/`scene new` call. |
| **Empty state — no recipes present at all** (scenes dir missing or empty) | When the user runs `wez scene launch <name>` (a name WAS given) and `~/.config/wezterm/wezterm-setup/scenes/` is missing or contains no `.toml` files, the missing recipes ARE the primary failure: stderr, exit non-zero (`2`): `error: no scene recipes found in ~/.config/wezterm/wezterm-setup/scenes/` then on the next line the actionable seed-hint: `  run: wez seed-scenes to restore the seeded examples (ai, docker, dev)`. (`wez seed-scenes` is the literal copy-if-absent reseed command — point at the runnable command, not a vague "reinstall"; resolved from review finding I-3, SCEN-06.) The bare-invocation (no name) variant is covered by the row above and shows only one `error:`. |
| **Error — recipe not found** (`<name>` has no matching file) | stderr, exit non-zero (`1`), problem + recovery path: line 1 `error: no scene recipe named '<name>' in ~/.config/wezterm/wezterm-setup/scenes/`; then a hint block listing what IS available (see "available-recipes hint block"). If zero recipes exist, fall through to the no-recipes guidance line instead. Validate-before-emit: this check happens before any `scene new` call, so a bad name builds nothing. |
| **Available-recipes hint block** (shared by the two errors above) | After the `error:` line, emit on its own line `available recipes:` then one `  - <name>` line per recipe (basename, no extension), **sorted** (one `.toml` per scene name), and a final suggestion line `try: wez scene launch <one-of-the-names>`. The names list is the SAME set the completion hook returns (single source of truth — see Completion Contract). |
| **Error — malformed recipe file** (file exists, fails to parse/validate) | stderr, exit non-zero (`1`), problem + which field + recovery: `error: scene recipe '<name>' is invalid: <reason>` where `<reason>` is specific and actionable, e.g. `missing required field 'layout'`, `unknown layout '<value>' — expected one of: tall, tall:mirrored, grid, horizontal`, `unknown color '<value>' — expected one of: red, orange, yellow, green, teal, cyan, blue, navy, purple, pink`, or `could not parse TOML at line <N>`. The layout/color reason strings **reuse the exact enum wording already shipped** by `cli/lib/scene.lua` `validate_layout`/`validate_color` (single source of truth — do not author new enum copy). Validate-before-emit: a malformed recipe builds zero panes. |
| **Recipe → scene-new mapping (SCEN-04 equivalence)** | A recipe's fields map 1:1 onto `wez scene new` arguments: `layout` → `--layout`; each `[[panes]]` entry → one `--pane` spec (`command` → the pane's `cmd=`, optional per-pane `color`/`title` → `color=`/`title=`); top-level `color` → `--color`; top-level `title` → `--title`. The launch path performs the SAME validate-before-emit and two-phase build as `scene new`; it must NOT re-implement layout geometry, palette, or OSC emission — it composes the existing `scene new` orchestration. |
| **Destructive confirmation** | none — this phase has no delete/overwrite/reset actions. Launching a recipe only spawns/styles panes (same non-destructive materialization as `scene new`: reuse a 1-pane tab or spawn a new tab in the same window; never closes the user's other tabs, never a new OS window). |
| **Install-time seeding messaging (SCEN-06)** | The installer seeds `ai`, `docker`, `dev` via **copy-if-absent**. Per-recipe messaging on the installer's stdout: when a recipe is newly written → `seeded scene recipe: <name>` (one line per newly-created file). When a recipe already exists (user has it) → `kept existing scene recipe: <name>` (NOT "skipped" — affirm the user's file is preserved, mirroring the install-state "user lines preserved" tone). These lines are advisory installer output, NOT `wez scene launch` output. Never overwrite a user-edited recipe (SCEN-06 contract). |

### Seeded recipe content (authoritative — REQUIREMENTS SCEN-06 table)

The three seeded recipes ship exactly these values (the executor writes these files; format is TOML
per the README-documented shape, `layout`/`color`/`title` top-level + `[[panes]]` with `command`):

| Recipe | Layout | Color | Panes | Startup commands |
|--------|--------|-------|-------|------------------|
| `dev` | `tall` | `green` | 2 | shell (cwd), shell (cwd) |
| `ai` | `tall` | `purple` | 2 | shell (cwd), shell (cwd) |
| `docker` | `grid` | `teal` | 4 | `docker stats`, `docker ps`, `docker compose logs -f`, shell |

- A "shell (cwd)" pane is a plain interactive shell with no startup command (the `shell` pane
  keyword from Phase 4 D-04) — it inherits cwd via the shipped OSC 7 mechanism; no `command` field,
  or `command = "shell"`, whichever the recipe schema chooses (planner decides, but it MUST
  round-trip to a `--pane shell` equivalent so no auto-title/command is injected — Phase 4 D-04/D-09).
- The `docker` recipe's 4th pane is a plain shell (no command).

## Completion Contract (SCEN-05 — dynamic recipe-name tab completion)

*(No template section maps directly; included because dynamic completion is a first-class success
criterion for this phase and the single largest interaction surface beyond copy.)*

| Aspect | Contract |
|--------|----------|
| Trigger | `wez scene launch <Tab>` completes recipe names in **both zsh and bash**. |
| Source | Candidates are read **dynamically at completion time** from `~/.config/wezterm/wezterm-setup/scenes/` — adding or removing a recipe file changes the completion set with **no regeneration / no manual step** (SCEN-05). |
| Extension point | A NEW `__complete` context (e.g. `scene-names`) added to `cli/commands/complete.lua`'s `CONTEXTS` table, providing a function that lists recipe basenames. The generated zsh/bash scripts gain a nested `scene)` → `launch)` arm that calls `wez __complete scene-names` — exactly mirroring the existing `pane)`/`tab)` nested dispatch arms in `cli/commands/completions.lua`. Do NOT hardcode recipe names into the static scripts (D-16 single source of truth). |
| Candidate shape | Recipe **basenames without extension** (the `.toml` stem), sorted (the SAME set the error hint block lists — one provider function, two consumers). Plain tokens only (T-07-02): no shell metacharacters emitted, so Tab-time output is always treated as data. |
| Empty state (no recipes) | The `scene-names` context emits **nothing** and exits `0` — Tab completion offers no candidates rather than erroring (a Tab-time hook must never fail the shell, matching the existing `__complete` no-op-on-unknown-context discipline). |
| Spec registration | `wez scene launch <name>` must be registered in `cli/spec.lua` under the existing `scene` command (`scene_cmd` target), alongside the shipped `new` subcommand, so the completion generator's spec-walk picks it up automatically. |
| Validity scope (documented decision — review finding I-2) | The provider lists **every `*.toml` stem** in the scenes dir, including a file that would fail to parse/validate. Tab-time completion deliberately does **NOT** validate file contents — validating every recipe on each `<Tab>` would be slow and could fail the shell. Validation happens at `wez scene launch <name>` (malformed → exit 1, see Copywriting Contract). So completion may offer a name that then errors on launch; this is an accepted v1 tradeoff, not a gap. A future `wez scene list` (deferred) is the intended place for a health-aware browse surface. |
