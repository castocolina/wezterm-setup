# Phase 06.6 Plan 03: OSC-Byte Well-Formedness Tier 1 Test Summary

Emitted-OSC-byte well-formedness assertions for every `wez pane/tab
color|title|icon` (+ reset/clear) OSC-on-stdout row (PRD Appendix A.1): capture
the subcommand's own stdout and assert the bytes match what the REAL emitter
builds for the same input — the OSC frame recomputed from cli/lib/color.lua and
the icon glyph resolved from cli/lib/title.lua, so those modules stay the single
sources of truth for "well-formed OSC bytes" and a contract-breaking change to
either fails loudly. 35/35 green under `make e2e`.

## What was built

**Task 1 — OSC-byte assertions for pane/tab color|title|icon (+reset/clear) (`c81aaca`)**

`tests/e2e/tier1/osc_bytes_e2e_test.lua` (requires the Plan 01 harness; binds the
real emitters: `cli.lib.color` build_osc11/build_reset_osc11/build_osc1337/_base64
+ MUTED_BG, and `cli.lib.title` resolve_icon). Each case runs `wez <subcmd>` via
the harness `run_capture` (STDOUT only), asserts exit 0, then asserts the captured
bytes CONTAIN the EXPECTED bytes the real emitter builds for the same input via
`captured:find(expected, 1, true)` (plain literal find — OSC control bytes matched
verbatim). All A.1 OSC-on-stdout rows:

- **`wez pane color cyan`** — the DUAL write: OSC-11 background
  `build_osc11(color.MUTED_BG.cyan)` (asserts the `\27]11;` prefix AND the `\27\\`
  ST terminator explicitly) PLUS OSC-1337 `WEZTERM_PANE_COLOR` with a base64 value
  equal to `color._base64("cyan")` and a `\7` BEL terminator.
- **`wez pane color reset`** — `build_reset_osc11()` = `\27]111\7` (BEL-terminated
  reset) PLUS the empty-payload `WEZTERM_PANE_COLOR` accent clear
  (`color._base64("")`).
- **`wez pane title api`** — OSC-1337 on the `WEZTERM_TAB_TITLE` carrier (the
  pane-title carrier; there is no WEZTERM_PANE_TITLE), base64 == `color._base64("api")`.
- **`wez pane title reset`** — the clear path: well-formed OSC-1337
  `WEZTERM_TAB_TITLE` with the empty/cleared base64 value (`color._base64("")`).
- **`wez pane icon python`** — OSC-1337 `WEZTERM_TAB_ICON` (the SHARED icon
  carrier), base64 == `color._base64(title.resolve_icon("python"))` — the glyph is
  resolved through `title.resolve_icon`, then base64-encoded; never a hardcoded
  glyph or base64 literal.
- **`wez tab color cyan` / `wez tab color reset`** — OSC-1337 `WEZTERM_TAB_COLOR`,
  base64 == `color._base64("cyan")` / `color._base64("")`. Also asserts tab color
  emits NO OSC-11 background (`\27]11;` absent — background is pane-only).
- **`wez tab icon python`** — OSC-1337 `WEZTERM_TAB_ICON` (SAME carrier + SAME
  resolution chain as pane icon), base64 == `color._base64(title.resolve_icon("python"))`.

Tab title is deliberately NOT byte-asserted: `wez tab title` writes via
`wezterm cli set-tab-title` (a subprocess, not OSC-on-stdout — confirmed in
tab.lua run_title), so its exit-code/output-shape contract is Plan 02's.

## Threat Flags

None. The test captures only the subcommand's own stdout (no terminal/mux driven,
fully headless + deterministic); it adds no network surface, no file writes, no new
trust boundary. The two mitigations the plan's threat register assigns are both
implemented: T-06.6-09 (the emitted user-var value is asserted base64 via
`color._base64`, so a control-byte input cannot break out of the OSC frame) and
T-06.6-10 (EXPECTED bytes are recomputed from the real emitters, never hardcoded,
so a color.lua/title.lua contract break fails the test).
