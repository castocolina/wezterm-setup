# Phase 06.6: Code Review Report

**Reviewed:** 2026-06-24T21:53:04Z
**Depth:** standard
**Files Reviewed:** 21 (note: `tests/e2e/README.md` was listed in scope but does not exist on disk; 20 source files reviewed)

## Summary

This is an E2E-battery scaffolding phase: shared Lua harness/skip modules, a platform
parity table, six Tier-1 `_e2e_test.lua` files, four CLI unit tests, and the bash tooling
(`run-tests.sh`, `run-e2e.sh`, `setup.sh`, `uninstall.sh`, `build.sh`, `bootstrap-wezterm.sh`).

Overall the test design is strong: the LOUD-SKIP contract in `skip.lua` is well-built (a
skip on a capable host is structurally impossible to hide via the `LIVE-ASSERTED` marker),
the OSC-byte tests recompute every expected byte from the real emitter (no hardcoded
literals), and the install/uninstall tests are genuinely fixture/temp-FS isolated.

The headline defect is a **bash-3.2 portability violation**: `tools/run-tests.sh` uses
`mapfile`, a bash-4-only builtin the project's macOS-parity constraint explicitly forbids
(`tests/e2e/platform.lua` itself documents "no mapfile/readarray"). It ships silently
because the only gate that runs it (`bash -n`) cannot catch a runtime-builtin, and
`shellcheck` is advisory-only in the same script. The remaining findings are robustness /
consistency issues in the test harness and runners, plus one test whose exit-code capture
relies on a Lua-version-specific quirk.

Note: the four `cli/commands/*` and `cli/lib/*` modules the e2e tests drive
(`uninstall`, `scene`, `update`, `color`, `title`, `spec`) are OUT of this review's file
scope — findings here are confined to the listed test + tooling files. Where a test's
correctness depends on those modules' behavior, that is called out but not itself flagged.

## Critical Issues

### CR-01: `tools/run-tests.sh` uses `mapfile` — a bash-4-only builtin forbidden by the macOS-parity constraint

**File:** `tools/run-tests.sh:56`
**Issue:** The unit-test runner collects files with:
```bash
mapfile -t ALL_TESTS < <(find "${TEST_ROOTS[@]}" -type f -name '*_test.lua' ! -name '*_e2e_test.lua' | sort)
```
`mapfile`/`readarray` does not exist in bash 3.2. macOS ships bash 3.2, and the project
constraint (CLAUDE.md "Bash explicitly excluded for cross-platform reasons" / the
`bash_version` row in `tests/e2e/platform.lua:96-101` which names "no mapfile/readarray")
requires all shipped orchestration to be bash-3.2-safe. On macOS this line fails with
`run-tests.sh: line 56: mapfile: command not found`, leaving `ALL_TESTS` empty, so
`make test` silently discovers **zero** tests and exits 0 ("no test files discovered") —
a false-green that hides every unit test on the Mac platform the project must support.

This is especially severe because `run-e2e.sh` (line 64-69) deliberately avoids `mapfile`
with an explicit "bash-3.2-safe while-read + array-append" comment — the sibling runner
proves the correct idiom exists and was simply not applied here. The `bash -n` syntax gate
in this very file (line 111) cannot catch it: `mapfile` is syntactically valid, it only
fails at runtime when the builtin is absent. `shellcheck -x` is advisory-only (line 122,
"not failing the suite"), so even if shellcheck flagged it the suite stays green.

**Fix:** Replace with the bash-3.2-safe while-read + array-append idiom already used in
`run-e2e.sh`:
```bash
ALL_TESTS=()
while IFS= read -r f; do
  [ -f "$f" ] && ALL_TESTS+=("$f")
done < <(find "${TEST_ROOTS[@]}" -type f -name '*_test.lua' ! -name '*_e2e_test.lua' | sort)
```

## Warnings

### WR-01: `install_cycle_e2e_test.lua` uses the RELATIVE `WEZ` under `env`/`HOME=` prefixes despite computing `ABS_WEZ` for exactly this hazard

**File:** `tests/e2e/tier1/install_cycle_e2e_test.lua:92,103,134,142,153`
**Issue:** The file computes `ABS_WEZ` (lines 60-63) with a header comment stating the
relative `./dist/wez` "breaks the instant a run is prefixed with HOME=… or runs from a
different CWD." Yet the `seed-scenes` and `install-state` runs prefix the command with an
`env`/`HOME=`/`WEZTERM_CONFIG_FILE=` string while still invoking `shquote(WEZ)` (the
relative path), not `ABS_WEZ`. Only the `update` smoke (line 302) actually uses `ABS_WEZ`.
These runs survive today ONLY because nothing in them changes CWD and `run-e2e.sh` happens
to `cd "${REPO_ROOT}"` first — so `./dist/wez` still resolves relative to the runner's CWD.
Run the file directly from any other directory (`cd /tmp && lua5.4 .../install_cycle_e2e_test.lua`)
and every seed-scenes/install-state assertion fails with "no such file or directory" on the
launcher, defeating the test rather than the code under test. The author already built the
mitigation (`ABS_WEZ`) and then did not use it on the paths that need it.
**Fix:** Use the absolute launcher consistently for every env-prefixed run:
```lua
local out1, exit1 = run_capture_all(env .. shquote(ABS_WEZ) .. " seed-scenes")
...
local out1, exit1 = run_capture_all(env .. shquote(ABS_WEZ) .. " install-state < /dev/null")
```

### WR-02: `uninstall_idempotent_test.lua` exit-code capture depends on a Lua-5.4-only `os.execute` quirk and silently degrades elsewhere

**File:** `tests/cli/uninstall_idempotent_test.lua:115-116`
**Issue:**
```lua
local _, _, code = os.execute(cmd)
local status = tonumber(code) or 0
```
In Lua 5.4 `os.execute` returns `(ok, "exit"|"signal", code)`, so the 3rd value is the
real exit code. But the failure mode is silent: when the command exits 0, Lua returns
`(true, "exit", 0)` — fine — but the `tonumber(code) or 0` fallback means ANY future change
(or a Lua build where the 3rd return is absent) collapses to `status = 0`, i.e. a PASS,
regardless of the actual exit. Test 1 ("uninstall.sh exits 0") would then pass even if the
script aborted non-zero — the exact regression the test exists to catch. The harness uses
the more robust `io.popen` + `p:close()` 3-return idiom for the same purpose; this file
hand-rolls a weaker `os.execute` variant. Verified `os.execute("exit 3")` returns
`(nil, "exit", 3)` and `os.execute("true")` returns `(true, "exit", 0)` on the local
lua5.4, so it works TODAY — but the `or 0` fallback hides any future breakage as a pass.
**Fix:** Make the fallback fail-loud rather than pass-silent, or capture via the harness's
`run_capture_all` idiom. Minimal hardening:
```lua
local ok, _, code = os.execute(cmd)
local status = tonumber(code) or (ok == true and 0 or 1)
```
so a missing numeric code on a failed command degrades to non-zero (FAIL) rather than 0 (PASS).

### WR-03: `setup.sh` passes `${extra_args}` unquoted to `wez install-state` (SC2086 suppressed) — relies on word-splitting

**File:** `tools/setup.sh:245-249`
**Issue:**
```bash
extra_args="$(resolve_install_state_args "${had_explicit}" "${tty_state}" "$@")"
...
# shellcheck disable=SC2086
"${BIN_DIR}/wez" install-state ${extra_args}
```
`resolve_install_state_args` echoes `"$*"` (the user flags joined by the first IFS char),
and the result is re-split by the unquoted `${extra_args}` expansion. This collapses the
argv boundary: a user flag value containing a space or a glob character is mangled, and an
empty `extra_args` is correctly elided only because of word-splitting (a quoted `""` would
pass a spurious empty argument). For the current closed flag set (`--force/--restore/--skip`)
this is benign, but it is fragile glue that depends on IFS defaults and will misbehave the
moment any install-state flag takes a value with whitespace.
**Fix:** Carry the resolved args as a bash array instead of a space-joined string, so quoting
is preserved end-to-end:
```bash
# resolver writes one arg per line; caller reads into an array
local -a extra_args=()
while IFS= read -r a; do [ -n "$a" ] && extra_args+=("$a"); done \
  < <(resolve_install_state_args "${had_explicit}" "${tty_state}" "$@")
"${BIN_DIR}/wez" install-state "${extra_args[@]}"
```

### WR-04: `install_cycle_e2e_test.lua` never deletes the seed `home`/scratch dirs on early `assert` failure — and several `io.open` results are unchecked

**File:** `tests/e2e/tier1/install_cycle_e2e_test.lua:125-127,189-191,233-234`
**Issue:** Fixtures are opened with bare `io.open(...)` and written without an `assert`
or nil-check:
```lua
local seed = io.open(cfg, "wb")
seed:write("return {}\n")   -- seed is nil -> "attempt to index a nil value"
seed:close()
```
If the scratch dir is unwritable (e.g. a `TMPDIR` permission edge, or a prior `rmrf` race),
`io.open` returns `nil` and the next line crashes with an opaque `attempt to index a nil
value (local 'seed')` instead of a clear failure — and because the crash is BEFORE `rmrf`,
the scratch dir leaks. Other fixture writers in the same file (lines 189-191 `cfh`, 233-234
`c2`) have the same unchecked pattern. `scene_edge`/`uninstall_test` use `assert(io.open(...))`
correctly; this file is inconsistent.
**Fix:** Wrap every fixture open in `assert`:
```lua
local seed = assert(io.open(cfg, "wb"))
```

### WR-05: `run-tests.sh` shell-syntax gate runs `bash -n` TWICE on a failing script (redundant + noisy), and the gate cannot catch the CR-01 class of bug

**File:** `tools/run-tests.sh:111-117`
**Issue:**
```bash
if bash -n "$s" 2>/dev/null; then
  printf 'PASS  bash -n %s\n' "$s"
else
  printf 'FAIL  bash -n %s\n' "$s"
  bash -n "$s" || true        # runs bash -n a SECOND time just to surface the error
  FAILED=$((FAILED + 1))
fi
```
The double-invocation is wasteful but harmless. The substantive problem is scope: this gate
is the project's primary automated defense for shell scripts, yet `bash -n` only detects
parse errors — it cannot detect the `mapfile`-on-bash-3.2 runtime failure (CR-01) or any
other bash-version-specific runtime defect. The header (lines 95-100) implies this gate is
the safety net for "a syntactically broken installer/build/publish script," which is an
accurate but dangerously narrow guarantee given the project's hard bash-3.2 requirement.
**Fix:** Capture the error once into a variable and reprint it; and add a grep-based
bash-4-construct gate (mapfile/readarray/`declare -A`/`${var^^}`/`${var,,}`) that DOES fail
the suite, since `bash -n` and advisory shellcheck both miss them:
```bash
if err="$(bash -n "$s" 2>&1)"; then
  printf 'PASS  bash -n %s\n' "$s"
else
  printf 'FAIL  bash -n %s\n%s\n' "$s" "$err"
  FAILED=$((FAILED + 1))
fi
# and, as a hard gate:
if grep -nE 'mapfile|readarray|declare -A|\$\{[A-Za-z_][A-Za-z0-9_]*\^\^|\$\{[A-Za-z_][A-Za-z0-9_]*,,' "$s"; then
  printf 'FAIL  bash-4 construct in %s (bash-3.2 required)\n' "$s"; FAILED=$((FAILED + 1))
fi
```

### WR-06: `harness.lua` swallows the exit code when a command emits no output, conflating "ran, empty output, exit 0" with failure-adjacent states

**File:** `tests/e2e/lib/harness.lua:51-58,61-68`
**Issue:**
```lua
local ok, _, code = p:close()
local exit = code or (ok and 0 or 1)
```
When `p:close()` returns `code == 0` (a genuine success), `exit = code` is `0` — correct.
But the `code or (...)` idiom treats a returned `code` of `0` as truthy in Lua (0 is truthy),
so that path is fine. The real gap: `io.popen` cannot fail for a non-existent command on
most platforms — `io.popen("does-not-exist")` returns a valid handle whose `read` yields ""
and whose close reports the shell's 127. That is handled. However, if `io.popen` itself
returns nil (resource exhaustion), the function returns `("", 1)` — indistinguishable from a
real command that exited 1 with no output. Tests that assert `exit == 0` are safe, but tests
that assert a SPECIFIC non-zero code (e.g. `scene new` exit 2, `unknown scene` exit 1) could
be satisfied by an unrelated harness failure that also yields 1. The Tier-1 files mostly use
the child-`lua5.4 -e` path (which captures the real code) for exact-code assertions, so this
is latent rather than active, but the merged-stream `run_capture_all` is used for some
exit-code checks where a spurious 1 would mask the true cause.
**Fix:** Distinguish popen-spawn failure from command exit by returning a sentinel the
callers can recognize, or document that `run_capture_all` exit codes are reliable only for
the `== 0` / `~= 0` distinction, not for exact non-zero values. At minimum, comment the
`code or (ok and 0 or 1)` line to flag the popen-nil ambiguity.

### IN-02: `os.tmpname()` is a known-weak temp primitive used across the CLI unit tests

**File:** `tests/cli/build_dev_launcher_test.lua:80,94,110,149`; `tests/cli/setup_sh_test.lua:90`; `tests/cli/uninstall_idempotent_test.lua:93-94`
**Issue:** `os.tmpname()` returns a predictable path and creates a classic TOCTOU window
(the name is reserved but not opened atomically). In a shared `/tmp` this is a (low-severity)
symlink/race surface. These are local test harnesses, so impact is minimal, but the e2e
harness's own `scratch_dir` already uses the safer `TMPDIR + os.time + random-suffix mkdir`
pattern — the CLI tests could adopt it for consistency.
**Fix:** Prefer the harness `scratch_dir`-style unique-dir creation, or `mktemp` via the
shell, over `os.tmpname()`.

### IN-03: `math.random(1, 1e6)` passes a float bound; relies on Lua 5.4 auto-seeding

**File:** `tests/e2e/lib/harness.lua:75`; `tests/cli/uninstall_idempotent_test.lua:79`; `tests/cli/uninstall_test.lua:77`; `tests/e2e/tier1/install_cycle_e2e_test.lua` (via `scratch_dir`)
**Issue:** `1e6` is a Lua float; `math.random(1, 1e6)` is accepted only because `1e6` is
integral (a non-integral float bound would raise "number has no integer representation").
No `math.randomseed()` is called — this is fine in Lua 5.4 (auto-seeded per process) but
would produce identical sequences across runs in Lua 5.3, risking scratch-dir collisions if
the suite is ever run under an older interpreter. The runners pin `lua5.4`, so this is
informational.
**Fix:** Use an integer bound (`1000000`) for clarity, and if cross-version robustness is
ever wanted, seed explicitly.

### IN-04: Duplicated `read_bytes`/`rmrf`/`count_blocks`/`file_exists` helpers across Tier-1 files

**File:** `tests/e2e/tier1/install_cycle_e2e_test.lua:65-80`; `tests/e2e/tier1/install_resolver_e2e_test.lua:61-74`; `tests/e2e/tier1/scene_edge_e2e_test.lua:44-51`
**Issue:** `read_bytes`, `rmrf`, `count_blocks`, `file_exists`, `write_file` are re-declared
in multiple Tier-1 files with byte-identical bodies. The whole stated purpose of `harness.lua`
was to HOIST exactly this kind of copy-pasted block ("Every test file used to re-declare the
SAME check/run_capture/shquote/scratch_dir block… this module HOISTS that block once").
These FS helpers were not hoisted, so the duplication the harness was created to kill
partially survives.
**Fix:** Move `read_bytes`/`file_exists`/`rmrf`/`count_blocks`/`write_file` into `harness.lua`
(e.g. `h.read_bytes`, `h.rmrf`) and consume them from there.

### IN-05: `keys_siblings_e2e_test.lua` macOS branch is structurally unreachable on the only verified platform (latent, by design but untested)

**File:** `tests/e2e/tier1/keys_siblings_e2e_test.lua:97-117`
**Issue:** The entire macOS live-assertion block (the `on_path` loop) only executes when
`OS == "macos"`, which the file's own comments confirm never happens on this Linux mainline
(`require_tool` exits 0 first). This is the intended loud-skip design, but it means the
macOS branch — including the `on_path` helper and the per-sibling assertions — has never
been executed and could harbor latent bugs (e.g. `on_path` reads only the first line of
`command -v`, which is correct, but is untested). The exit-code composition
`h.footer() == 0 and xplat_rc or 1` is also subtle: it returns `xplat_rc` only when the
post-gate footer is clean, which on the skip path never runs (the `os.exit(0)` inside
`require_tool` fires first). Worth a comment confirming the skip path's exit is owned by
`require_tool`, not this line.
**Fix:** Add a CI lane (or a forced `OS` override hook) that exercises the macOS branch in
isolation so it is not dead-on-arrival when the Mac pass lands, and annotate the final
`os.exit` composition.
