# Phase 6.3: Distribution Channels (INSERTED) - Context

**Gathered:** 2026-06-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Make `wez`-CLI-binary releases **self-renewing, user-selectable, and reversible**:

1. A **scheduled rolling channel** for the project's own `wez` binary (datestamped
   nightly prereleases) alongside the existing pinned `v*` stable tags.
2. A **bootstrapper channel selector** so the user chooses which build to pull
   (`nightly` / `stable` / explicit tag) instead of the hardcoded `WEZ_RELEASE_TAG=v0.1.0`.
3. A first-class **`wez uninstall`** that works in the binary-only case (no cloned repo).

**Critical disambiguation (do not conflate):** this phase distributes the project's own
**`wez` CLI binary** (a GitHub release asset of THIS repo). It is NOT the upstream WezTerm
*application* channel — `tools/bootstrap-wezterm.sh` already resolves the WezTerm app's
upstream `nightly`/`pinned` target (P6-D09). Two separate "nightly" notions; this phase
owns the `wez`-binary one.

**Out of scope (own future phases):** asset compression format, rollback/downgrade UX,
checksum re-verification policy on channel switch (handled by existing `.sha256` contract),
README rewrite (Phase 6.4), macOS asset CI legs (Phase 7).

</domain>

<decisions>
## Implementation Decisions

### Channel model
- **D-01:** **Two channels** — `stable` (a moving pointer to the newest `v*` tag release)
  and `nightly` (rolling, rebuilt from main on a schedule). Explicit `vX.Y.Z` pins remain
  addressable as a third, explicit option.
- **D-02:** **Default channel = `nightly`** for a new user / the non-interactive one-liner —
  intentionally consistent with the WezTerm-*app* default (P6-D09): one mental model,
  "everything tracks nightly unless you pin." (This is a deliberate divergence from a
  "stable-by-default" norm; chosen for consistency with the app channel.)
- **D-03:** **Resolution mechanism** — `stable` resolves via GitHub's `/releases/latest`
  endpoint (which excludes prereleases, so nightlies are auto-filtered out). `nightly`
  resolves to the newest `nightly-*` prerelease, mirroring the existing
  `latest_nightly_datestamp` helper shape in `tools/bootstrap-wezterm.sh`.

### Rolling release shape (CI)
- **D-04:** **Datestamped prereleases** — each nightly is its own GitHub release tagged
  `nightly-YYYYMMDD`, marked prerelease. (Chosen over a single force-repointed `nightly`
  tag.) Release **assets are permanent** (Releases store, not the 90-day Actions-artifact
  store), so they never expire — but they also accumulate, which mandates D-06 pruning.
- **D-05:** **Cadence = weekly** cron (e.g. Monday) with a **skip-if-unchanged** guard:
  if `HEAD` equals the SHA of the last published nightly, the run is a no-op (no empty
  rebuild). The rolling channel keyword stays **`nightly`** by convention despite the
  weekly cadence (flagged; rename to `rolling` only if the user later objects).
- **D-06:** **Retention = keep newest 5** datestamped nightlies; the workflow prunes older
  `nightly-*` releases (`gh release delete`) after each successful publish.

### CI routing
- **D-07:** **One workflow file, two triggers** — `.github/workflows/release.yml` keeps
  `on: push: tags: v*` (→ stable publish) and gains `on: schedule` (→ nightly publish +
  prune). A single channel-resolution step branches on `github.ref`: a tag ref publishes
  stable; a schedule/dispatch ref publishes a datestamped nightly. **Tagging a commit is
  the act of cutting a stable release; everything else is nightly** (the user's rule).
  No manual channel flag in CI.
- **D-12:** **Keep the workflow matrix-shaped for Phase 7.** The nightly/schedule changes to
  `release.yml` MUST be structured so Phase 7 (macOS Parity Pass, D-18) can add the two macOS
  legs without rewriting the nightly/publish/prune logic — i.e. build/checksum/publish steps
  factored to run per-target, even though v1 still ships a single `ubuntu-latest` job. **No
  macOS work happens in 6.3** — it is gated on real-hardware verification (Homebrew lua 5.5≠5.4,
  the Intel runner `/usr/local` brew permission error, Apple-Silicon ad-hoc codesign). This is a
  "don't paint Phase 7 into a corner" constraint only, not new work.

### Selector UX (bootstrapper)
- **D-08:** **`WEZ_CHANNEL` env var + interactive TTY prompt.** `WEZ_CHANNEL=nightly|stable|<vX.Y.Z>`
  replaces the hardcoded `WEZ_RELEASE_TAG=v0.1.0` in `tools/build.sh` `download_release()`.
  - Non-interactive pipe path (`curl|bash`) → uses the env var, defaults to `nightly` (D-02).
  - Interactive TTY with no channel set → present a picker (nightly / newest stable /
    recent tags), mirroring the existing WezTerm version selector in `bootstrap-wezterm.sh`.

### `wez uninstall` surface
- **D-09:** **Front door over the engine.** `wez uninstall` is the documented user command;
  the existing `uninstall-state` (cli/commands/uninstall_state.lua) stays the internal engine
  it delegates to. No repo checkout required — everything targets user paths (sudo-free, D-18).
- **D-10:** **Binary self-deletion last.** The running `wez` binary unlinks itself as the
  FINAL step, after removing the managed config block / config dir / backups. On Linux/macOS
  unlinking a running executable is safe (the inode persists until process exit).
- **D-11:** **Confirm-then-remove-everything default** — no-arg `wez uninstall` prompts for
  confirmation on a TTY, then removes the managed block + config + binary + `wezterm.lua.bak.*`
  backups (matches today's `uninstall-state` default — least new behavior). `--yes` skips the
  prompt and is **required on a non-TTY pipe** (else abort, mirroring the D-03 no-TTY pattern).
  The engine's `--keep-config` / `--keep-cli` / `--keep-backup` flags are surfaced on
  `wez uninstall` to preserve individual pieces.

### Claude's Discretion
- Exact cron expression / day-of-week and UTC hour for the weekly schedule.
- `nightly-YYYYMMDD` collision handling if two runs land on the same date (e.g. `--clobber`
  vs suffix).
- Prune implementation details (sort + slice the `nightly-*` release list).
- Confirmation prompt wording and the precise no-op log line for skip-if-unchanged.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `tools/bootstrap-wezterm.sh` channel machinery (`WEZTERM_TARGET`, `latest_nightly_datestamp`,
  no-TTY abort, the TTY picker) is a direct template for the `WEZ_CHANNEL` selector (D-08).
- `cli/commands/uninstall_state.lua` already implements the full keep/remove decision matrix
  and sentinel-block excision — `wez uninstall` is a thin front door, not new removal logic (D-09).
- `release.yml`'s "Ensure release exists" idempotent create + `gh release upload --clobber`
  pattern carries over to nightly publishing.
- `.sha256` per-asset checksum contract (P6-D08) applies unchanged to nightly assets.

### Established Patterns
- **D-01 glue boundary** — `release.yml` and `tools/*.sh` make NO version/channel decisions in
  YAML/bash where avoidable; channel resolution that involves logic belongs near the binary.
  CI routing (D-07) is the allowed exception: a `github.ref` branch is trigger-plumbing, not
  install logic.
- **No-TTY abort** — non-interactive paths must resolve deterministically (default nightly for
  install; `--yes`-required for uninstall) rather than hang on a prompt (D-08, D-11).

### Integration Points
- `release.yml` schedule trigger ↔ GitHub Releases store (datestamped nightly objects + prune).
- `tools/build.sh download_release()` ↔ `WEZ_CHANNEL` ↔ GitHub `/releases/latest` + `nightly-*`
  prerelease resolution.
- `wez uninstall` ↔ `uninstall-state` engine ↔ self-deleting binary on user paths.

</code_context>

<specifics>
## Specific Ideas

- "In CI/CD detect if last commit has a tag — in that case it's stable, without a tag it's
  nightly." → captured as D-07 (the channel a build publishes to is derived from the trigger
  ref; tagging = cutting stable).
- Explicitly mirror the *existing* WezTerm version selector UX rather than invent a new one (D-08).
- Reuse the existing `uninstall-state` engine rather than duplicate removal logic (D-09).

</specifics>

<deferred>
## Deferred Ideas

- **Build/release badges → Phase 6.4.** README build-status / latest-release / nightly badges
  belong with the README audit + `/agent-md-refactor` rewrite (Phase 6.4), so they land in the
  final restructured README rather than one about to change. 6.3 builds the CI/release infra
  that makes them meaningful, but does NOT add badges. (User decision, 2026-06-17.)
- **macOS build legs → Phase 7.** Not deferred *ideas* but a hard phase boundary: the macOS
  nightly/stable legs are owned by Phase 7 (D-18), gated on real-Mac verification. 6.3 only keeps
  the workflow matrix-friendly for them (D-12).
- **Rename `nightly` → `rolling`** if the weekly cadence vs the `nightly` keyword proves
  confusing — kept as `nightly` for now (D-05).
- **Asset compression** (raw vs `.gz`) — P6-D01 left this open; still the planner's call,
  not re-decided here.
- **Rollback / downgrade UX** beyond pinning an explicit `vX.Y.Z` — not in scope.
- **Channel-switch checksum re-verification policy** — covered by the existing per-asset
  `.sha256` contract; no new behavior planned.

None of these are blockers — discussion stayed within phase scope.
