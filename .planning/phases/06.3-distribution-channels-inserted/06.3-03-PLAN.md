<objective>
Replace the hardcoded `WEZ_RELEASE_TAG=v0.1.0` pin in `tools/build.sh`
`download_release()` with a `WEZ_CHANNEL=nightly|stable|<vX.Y.Z>` selector (D-08).
A non-interactive pipe (the `curl|bash` remote-bootstrap path) defaults to
`nightly` (D-02) and resolves deterministically — it never hangs; an interactive
TTY with no channel set shows a numbered picker (nightly / newest stable / recent
tags) mirroring `bootstrap-wezterm.sh`'s existing selector SHAPE. Resolution
(D-03): `stable` → GitHub `/releases/latest` (which excludes prereleases, so the
Plan 02 nightlies are auto-filtered out); `nightly` → the newest `nightly-*`
prerelease (mirroring the `latest_nightly_datestamp` shape); `<vX.Y.Z>` → that
exact tag literally. The channel switch ONLY changes the resolved tag segment of
the download URL — it NEVER bypasses the existing verify-SHA-256-before-chmod
checksum gate (P6-D08), and a degraded/empty API resolution fails loudly rather
than installing an unverified asset.

Purpose: let the user choose which build to pull (the nightly channel Plan 02
publishes, the moving stable pointer, or an explicit pin) instead of being locked
to `v0.1.0`.
Output: a channel-aware `download_release()` in `tools/build.sh` and a
regression-guard test `tests/cli/build_channel_test.lua`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `WEZ_CHANNEL`/`WEZ_RELEASE_TAG` (env, user/installer-supplied) → URL construction | untrusted-ish channel string crosses into the download URL's tag segment |
| GitHub release API response → resolved tag | the API answer (latest / nightly-* list) drives which asset is fetched |
| downloaded asset → executable on disk | the fetched binary becomes `chmod +x dist/wez`; the `.sha256` gate is the trust boundary here |
| no-TTY pipe (`curl|bash`) → channel decision | a non-interactive path must resolve deterministically, never hang, never silently pick an unverified asset |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06.3-03-01 | Tampering | `WEZ_CHANNEL`/`WEZ_RELEASE_TAG` → download URL | mitigate | The resolved tag only fills the existing `${WEZ_RELEASE_BASE}/<tag>/<asset>` path; `WEZ_RELEASE_BASE` stays fixed to the project's releases host (not user-overridable to an arbitrary origin in the resolver). A `stable`/`nightly` value resolves via the project's own API; a literal `<vX.Y.Z>` is used only as a path segment. No path-traversal: the asset name is derived from `platform.sh` (`wez-<os>-<arch>`), not from the channel string, so a `../`-laden channel cannot escape `WEZ_RELEASE_BASE` |
| T-06.3-03-02 | Tampering | channel switch vs `.sha256` gate | mitigate | The channel switch changes ONLY the URL's tag segment; the verify-SHA-256-before-chmod block (build.sh lines 165-189) stays byte-identical — `.sha256` is fetched and compared, and `chmod +x` happens ONLY after a match (P6-D08). build_channel_test.lua asserts the verify markers survive the edit, so a future change that bypasses the gate fails the suite |
| T-06.3-03-03 | Spoofing / Denial of Service | degraded/empty API resolution | mitigate | A failed/empty/unparseable `/releases/latest` or `nightly-*` resolution returns NON-ZERO and `download_release()` aborts with a clear ERROR (P6-D01/D07 fail-loud) — it NEVER falls through to an empty tag or silently installs an unverified/wrong asset. Mirrors bootstrap-wezterm.sh's graceful-empty-degradation, hardened to fail-loud here because this path PLACES an executable |
| T-06.3-03-04 | Denial of Service | no-TTY pipe hang | mitigate | The `[ ! -t 0 ]` branch resolves deterministically to `WEZ_CHANNEL` (default `nightly`, D-02) and NEVER blocks on `read` — a `curl|bash` install can't hang waiting for a prompt (mirrors select_release no-TTY determinism) |
| T-06.3-03-05 | Tampering | API parse (control chars in release body) | mitigate | The resolver mirrors bootstrap-wezterm.sh's robust field extraction (`tr ',' '\n'` + scoped `grep -oE`, NO full-document jq parse) which already tolerates C0 control chars in release bodies; the resolved value is constrained to a tag-shaped token before use |
| T-06.3-03-SC | Tampering | npm/pip/cargo installs | mitigate | N/A — this plan installs NO third-party packages (pure bash glue + a Lua test reusing the in-repo harness); the only network call is the project's own GitHub release API via the existing `fetch()` (curl/wget). The package-legitimacy gate has nothing to clear |
</threat_model>
