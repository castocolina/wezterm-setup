<objective>
Extend the single `.github/workflows/release.yml` so the project's own `wez` CLI
binary is published on TWO channels from ONE workflow (D-07): a pushed `v*` tag
cuts a STABLE release (the existing, unchanged path), while a weekly `schedule`
cron — and a manual `workflow_dispatch` — publishes a datestamped
`nightly-YYYYMMDD` PRERELEASE (D-04). The channel a build targets is derived
purely from `github.ref` (tag ref → stable, anything else → nightly); there is no
manual channel flag. The nightly path reuses the existing per-asset `.sha256`
contract (P6-D08), the idempotent create + `--clobber` upload shape, a
skip-if-unchanged guard so an unchanged HEAD is a no-op (D-05), and a prune step
that keeps only the newest 5 `nightly-*` releases (D-06). All steps stay factored
so Phase 7 can add the two macOS legs without rewriting nightly logic (D-12) — NO
macOS work happens here (v1 stays a single `ubuntu-latest` job).

Purpose: make `wez` releases self-renewing — a nightly channel tracks `main`
automatically alongside the pinned stable tags — without drifting from the
maintainer/`make publish` asset contract.
Output: a modified `release.yml` with a `schedule` trigger, `github.ref` channel
routing, datestamped nightly publish, skip-if-unchanged guard, and prune-to-5.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub event (push tag / schedule / dispatch) → workflow | the trigger ref is the only channel signal (D-07); a malicious ref shape must not escalate scope |
| workflow job → GitHub Releases store | create/upload/delete of release objects via `gh` + `github.token` |
| `github.token` (job secret) → steps | the scheduled job runs unattended; secrets must not leak to logs or be over-scoped |
| prune `gh release delete` → release objects | destructive; must be impossible to target a stable `v*` release |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06.3-02-01 | Elevation of Privilege | workflow `permissions` | mitigate | `permissions: contents: write` is the ONLY scope and is unchanged; it is exactly what `gh release create/upload/delete` need and carries identically to the scheduled job — no `id-token`/`packages`/`actions` write added (least privilege, T-06-03-03 carried forward) |
| T-06.3-02-02 | Tampering / Denial of Service | prune `gh release delete` | mitigate | The prune step filters `gh release list` to the `nightly-` prefix ONLY and re-asserts a `case "$tag" in nightly-*)` guard immediately before each `gh release delete`; a `v*` stable release can never be reached. Prune runs only on the nightly channel (`env.CHANNEL == 'nightly'`) and only on a successful, non-skipped publish (D-06) |
| T-06.3-02-03 | Spoofing / Tampering | channel routing on `github.ref` | mitigate | The channel is derived ONLY from `startsWith(github.ref, 'refs/tags/')` — a tag ref → stable, everything else → nightly (D-07). There is NO manual channel input to spoof; a non-tag ref can NEVER publish a stable (non-prerelease) release, and a tag ref can NEVER trigger nightly prune |
| T-06.3-02-04 | Information Disclosure | `github.token` in the scheduled (unattended) job | mitigate | The token is consumed only via `env: GH_TOKEN: ${{ github.token }}` on the `gh` steps; no `echo`/`set -x` of the token, no third-party action to exfiltrate it, all actions pinned to immutable release tags (`actions/checkout@v4.2.2`, T-06-03-01); the scheduled job adds no new secret surface |
| T-06.3-02-05 | Tampering | nightly asset integrity | mitigate | Nightly reuses the per-asset `.sha256` producing block byte-identically (P6-D08) — `sha256sum || shasum -a 256` over `wez-<os>-<arch>`; the consumer (Plan 03) verifies it before chmod, so a nightly asset is held to the SAME supply-chain integrity contract as a stable asset |
| T-06.3-02-SC | Tampering | npm/pip/cargo installs | mitigate | N/A — this plan installs NO third-party packages; toolchain provisioning is the existing `tools/ci-setup-toolchain.sh` (unchanged), and the only actions are `gh` (first-party, github.token auth) + the pinned `actions/checkout`. The package-legitimacy gate has nothing to clear |
