<objective>
Add a first-class `wez uninstall` command: a thin Lua front door over the existing
`uninstall-state` removal engine (D-09) that works in the binary-only case (no repo
checkout). It confirms-then-removes-everything by default on a TTY, requires `--yes`
on a non-TTY pipe (D-11/D-03), surfaces the engine's `--keep-config`/`--keep-cli`/
`--keep-backup` flags, and orders removal so the running `wez` binary self-deletes
LAST (D-10). Repoint the `tools/uninstall.sh` / `make uninstall` glue to the new
front door so the documented user command and the Makefile path stay consistent.

Purpose: make releases reversible with a single documented command, mirroring the
`wez update` front-door pattern, without duplicating any removal logic.
Output: `cli/commands/uninstall.lua` (new), 3-place spec registration, repointed
`tools/uninstall.sh`, and `tests/cli/uninstall_test.lua` (new).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user shell → `wez uninstall` | the destructive action enters here; confirmation/`--yes` gate it |
| `wez uninstall` → filesystem (user paths) | block/config/backups/binary removal; sudo-free, user-paths only |
| `make uninstall`/`tools/uninstall.sh` → `wez uninstall` | non-interactive glue; passes `--yes` so the pipe is intentional, not a hang |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06.3-01-01 | Denial of Service | `wez uninstall` destructive default | mitigate | Confirm-then-remove on TTY (D-11); non-TTY without `--yes` aborts non-zero and removes NOTHING (the engine is never called) — no accidental data loss via a stray pipe |
| T-06.3-01-02 | Tampering | removed paths | mitigate | Removal is DELEGATED to the audited `uninstall_state` engine which removes ONLY the sentinel-block range (byte-identical user lines, T-06-01), the `wezterm-setup/` subtree (never its parent, T-06-03), and `wezterm.lua.bak.*`; the front door adds NO new path globs |
| T-06.3-01-03 | Elevation of Privilege | binary self-delete | accept | The running binary is unlinked via `os.remove` on a user path (`~/.local/bin/wez` or `$WEZ_BIN`); no sudo, no system path; inode persists until process exit (safe on Linux/macOS) — no privilege boundary crossed |
| T-06.3-01-04 | Tampering | shelled paths | mitigate | Any path the front door passes to a shell goes through `install_state.shquote` (CR-02); the engine already shquotes its `rm -rf`/`ls` (uninstall_state.lua line 130/145) |
| T-06.3-SC | Tampering | npm/pip/cargo installs | mitigate | N/A — this plan installs NO third-party packages (pure in-repo Lua + bash glue); the package-legitimacy gate has nothing to clear |
</threat_model>
