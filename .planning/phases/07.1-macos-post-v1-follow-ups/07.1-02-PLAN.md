<objective>
Fix the cross-platform `wez keys --json` bug (macOS deviation #5): `cli/commands/keys.lua:262`
does a bare `require("dkjson")`, but the vendored module is bundled as `cli.vendor.dkjson` — so
the SHIPPED luastatic binary fails `module 'dkjson' not found` (Linux and macOS alike). Replace
the bare require with the project's proven dual-resolve idiom and add a regression that pins the
BUNDLE module name so it can't recur (D-04/D-05).

Purpose: the bug is invisible in the current test harness because `keys_test.lua:18` puts
`cli/vendor/?.lua` on `package.path`, letting the bare name resolve under the runner while the
bundle has no top-level `dkjson` module. The fix mirrors `cli/lib/shell.lua:32-33` exactly
(`pcall(require, "cli.vendor.dkjson")`, fall back to bare `dkjson`). No `build.sh` change is
needed — `tools/build.sh:211-229` already globs `cli/vendor/*.lua` into the bundle.
Output: a two-line require change in `keys.lua` + a `--json` parse regression that requires the
bundle module name and round-trips `build_json` output. Closes deviation #5 (cross-platform);
contributes to INST-08 macOS verification. NOTE: the fix reaches end-user binaries only via a
NEW release (the v1.0.0 asset still carries the bug) — non-gating per phase scope.
</objective>
