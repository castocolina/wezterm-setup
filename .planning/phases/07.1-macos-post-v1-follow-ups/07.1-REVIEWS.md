In `07.1-02-PLAN.md`, Task 1's `<behavior>` block labels **two** assertions "(RED now)", but the
plan's own prose concedes the first one passes today:

- "Test 1 (RED now): `require("cli.vendor.dkjson")` succeeds … **It should PASS even today** via
  package.path … so this assertion guards the require PATH, not the fix."
- "Test 2 (RED now): a check that `cli/commands/keys.lua` source does NOT contain a bare
  `require("dkjson")` … **FAILS today**."

Only the second assertion (the source-text guard) is the actual RED condition. Labeling a check
that the plan says will PASS as "RED now" is a semantic contradiction: the TDD RED-confirmation
step (`test $? -ne 0`) depends on the executor knowing exactly which check produces the failure.

**Fix:** relabel so only the genuinely-failing source-guard carries "(RED now)" — e.g.
rename the bundle-name `require` assertion to **"Test 1 (GREEN today — pins the bundle module
name / guards the require path, not the fix)"** and the source-text guard to **"Test 2 (RED now
— fails until keys.lua:262 is fixed; this is the RED-confirmation check)"**. No change to the
assertions themselves, the action, the acceptance criteria, or the GREEN task — labels only.
