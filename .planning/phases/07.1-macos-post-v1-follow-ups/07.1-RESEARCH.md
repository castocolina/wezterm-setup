## Summary

This is a small, concrete fix phase — three code/doc fixes plus one self-run verification kit — on top of an already-shipped v1.0.0. All findings are anchored in this repo's own source (no external library research needed): the symlink precedent, the luastatic bundle mechanism, the vendor-require idiom, and the existing TDD test patterns all already exist in-tree and just need mirroring. The published `v1.0.0` release already carries `wez-macos-aarch64` + `.sha256` [VERIFIED: `gh release view v1.0.0`], so the Apple-Silicon check is a pure download-and-observe runbook with no new build work.

The single highest-risk item — "will the `dkjson` require fix actually resolve inside the shipped luastatic binary?" — resolves cleanly and with HIGH confidence: `tools/build.sh` globs every `cli/**/*.lua` (relative paths, cwd=REPO_ROOT) into the bundle, so `cli/vendor/dkjson.lua` is **already baked in** as module `cli.vendor.dkjson`. The bug is purely that `keys.lua:262` requires the bare name `"dkjson"` instead of the bundle module path. The project already has a proven idiom for exactly this (`cli/lib/shell.lua:32-33`: try `cli.vendor.dkjson`, fall back to bare `dkjson`). The fix is a two-line change to match it; no build.sh change is needed.

**Primary recommendation:** Mirror existing in-repo idioms verbatim — (1) copy `install_linux`'s `ln -sfn` symlink block into `install_macos` with the macOS bundle path; (2) change `keys.lua:262` to the `pcall(require, "cli.vendor.dkjson")` dual-resolve idiom already used in `cli/lib/shell.lua`; (3) extend `tests/cli/bootstrap_macos_test.lua` (symlink TEXT assertion) and `tests/cli/keys_test.lua` (a `cli.vendor.dkjson`-path `--json` parse assertion); (4) ship the Silicon check as a runbook section in `docs/macos-verification.md` plus the keybindings rationale note in the same doc.

## The luastatic Bundle Mechanism (highest-risk item — RESOLVED)

**Question:** Will fixing the require to `cli.vendor.dkjson` actually pull dkjson into the static binary?

**Answer: Yes — dkjson is ALREADY in the bundle. No build.sh change is needed.** [VERIFIED: codebase, `tools/build.sh:211-229`]

How the bundle is built (`tools/build.sh:211-229`):

```bash
# Collect every Lua source under cli/ (entry + spec + commands + vendored deps).
# CRITICAL: luastatic derives each bundled module's name from the PATH STRING it
# is given, so we must invoke it from REPO_ROOT with RELATIVE paths (cli/spec.lua
# -> module `cli.spec`). ...
local sources=()
while IFS= read -r f; do sources+=("$f"); done \
  < <(find cli -type f -name '*.lua' ! -name 'wez.lua' | sort)

(
  cd "${REPO_ROOT}"
  luastatic "${ENTRY}" "${sources[@]}" ${liblua:+"${liblua}"} ${lua_cflags}
)
```

Key facts that make the fix safe:
1. The `find cli -type f -name '*.lua' ! -name 'wez.lua'` glob **already includes `cli/vendor/dkjson.lua`** (it matches `cli/vendor/*.lua` — confirmed alongside `argparse.lua` and `tinytoml.lua`, both already required as `cli.vendor.*`). [VERIFIED: codebase]
2. luastatic derives the module name from the **relative path string** with `/`→`.`, so `cli/vendor/dkjson.lua` is baked as module **`cli.vendor.dkjson`** (the build runs with `cwd=REPO_ROOT`). [VERIFIED: build.sh comment + codebase]
3. The bare `require("dkjson")` at `keys.lua:262` fails because the bundle has **no** top-level `dkjson` module — only `cli.vendor.dkjson`. [VERIFIED: `deferred-items.md` 07-05 entry: "no module 'dkjson' in luastatic bundle"]

**Established vendor-require idiom (mirror this exactly):** `cli/lib/shell.lua:32-33` [VERIFIED: codebase]

```lua
local ok, dkjson = pcall(require, "cli.vendor.dkjson")
if not ok then ok, dkjson = pcall(require, "dkjson") end
```

The same dual-resolve pattern is used for argparse (`cli/spec.lua:79`) and tinytoml (`cli/lib/recipe.lua:20`). The bare-name fallback covers the dev source-launcher / on-package.path resolution; the `cli.vendor.dkjson` first-try covers the shipped bundle. **Use this exact two-line form in `keys.lua`.**

## Architecture Patterns

### Pattern 1: Mirror `install_linux`'s symlink block in `install_macos`
**What:** `install_macos()` (ends at `bootstrap-wezterm.sh:566`) currently places `~/Applications/WezTerm.app` but never symlinks the CLI onto PATH. Add the same `mkdir -p "${BIN_DIR}"` + `ln -sfn` block `install_linux` uses.
**When to use:** Right after the `cp -R` bundle placement + the run-the-binary evidence check (around `bootstrap-wezterm.sh:557-565`).
**Source idiom (`install_linux`, `bootstrap-wezterm.sh:449-451`):** [VERIFIED: codebase]
```bash
mkdir -p "${BIN_DIR}"
ln -sfn "${target}" "${BIN_DIR}/wezterm"
log "symlinked ${BIN_DIR}/wezterm -> ${target}"
```
**macOS adaptation (the bundle binary path is fixed):**
```bash
# Symlink the bundled WezTerm CLI onto the user PATH so `wez scene` resolves
# `wezterm` by name (the .app bundle does not export it). Mirrors install_linux,
# sudo-free, user-path only (D-01 / A-4).
local wez_bin="${app_dir}/WezTerm.app/Contents/MacOS/wezterm"
mkdir -p "${BIN_DIR}"
ln -sfn "${wez_bin}" "${BIN_DIR}/wezterm"
log "symlinked ${BIN_DIR}/wezterm -> ${wez_bin}"
```
- `BIN_DIR` is already defined (`bootstrap-wezterm.sh:67`, `${WEZTERM_BIN_DIR:-${HOME}/.local/bin}`) and reachable inside `install_macos`. [VERIFIED: codebase]
- `ln -sfn` is idempotent (`-f` force-overwrite, `-n` treat existing symlink-to-dir as a file not a target dir) — a re-install/update overwrites cleanly, matching the Linux behavior. [VERIFIED: codebase — same flags used in install_linux]
- The existing PATH-not-on-PATH note (`bootstrap-wezterm.sh:465-468`) is Linux-only inside `install_linux`; consider mirroring the same `case ":${PATH}:"` note in `install_macos` for parity (optional, low-value — `verify-macos.sh:61` already probes `wezterm` on PATH).

### Pattern 2: Dual-resolve vendor require (dkjson fix)
**What:** Replace `keys.lua:262`'s `local json = require("dkjson")` with the proven `cli/lib/shell.lua` idiom.
**Source (`cli/lib/shell.lua:31-36`):** [VERIFIED: codebase]
```lua
function M.decode_json(text)
  local ok, dkjson = pcall(require, "cli.vendor.dkjson")
  if not ok then ok, dkjson = pcall(require, "dkjson") end
  if not ok or type(dkjson) ~= "table" then return nil end
  return dkjson.decode(text)
end
```
**Adaptation in `keys.lua` (it needs `encode`, so resolve the module then encode):**
```lua
if args.json then
  local ok, json = pcall(require, "cli.vendor.dkjson")
  if not ok then ok, json = pcall(require, "dkjson") end
  if not ok or type(json) ~= "table" then
    io.stderr:write("wez keys: JSON encoder (dkjson) unavailable\n")
    return 1
  end
  io.write(json.encode(M.build_json(entries, conflicts), { indent = true }))
  io.write("\n")
  return 0
end
```
**Note for the test:** `tests/cli/keys_test.lua:179` currently does `require("dkjson")` and only passes because the test harness puts `cli/vendor/?.lua` on `package.path` (`keys_test.lua:18`). That dev-only path is why the bug went uncaught in CI. The new regression should assert the **bundle-path** require (`require("cli.vendor.dkjson")`) round-trips, and ideally drive the actual `keys.run({json=true})`-shaped path. See Validation Architecture.

### Anti-Patterns to Avoid
- **Editing `build.sh` to "add dkjson to the bundle":** It is already bundled. Adding it again (or special-casing it) is redundant and risks breaking the relative-path module-naming invariant. The fix is in `keys.lua` only. [VERIFIED: build.sh:211-219]
- **Prepending `WezTerm.app/Contents/MacOS` to PATH via shell-rc:** Violates D-01 (no shell-rc edits, no broad PATH manipulation). Use the symlink.
- **Stripping `com.apple.quarantine` in the installer:** D-07 (Phase 7) deliberately does NOT strip quarantine; `bootstrap_macos_test.lua:163,186` asserts no `xattr` mutation. Do not add one. The Silicon check observes Gatekeeper behavior; it does not pre-empt it in the installer.
- **Bare `require("dkjson")` anywhere new:** always use the `cli.vendor.dkjson`-first dual-resolve.

## Common Pitfalls

### Pitfall 1: Ad-hoc codesign ALWAYS fails Gatekeeper assessment (`spctl`) — that is expected
**What goes wrong:** The Silicon check (or anyone) runs `spctl -a -vv wez` and sees "rejected", and concludes the binary is broken.
**Why it happens:** The arm64 `wez` is **ad-hoc** codesigned (`codesign --force --sign -`, `build.sh:257`), not Developer-ID signed/notarized. Gatekeeper's `spctl` assessment ALWAYS rejects ad-hoc signatures — build.sh's own comment (`build.sh:250-254`) calls this "Pitfall 4" and deliberately does NOT gate the build on `spctl`. [VERIFIED: codebase]
**How to avoid:** The Silicon check's evidence is **`codesign --verify --verbose wez` succeeds** + **the binary actually runs** (`wez version`, `wez doctor` exit 0) — NOT `spctl`. For a CLI binary invoked from a terminal (not double-clicked from Finder), Gatekeeper does not block execution the way it blocks `.app` launches; the real concern is the `com.apple.quarantine` xattr on browser-downloaded files.
**Warning signs:** A check that treats `spctl` rejection as failure.

### Pitfall 2: `com.apple.quarantine` only attaches to BROWSER downloads, not curl/CLI
**What goes wrong:** The end-user downloads `wez-macos-aarch64` via a browser, then `wez` is killed/blocked on first run; the check doesn't anticipate it.
**Why it happens:** macOS attaches `com.apple.quarantine` to files downloaded by quarantine-aware apps (Safari/Chrome). Phase 7 (07-04 Task 2, D-07) proved the **curl-download path sets NO quarantine** and Gatekeeper did not block first launch. A browser download is different. [VERIFIED: `MACOS-PARITY-AND-FOLLOWUPS.md` §C-1]
**How to avoid:** The Silicon check should (a) prefer `curl`/`gh release download` to avoid quarantine entirely, AND (b) document the fallback for browser downloads: `xattr -d com.apple.quarantine wez` or right-click→Open. Have the check observe `xattr -p com.apple.quarantine wez` (absent = clean) as part of its report.
**Warning signs:** "killed: 9" / "cannot be opened because the developer cannot be verified".

### Pitfall 3: The dkjson bug is INVISIBLE in the dev test harness
**What goes wrong:** A regression test that just does `require("dkjson")` (like the current `keys_test.lua:179`) passes in CI but the shipped binary still fails.
**Why it happens:** `keys_test.lua:18` puts `cli/vendor/?.lua` on `package.path`, so the bare name resolves under the test runner. The luastatic bundle has no such path. [VERIFIED: codebase]
**How to avoid:** The new `--json` regression must require **`cli.vendor.dkjson`** (the bundle module name), and/or exercise `keys.run({json=true})`'s actual code path so it goes through the fixed dual-resolve. Asserting the OUTPUT is JSON-valid (decode round-trip) + exit 0 is the contract.
**Warning signs:** Test green but `dist/wez keys --json` still tracebacks.

### Pitfall 4: macOS BSD tools differ from GNU (already handled in-tree, keep using the in-tree idioms)
**What goes wrong:** Using `sha256sum`, GNU `ln` flags, or GNU `tar` flags that don't exist on macOS.
**Why it happens:** macOS ships BSD coreutils. The repo already learned this (build.sh's `shasum` branch; the removed BSD-only tar flag noted at `bootstrap-wezterm.sh:436-437`).
**How to avoid:** Reuse the in-tree portable idioms (`ln -sfn` works on both; `shasum -a 256` for digests). Don't introduce GNU-only flags.
