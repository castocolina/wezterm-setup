## Summary

Adversarial deep review of the Phase 07.1 macOS post-v1 follow-ups: the `wez keys --json`
dkjson dual-resolve fix (deviation #5), the `install_macos` user-PATH symlink (deviation #6 /
A-4), and the NEW download-and-execute kit `tools/silicon-check.sh` (INST-08).

Headline: **no Critical findings.** The security-sensitive invariants of `silicon-check.sh`
hold under scrutiny — checksum verification *does* precede `chmod +x` and execution, downloads
land only in a `mktemp -d` scratch dir removed by an EXIT trap, no `sudo`/`hdiutil`/`spctl`,
quarantine/codesign are observed not mutated, and the official-host URL is built from a pinned
`REPO`/`TAG` (not attacker-controlled). The dkjson resolve fix correctly mirrors the
`shell.lua:decode_json` idiom and the regression test pins it.

However, several robustness gaps in the download-and-execute path warrant attention before this
kit is handed to an end-user on hardware the project's agents cannot test: a checksum-format
trust gap (whitespace-only `.sha256` passes the non-empty guard), a `set -e` masking issue
around `gh`'s partial-download failure mode, and a missing integrity gate on the *downloaded
binary's* own arch/format before it is executed. The classification-classify path in `keys.lua`
carries one real correctness gap (mods are matched normalized but rendered raw, so the conflict
display can mis-show modifier order) plus dead-code in `actions_equivalent`.

There were no `<structural_findings>` provided, so this is narrative-only.

## Warnings

### WR-01: `silicon-check.sh` checksum guard accepts a whitespace-only / malformed `.sha256`

**File:** `tools/silicon-check.sh:91-95`
**Issue:** `want="$(awk '{print $1}' "${SUMS_PATH}")"` then guards only `[ -z "${want}" ]`.
`awk '{print $1}'` returns the first field of the first *record*. If the `.sha256` asset is
empty the guard catches it, but if it contains a non-hex token (a truncated download, an HTML
error page that happened to be saved as the `.sha256`, or a leading non-hex line), `want` is
non-empty garbage and the script proceeds to a `[ "${want}" != "${got}" ]` compare. That
compare will mismatch and abort — so it fails *closed* in the common case, which is good — but
the guard gives a false sense of validation: it never confirms `want` is a 64-char hex digest.
A `.sha256` whose first line is, say, a `<html>` error body whose first field coincidentally
equalled the computed hash is implausible, but a `.sha256` that begins with the *correct* digest
on a wrapped/continued line is silently accepted. This is verify-before-run hygiene on an
execute-a-remote-binary path.
**Fix:**
```bash
want="$(awk 'NR==1{print $1}' "${SUMS_PATH}")"
case "${want}" in
  [0-9a-fA-F]*) [ "${#want}" -eq 64 ] || { err "checksum is not a 64-hex SHA-256 in ${SUMS}"; exit 1; } ;;
  *) err "no valid SHA-256 found in ${SUMS} — refusing to run an unverified binary"; exit 1 ;;
esac
```

### WR-02: `gh release download` partial-success leaves an unverifiable/zero-byte asset, and `set -e` can abort before the checksum gate reports

**File:** `tools/silicon-check.sh:62-81`
**Issue:** `download()` tries `gh` first and only falls back to `curl` when the *whole* `gh`
invocation returns non-zero. `gh release download ... --clobber` can write a partial/empty file
and still exit non-zero on a network blip, but the `2>/dev/null` swallows the diagnostic, the
fallback `curl` then runs against the same `${WORK}` dir, and a `curl -fsSL` failure under
`set -e` aborts the whole script *before* the report block is ever printed. The script's stated
contract (lines 175-178) is "always give the user a pasteable block; only the checksum is a hard
fail" — but a download failure exits the script with no report and no actionable line beyond
curl's terse stderr. For a kit run by a non-developer end-user on hardware the team cannot
reproduce on, a clean "DOWNLOAD FAILED — check network / tag exists" report path matters.
**Fix:** Trap the download failure and emit a structured failure report instead of letting
`set -e` kill the run bare:
```bash
if ! download "${ASSET}"; then err "could not download ${ASSET} from ${REPO}@${TAG}"; exit 1; fi
if ! download "${SUMS}"; then err "could not download ${SUMS} from ${REPO}@${TAG}"; exit 1; fi
```
and verify both files are non-empty (`[ -s "${ASSET_PATH}" ] && [ -s "${SUMS_PATH}" ]`) before
the checksum step so a 0-byte `gh` partial is caught explicitly, not as a hash mismatch.

### WR-03: The downloaded binary is run with no arch/Mach-O format gate — wrong-arch or corrupt binary is `chmod +x`'d and exec'd

**File:** `tools/silicon-check.sh:111, 144, 150`
**Issue:** After the checksum passes, the asset is `chmod +x`'d and executed (`version`, then
`doctor`) regardless of whether it is actually a Mach-O arm64 binary. The checksum only proves
"this is the published asset" — it does NOT prove the asset is runnable on *this* machine. On
the documented "run on the wrong arch and it just won't run" path the failure is caught by the
`if`/`||` and reported, which is fine. But there is no `file`/`lipo -archs` observation in the
report, so a user pasting a failed-to-run report has no signal distinguishing "wrong arch" from
"corrupt binary" from "Gatekeeper killed it (SIGKILL 9)". Given that ad-hoc-signed arm64
binaries are documented to be SIGKILL'd on first run (macos-verification.md:89-92), the report
should surface `file`/`lipo` + the kill signal so the human triage in the runbook landing spot is
actionable.
**Fix:** Add an observe-only line before running:
```bash
ARCH_INFO="$(file -b "${ASSET_PATH}" 2>/dev/null; lipo -archs "${ASSET_PATH}" 2>/dev/null)"
# ... and add `binary format : ${ARCH_INFO}` to the REPORT block.
```

### WR-04: `keys.lua` matches bindings on normalized mods but renders/keys them raw — conflict and entry output can show inconsistent modifier order

**File:** `cli/commands/keys.lua:127-134, 142-157, 282, 289`
**Issue:** `id_of()` canonicalizes mods (`norm_mods` sorts `CTRL|SHIFT` == `SHIFT|CTRL`) for
cross-source matching — correct. But the `entries` and `conflicts` records store the **raw**
`e.mods` / `o.mods` (lines 129, 145, 153), and the human renderer prints that raw string
(lines 282, 289). So two sources that legitimately match under normalization can display
`SHIFT|CTRL` for one binding and `CTRL|SHIFT` for another, and a conflict row shows OUR raw mods
order rather than a canonical one. This is a display-correctness defect: the tool's whole job
(DIAG-03) is to truthfully show who-wins, and inconsistent modifier ordering in the output
undermines that. It is not a matching bug (matching uses the normalized id), only a rendering
inconsistency.
**Fix:** Store the canonical form for display, e.g. set `mods = norm_mods(e.mods)` (and
`norm_mods(o.mods)`) when building `entries`/`conflicts`, or normalize at render time in the
`("%-18s..."):format(...)` lines.

### WR-05: `wezterm_datestamp_ge` does a numeric string compare that breaks at year 2100 / non-8-digit inputs

**File:** `tools/bootstrap-wezterm.sh:81-83` (touched-context for the macOS symlink change)
**Issue:** `[ "$1" -ge "$2" ]` does an *arithmetic* compare on the datestamps. The extractor
`wezterm_version_datestamp` greps `[0-9]{8}` and takes the first match — but it can match an
8-digit run that is NOT a date (e.g. a short SHA fragment `12345678` if it appears before the
real datestamp, or a version like `20260604` followed by `-145453`). Because the compare is
arithmetic, a malformed 8-digit value still "compares" and can wrongly satisfy or fail the floor
gate. `grep -oE '[0-9]{8}' | head -n1` assumes the date is always the first 8-digit run, which
holds for the real `YYYYMMDD-HHMMSS-sha` format but is fragile against any string drift. This is
pre-existing in the file but lives in the diff context of the macOS change.
**Fix:** Anchor the extractor to the known format and validate it is a plausible date range
before the arithmetic compare (e.g. `case "$1" in 20[0-9][0-9][01][0-9][0-3][0-9]) ;; *) return 1;; esac`).

### WR-06: `silicon-check.sh` ignores the cleanup `rm -rf` failure and the `mktemp` template can collide with a hostile `$TMPDIR`

**File:** `tools/silicon-check.sh:48-51`
**Issue:** `WORK="$(mktemp -d "${TMPDIR:-/tmp}/wez-silicon-check.XXXXXX")"` interpolates an
unvalidated `$TMPDIR` into the template. If `$TMPDIR` is unset/`/tmp` (normal) this is fine, but
a caller-controlled `$TMPDIR` containing a path that does not exist makes `mktemp` fail, and
under `set -e` the script aborts with a bare mktemp error and no report. More importantly the
downloaded-and-executed binary is run *from* this scratch dir; on a shared/multi-user `/tmp` the
predictable prefix `wez-silicon-check.` plus the world-tradition of `/tmp` does not by itself
create a TOCTOU on the binary (the `XXXXXX` randomization + the EXIT trap mitigate it), but the
script never asserts `${WORK}` was created with restrictive perms (`mktemp -d` does give 0700 on
macOS/BSD — acceptable — but this is not asserted/documented).
**Fix:** Validate the dir was created (`[ -d "${WORK}" ] || { err "scratch dir creation failed"; exit 1; }`)
and prefer the no-template default form `mktemp -d` (BSD/macOS supports it) to avoid `$TMPDIR`
interpolation surprises; note the 0700 expectation in a comment.

## Info

### IN-01: `actions_equivalent` is partially dead — the caller's `tostring` pre-check makes the table-branch unreachable for the conflict it guards

**File:** `cli/commands/keys.lua:91-96, 148-149`
**Issue:** The conflict check is `tostring(eff.action) ~= tostring(o.action) and not actions_equivalent(o.action, eff.action)`. When `o.action` is a declarative TABLE, `tostring(o.action)` is `"table: 0x..."`, which never equals the effective action string, so the first clause is always true; `actions_equivalent` then returns `true` for the table case, so the whole `and` is false and no conflict is recorded. The logic is *correct* (declarative tables rely on the absence check), but the `tostring(...) ~= tostring(...)` pre-clause is redundant with `actions_equivalent` and makes the intent hard to read. Our `ours` records always carry declarative tables (confirmed in `keybindings.lua` — `action = { type = ... }`), so the string branch of `actions_equivalent` is never exercised in production, only in the synthetic test fixtures.
**Fix:** Drop the redundant `tostring ~= tostring` pre-clause and let `actions_equivalent` be the sole decider, or add a comment that the string branch is test-only since production `ours` is always declarative.

### IN-02: `category_of` infers from `tostring(rec.action)` but is only ever called on effective (string-action) records — silent assumption

**File:** `cli/commands/keys.lua:71-83, 132`
**Issue:** `category_of` does `tostring(rec.action)` and `a:find("Tab")` etc. It is only called on `effective` entries (line 132), whose `action` is a verbatim string from `showkeys.parse`, so the inference works. If a future refactor ever calls `category_of` on an `ours` record (declarative table), `tostring` yields `"table: 0x..."` and every binding silently falls to `"Other"`. The `rec.category` short-circuit at the top is also dead today because effective records never carry a `category` field. Not a current bug; a latent footgun.
**Fix:** Add an assertion/comment that `category_of` expects a string-action effective record, or normalize the action to a string at the parse boundary.

### IN-03: `load_our_bindings` drops `disabled_defaults` despite the comment implying they inform conflicts

**File:** `cli/commands/keys.lua:216-232`
**Issue:** The comment (lines 228-231) says disabled defaults "inform conflict reasoning if needed later" but the function returns only `mod.keys`. A WezTerm default that we explicitly disabled (e.g. `k`+`SUPER`, see `keybindings.lua:135-136`) will appear in `baseline` and, if still present in `effective`, be labeled `default` rather than recognized as "ours, intentionally removed." This is a known/accepted scope cut per the comment, but the dead `disabled_defaults` reference is misleading.
**Fix:** Either consume `disabled_defaults` to suppress false `default` labels, or trim the comment to state plainly that disabled defaults are out of scope for this classifier.

### IN-04: `capture()` discards stderr and conflates "no session" with "command missing"

**File:** `cli/commands/keys.lua:204-211, 238-243`
**Issue:** `io.popen(cmd .. " 2>/dev/null")` throws away stderr, so when `wezterm show-keys --lua` fails the user gets the generic "a running WezTerm session is required" message even if the real cause is `wezterm: command not found` (relevant on macOS where the symlink fix in `bootstrap-wezterm.sh:573-576` is exactly what makes `wezterm` resolvable by name). Cross-file: the deviation #6 symlink fix exists precisely because `wezterm`-by-name can be absent on macOS; this error path would mask that very failure mode.
**Fix:** Capture stderr to a temp or fold it into the message so "command not found" vs "no session" is distinguishable.

### IN-05: `silicon-check.sh` `DOCTOR_TAIL` via `tail -3` can leak ANSI/control bytes into the pasted report

**File:** `tools/silicon-check.sh:150-151, 166`
**Issue:** `DOCTOR_OUT="$("${ASSET_PATH}" doctor 2>&1)"` captures combined stdout+stderr including any color escapes `wez doctor` emits, and the last 3 lines are pasted verbatim into a `text` fenced block in the runbook. Color escape sequences in a pasted "evidence" block are noisy and can corrupt the markdown rendering of the landing spot. Minor, cosmetic.
**Fix:** Strip control sequences before placing in the report, e.g. pipe through `sed $'s/\033\\[[0-9;]*m//g'`, or run `doctor` with a no-color flag if one exists.

### IN-06: `unescape_key` in showkeys.lua does not handle `\n`/`\t`/`\xNN` — narrow but undocumented for untrusted input

**File:** `cli/lib/showkeys.lua:35-38`
**Issue:** `unescape_key` only unescapes `\" \' \\`. The header comment says show-keys "only emits these for the punctuation key names," which is the safe assumption, but the input is explicitly labeled UNTRUSTED process output (line 25). A key literal containing `\n` would be passed through with the backslash intact and become a slightly-wrong key token (not a security issue — it is never `load()`'d). Acceptable per the documented scope; flagged for completeness since the file self-identifies as parsing untrusted input.
**Fix:** None required; optionally note the deliberate minimal-unescape scope in a TODO.

### IN-07: Test asserts source TEXT, not behavior, for the dkjson dual-resolve — a refactor that keeps the string but breaks the runtime path would pass

**File:** `tests/cli/keys_test.lua:206-224`
**Issue:** The regression guard greps the source for the literal `cli.vendor.dkjson` and the
absence of `require("dkjson")`. This pins the *fix text* but not the *behavior* in the bundle
context (the round-trip test on lines 198-205 succeeds only because `cli/vendor/?.lua` is on
`package.path` under the runner — it never exercises the real luastatic-bundle resolution where
the bare `require("dkjson")` actually fails). So the test cannot regress if someone reorders the
two `pcall(require, ...)` calls such that the bare name is tried first, as long as both strings
remain present. The `has_bare` check specifically looks for `require("dkjson")` with parens-and-
quotes, but `keys.lua:267` uses `pcall(require, "dkjson")` (comma form) — so the intended
"no bare require" guard does NOT actually match the fallback line in the file under test.
**Fix:** Assert order/behavior (e.g. that `cli.vendor.dkjson` is attempted before any `dkjson`
fallback) rather than string presence, and make the `has_bare` pattern match the actual
`pcall(require, "dkjson")` form used in the source.
