## Summary

The two open research questions (D-03 SUPER label + Linux-grab truthfulness; and the `Mapped` key-resolution semantics that govern D-01/D-08/D-10) were both resolved by running `wezterm show-keys --lua` against probe configs on the live machine. The decisive finding: **WezTerm itself folds `mapped:<lowercase-letter>` + explicit `SHIFT` into the produced uppercase character in its effective table, and it dedupes the lowercase-twin and uppercase-twin declarations into a single effective row.** This makes the dual lower+upper twins in `keybindings.lua` provably redundant (D-10), makes the D-01 canonicalization a deterministic letter-only transform, and makes the D-08 case-variant collapse automatic once D-01 lowercases. The D-10 "fallback uppercase-char" form produces an *identical* effective row to the lowercase+SHIFT form, so either declaration is safe — D-10's primary form is preferred for matching the display convention.

The implementation surface is almost entirely **pure Lua** in `cli/commands/keys.lua` (canonicalize, mod-ordering, dedupe, platform-map, action-grouping) plus a tiny new ANSI SGR helper, with only TTY/`NO_COLOR`/host-OS detection living in the IO shell. This means the entire renderer is fixture-testable headless (the TDD RED/GREEN surface — the autonomous gate), and the only thing that *needs* a live WezTerm session is the D-09 firing probe (does the reconciled single-entry binding still fire) and the e2e read-back of `wez keys` output. The project already has a proven live-GUI/headless recipe and a `WEZTERM_INTEGRATION=1` guarded integration-test lane to host the e2e.

**Primary recommendation:** Reconcile `keybindings.lua` to single lowercase+SHIFT entries (D-10 primary form — empirically verified to produce the same effective row as the twins and the uppercase fallback), build the renderer as pure functions in `keys.lua` driven by fixtures captured from real `show-keys --lua` text, add a new `cli/lib/ansi.lua` SGR helper, render SUPER platform-aware with a Linux-grab footnote (NOT runtime grab-detection — it is not reliably detectable), and gate the firing reconcile behind a `WEZTERM_INTEGRATION=1` live e2e + a `.tmp/h<NN>-*/` manual repro.

### Pattern 1: Pure transform on parsed records (D-01 canonicalize)
**What:** A deterministic record→record transform applied after parse, before render.
**When to use:** Every chord render; this is the heart of D-01.
**The empirically verified rule (single letters only):**
```lua
-- Source: live `wezterm show-keys --lua` probe (2026-06-18, wezterm 20260614)
-- Observed: declared { key='mapped:x', mods='ALT|SHIFT' }  →  effective { key='X', mods='ALT' }
-- Inverse transform to canonical form:
--   IF key is a single letter that is UPPERCASE, AND mods does NOT contain SHIFT:
--     → re-add SHIFT to mods, lowercase the key token.
-- Letters ONLY. Digits and named keys do NOT fold (see Pitfall 2).
local function canonicalize_key(key, mods)
  if key:match("^%a$") and key:upper() == key and not mods:find("SHIFT") then
    return key:lower(), add_shift(mods)
  end
  return key, mods
end
```

### Pattern 2: Fixed canonical mod order (D-02) — replace the alphabetical sort
**What:** `norm_mods()` currently does `table.sort(parts)` (alphabetical). D-02 replaces it with a fixed rank.
```lua
-- Source: CONTEXT D-02. Replaces keys.lua:51 table.sort(parts).
local MOD_RANK = { SUPER = 1, CTRL = 2, ALT = 3, SHIFT = 4 }
table.sort(parts, function(a, b) return (MOD_RANK[a] or 99) < (MOD_RANK[b] or 99) end)
-- Human form joins with "+"; --json keeps native "|" (D-02).
```
**Caveat:** `norm_mods` is *also* the cross-source identity key (`id_of`). Changing its *order* is safe for matching (it is still canonical), but if you change the *separator* for the human form do it in a NEW function — keep `id_of` on the pipe form so classify still matches across sources.

### Pattern 3: Action-centric grouping (D-07)
**What:** One row per action, listing all distinct real chords, reliable-chord-first.
```
ClearScreenAndScrollback   SUPER+k, CTRL+SHIFT+k      [setup]
CloseCurrentTab            SUPER+w, CTRL+SHIFT+w      [setup]
```
Reliable-chord-first = put the layout-stable / non-Super-grabbed chord first on Linux (ties to D-03). On a host where `--platform macos`, Super (Cmd) is reliable and can lead.

### Anti-Patterns to Avoid
- **Folding digits/named keys like letters:** `mapped:1`+`ALT|SHIFT` does NOT cleanly fold — it registers both `!` and `1`+SHIFT (Pitfall 2). The canonicalize transform MUST be letter-only.
- **Overloading `cli/lib/color.lua`:** It is an OSC *background* emitter. D-06 text color is a separate ANSI SGR concern — new module/path (CONTEXT explicitly says do not overload it).
- **Coloring `--json`:** Never emit SGR into JSON (D-06). Gate color on `not args.json AND tty AND not NO_COLOR`.
- **Runtime Super-grab detection:** Not reliable; do not attempt (Pitfall 1).

## Common Pitfalls

### Pitfall 1: Implying a grabbed Super chord works (D-03 — the central truthfulness concern)
**What goes wrong:** Rendering a friendly `Super+k` row implies the chord fires, but on Linux the WM/compositor grabs Super-modified keys before WezTerm ever sees them (Pop!_OS grabs `Super+K`/`Super+W`). The user reported "close tab is not an option at all" for exactly this reason.
**Why it happens:** The Super grab is a *compositor-level* binding, invisible to WezTerm. `wezterm show-keys` STILL lists the SUPER binding (it's in WezTerm's config) even though the key never reaches it — so the effective table is *not* truthful about reachability. [VERIFIED: live probe shows `key='w' mods='SUPER'` present in effective table despite being grabbed]
**How to avoid:** Do NOT attempt runtime grab-detection — there is no portable, reliable CLI API to ask "does the compositor grab Super+X" across Wayland/X11/GNOME/Pop!_OS (would require per-compositor D-Bus/protocol introspection that doesn't exist uniformly). Instead: (a) order the **layout-stable reliable chord first** per D-07 (the `CTRL+SHIFT+*` twin that DOES reach WezTerm on Linux), and (b) add a static footnote/annotation on Super-bearing rows on Linux ("Super may be intercepted by your desktop"). This is the honest fallback CONTEXT D-03 explicitly permits.
**Warning signs:** A `Super+…` row presented as the *only* or *first* chord for an action on Linux.

### Pitfall 2: Folding digits/named keys like letters
**What goes wrong:** Applying the letter-fold to `1`/`PageUp`/`+` produces wrong output.
**Why it happens:** Only single *letters* fold to an uppercase produced char. Empirically [VERIFIED: live probe]:
- `mapped:1`+`ALT|SHIFT` → registers BOTH `key='!' mods='ALT'`-ish AND `key='1' mods='SHIFT|ALT'` (digit keeps SHIFT explicit; the symbol is a separate row).
- `mapped:PageUp`+`CTRL|SHIFT` → stays `key='PageUp' mods='SHIFT|CTRL'` (named keys never fold).
**How to avoid:** Guard the canonicalize transform with `key:match("^%a$")` (single ASCII letter) before applying the lowercase+add-SHIFT rewrite. Everything else passes through unchanged.
**Warning signs:** A digit or named key appearing lowercased-with-added-SHIFT in a way that doesn't match its effective row.

### Pitfall 3: `resolve_action` lockstep (config-load crash)
**What goes wrong:** Changing a `keybindings.lua` action `type` without a matching arm in `init.lua resolve_action` crashes config load (WezTerm pops a config-error window).
**Why it happens:** `resolve_action` ends in `error("unknown action spec type ...")` — it is a closed switch. [VERIFIED: init.lua:98]
**How to avoid:** D-10 reconcile only changes `key`/`mods` (not `action.type`), so this should be untouched — but verify no action type drifts. Keep both in lockstep.
**Warning signs:** A config-error window on WezTerm reload after the reconcile; the firing probe will catch it immediately.

### Pitfall 4: Stale installed config masking the test
**What goes wrong:** The live firing probe tests the OLD twins because the edited repo `keybindings.lua` was never synced to `~/.config/wezterm/wezterm-setup/`.
**Why it happens:** Config is COPIED, not symlinked. [VERIFIED: project memory]
**How to avoid:** `cp` (or re-run the installer) the edited `keybindings.lua` to the install dir before the live e2e/probe. The e2e harness should do this explicitly and log it.
**Warning signs:** `wez keys` output unchanged after editing the repo file.
