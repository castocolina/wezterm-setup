# Plan 06.5-05 — `wez keys` grouping + conflict-noise fix (gap from 06.5-04 checkpoint)

## Objective

Close the renderer gap surfaced when the operator reviewed live `wez keys` output at the
06.5-04 checkpoint (2026-06-18). Two operator-authorized behavior changes plus the
root-cause matching bug that drove both symptoms.

## Background (what was wrong)

1. **Matching bug (root cause).** `id_of` (keys.lua) builds the cross-source identity from
   RAW key+mods. `canonicalize_key` (case-fold letter base + implicit→explicit SHIFT) is only
   applied in `group_by_action` at RENDER time, never in matching. So our `mapped("x")` +
   `ALT|SHIFT` (id `x\0ALT|SHIFT`) never matches the effective `X` + `ALT` (id `X\0ALT`).
   Consequence: every letter chord we own is (a) classified `[user]` instead of ours, and
   (b) reported as a false `overridden` conflict because "ours is absent from effective".

2. **Ordering.** D-14 only made `ours ∩ baseline ∩ effective` the "managed" section, so our
   genuine additions (ALT+SHIFT+H/V/X/Z, RotatePanes, pane-nav arrows) — not WezTerm
   defaults — could never qualify as managed and sank into the defaults block.

3. **Conflict noise.** The who-wins section flagged our intentional overrides AND WM-grabbed
   Super chords as `[CONFLICT]`, compounded by the matching bug's false positives and a
   stale (un-reloaded) live session.

## Tasks

### Task 1 (TDD) — canonical matching + three-group classify + true-conflict filter

RED then GREEN in `cli/commands/keys.lua` + `cli/commands/keys_test.lua`.

- **id_of fix:** canonicalize key+mods (reuse `canonicalize_key`, then `norm_mods`) before
  building the token, so ours/baseline/effective compare on the SAME canonical chord. Keep
  `norm_key` `mapped:` stripping. Digits/symbols/named keys still pass through unchanged.
- **classify → three buckets** keyed on `(in_ours, in_base)`:
  - `in_ours and in_base` → group `managed`, label `setup`
  - `in_ours and not in_base` → group `additions`, label `added`
  - `not in_ours and in_base` → group `defaults`, label `default`
  - `not in_ours and not in_base` → group `defaults`, label `user`
- **conflicts (true only):** a conflict is recorded ONLY when an OUR binding is absent from
  effective AFTER canonical matching AND its mods do NOT contain SUPER. Drop the
  action-mismatch branch's noise where ours is actually present (present = ours wins).
- **render:** three sections in order — `== Managed (overrides) ==`, `== Our additions ==`,
  `== WezTerm defaults ==` — each via the existing `render_section`/`group_by_action` path
  (category sub-ordering preserved). Empty section → no header. Zero conflicts → no section.
  Keep the Linux Super footnote after the managed/additions block on linux/all.
- **--json:** `build_json` consumes the same filtered conflicts; stays jq-valid, no SGR.

**Verify:** `keys_test.lua` green; live `./dist/wez keys` shows our ALT+SHIFT keys under
"Our additions", zero Super rows in conflicts, no false `overridden` rows for present
bindings; `./dist/wez keys --json | jq .` exits 0 with no `\27[` bytes.
