# Phase 6.5: Keybinding Clarity & `wez keys` Output Curation (INSERTED) - Context

**Gathered:** 2026-06-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Make `wez keys` output **trustworthy and low-noise**, and make the `keybindings.lua`
declarations **internally consistent** with what is displayed and what is actually pressed.

Four coupled changes:

1. **One display convention.** Every chord renders unambiguously with all modifiers
   explicit — Shift is NEVER implied by an uppercase letter. The display layer
   (`cli/commands/keys.lua`) canonicalizes the live `show-keys` effective table into the
   single chosen form.
2. **Curated-first presentation.** wezterm-setup managed bindings are listed FIRST; WezTerm
   defaults/inherited bindings come after (nothing hidden).
3. **De-noise.** Rows that represent the SAME effective chord collapse to one; an action
   reachable by multiple distinct chords renders as a single action-centric row.
4. **Reconcile `keybindings.lua`.** Normalize the inconsistent "declare both lower+upper"
   pattern to a single canonical declaration form, so the declared form, the displayed chord,
   and the keys actually pressed all agree — gated behind a real-WezTerm verification probe.

Plus regression tests for the new ordering + dedupe + unambiguous rendering.

**In scope:** the `wez keys` renderer/classifier (`cli/commands/keys.lua`), the show-keys
parser if needed (`cli/lib/showkeys.lua`), the curated key table
(`config/wezterm-setup/keybindings.lua`), a new `--platform` selector flag, ANSI-red conflict
highlighting, and the live hypothesis probe for the declaration reconcile.

**Out of scope (own phases):** the doc audit that documents the final keybinding reality
(Phase 6.4 — runs last); macOS on-hardware re-verification of the reconciled bindings
(Phase 7); any NEW keybindings or changes to which actions are bound (this phase changes how
bindings are *declared/displayed*, not *what* is bound).

</domain>

<decisions>
## Implementation Decisions

### Chord render format (display convention)
- **D-01:** **Canonical lowercase base-key token.** A shifted chord renders as the physical
  base key in lowercase with ALL modifiers (including Shift) explicit in the mods:
  `ALT+SHIFT+x`, `CTRL+SHIFT+w`, `ALT+SHIFT+z`. **Letter case never carries meaning** — the
  old "uppercase letter silently implies Shift" signal is eliminated. The renderer must
  canonicalize WezTerm's native produced-character form (e.g. `show-keys` reports close-pane
  as `ALT+X` with Shift folded into the uppercase char) back into `ALT+SHIFT+x` — a
  deterministic transform for letter keys (single uppercase letter + no SHIFT mod ⇒ re-add
  explicit SHIFT and lowercase the token).
- **D-02:** **`+` separator, fixed canonical modifier order.** Human output uses `+` between
  tokens (`CTRL+SHIFT+x`), NOT WezTerm's native `|` pipe form. Modifiers are sorted to a fixed
  canonical order so the same chord always reads identically regardless of source ordering.
  Recommended order: **SUPER > CTRL > ALT > SHIFT** (most-significant first, matches how chords
  are spoken). (`--json` may keep raw/native mods as data; the canonical `+` form is the
  human-table contract.)
- **D-03 (RESEARCH NEEDED):** **SUPER label rendering is deferred to research.** WezTerm maps
  `SUPER` → Cmd on macOS, Super/Win on Linux (`keybindings.lua:47` already documents the intent
  for `wez keys` to report the platform-appropriate label). UNRESOLVED: render a friendly
  platform-aware label (`Cmd+k` / `Super+k`) vs the literal `SUPER+k` token. **First-class
  research concern — the Linux Super-grab truthfulness problem:** on Linux the WM/DE frequently
  grabs the Super key (Pop!_OS grabs `Super+K`, etc.) so it never reaches WezTerm — rendering a
  friendly `Super+k` row risks *implying it works* when the compositor eats it. The researcher
  MUST address whether the renderer can detect/annotate/footnote likely-grabbed Super chords (or
  at minimum order the layout-stable reliable chord first per D-07). This is why the dual
  `Ctrl+Shift+K` binding exists.

### Output verbosity & flags
- **D-04:** **`--platform` selector flag is IN SCOPE.** `wez keys --platform linux|macos|all`
  overrides the rendered platform; default is the host OS. `--platform all` shows every
  platform's labels. Serves cross-platform review and feeds the Phase 6.4 doc audit (a Linux
  user can preview the macOS `Cmd+…` chords and vice-versa). NOTE: `--platform` is the ONLY new
  selector flag — keep it named distinctly from any "show more rows" notion (there is none; see
  D-05).
- **D-05:** **Default view = curated-first, everything shown.** Bare `wez keys` lists the
  wezterm-setup managed section FIRST, then a WezTerm-defaults section AFTER. **Nothing is
  hidden** and there is **NO curated-only filter flag** — ordering carries the signal. (User
  explicitly rejected hiding defaults and rejected a `--managed`/`--mine` filter.)
- **D-06:** **Conflicts rendered in RED — inline + summary.** A conflicting binding's row is
  highlighted red where it appears in its section AND a red `== Conflicts (who-wins) ==` summary
  is kept at the bottom. Color is ANSI SGR text color (NEW — today's renderer is plain text;
  `cli/lib/color.lua` only emits OSC *background* colors, so a small ANSI helper is needed).
  **Color safety:** emit ANSI only on a TTY, respect `NO_COLOR`, and never colorize `--json`
  output.

### Dedupe boundary
- **D-07:** **Action-centric layout — one row per action, distinct chords grouped.** An action
  reachable by multiple genuinely-different chords renders as a SINGLE row listing all real
  chords (e.g. `CloseCurrentTab  SUPER+w, CTRL+SHIFT+w`; `ClearScreenAndScrollback  SUPER+k,
  CTRL+SHIFT+k`). Chord ordering within the row should put the **layout-stable / reliable chord
  first** (ties to D-03's Linux-Super-grab concern). This is the de-noise mechanism for the
  intentional dual-chord-per-action pattern (which `keybindings.lua` calls "truthful, not a
  conflict") — collapse the *visual* repetition without dropping any real chord.
- **D-08:** **Identical-after-canonicalization rows collapse to one.** The old `CTRL+SHIFT+z` +
  `CTRL+SHIFT+Z` near-duplicate twin rows collapse automatically once D-01 lowercases the token —
  no separate dedupe heuristic needed for the case-variant twins; they become the same rendered
  row.

### keybindings.lua reconcile
- **D-09:** **Normalize the declarations (not display-only), gated behind a real-WezTerm
  probe.** The fix lives in `config/wezterm-setup/keybindings.lua`, not just the display layer.
  Because this changes firing behavior, it MUST be validated against a live WezTerm session
  (hypothesis probe under `.tmp/h<NN>-*/` per project rules) confirming **every chord still
  fires** before integration. No "should work."
- **D-10:** **Canonical declaration form = single entry, lowercase base + explicit SHIFT in
  mods.** Drop the dual lower+upper twins; one entry per binding with Shift explicit:
  `mapped('k')` `CTRL|SHIFT`, `mapped('w')` `CTRL|SHIFT`, `mapped('x')` `ALT|SHIFT`,
  `mapped('z')` `ALT|SHIFT`. This **mirrors the already-working close-pane binding**
  (`mapped('x')` `ALT|SHIFT` is a single entry, live-verified during the Pop!_OS debugging that
  surfaced this phase) and makes the declared form match the D-01 display convention.
  **Fallback (probe-driven only):** if the probe shows Mapped mode requires the produced
  uppercase char to fire reliably, use a single `mapped('W')` `CTRL|SHIFT`-style entry instead —
  still ONE entry per binding, no twin.

## Existing Code Insights

### Reusable Assets
- `cli/commands/keys.lua` already separates PURE logic (`classify`, `build_json`, `norm_key`,
  `norm_mods`, `category_of`) from live wiring (`run`, `capture`, `load_our_bindings`). The new
  render convention, dedupe, and platform/color logic should stay in the pure layer so they're
  fixture-testable with no live WezTerm session (the autonomous gate).
- `norm_mods()` is the natural home for the D-02 fixed-order canonicalization (replace its
  `table.sort` alphabetical sort with the canonical order).
- The 3-way classify (setup/default/user) + conflict list already exist — D-05 (curated-first
  sectioning) and D-06 (red conflicts) build on the existing `label` field and `conflicts`
  array, not new classification.

### Established Patterns
- **Pure-core / IO-shell split** — consistent across the CLI (`cli/lib/*` pure, `cli/commands/*`
  wires IO). Keep canonicalization/dedupe/platform-mapping pure; keep TTY/`NO_COLOR`/popen in the
  shell.
- **Verify before declaring done** — the D-09 reconcile is behavior-affecting and MUST be
  validated against a real running WezTerm session (recorded repro), not grep-verified. The
  close-pane/close-tab debugging on Pop!_OS (2026-06-16/17) that surfaced this phase is the
  cautionary precedent.
- **Mapped-mode truthfulness** — `keybindings.lua` deliberately lists multiple chords for one
  action as "truthful, not a conflict." D-07 preserves that truth (no chord dropped) while
  removing the visual repetition.

### Integration Points
- `wez keys` ↔ live `wezterm show-keys --lua` (effective) + `wezterm -n show-keys --lua`
  (baseline) + installed `~/.config/wezterm/wezterm-setup/keybindings.lua` (ours).
- `keybindings.lua` declarations ↔ `init.lua resolve_action` arms (lockstep; crash-on-unknown).
- `--platform` ↔ the SUPER→Cmd/Super mapping (`M.super_mod`) and the D-03 label decision.
