<objective>
Scaffold the `wez` companion CLI: a Lua 5.4 entry point with a single source-of-truth argparse
command spec that registers the COMPLETE Phase 1 subcommand surface upfront (the interface-first
contract), the two vendored pure-Lua dependencies (argparse, dkjson), a first trivial `version`
subcommand to exercise dispatch, and the `make build` toolchain (luastatic single-binary with a
release-download fallback). Also create the shared bash platform-detection helper that the emulator
bootstrap and installer reuse.

Purpose: Every DIAG requirement (`wez doctor`, `wez keys`, completions) and the installer's
install-state logic (D-01: "ALL logic with decisions lives in the Lua `wez` binary") build on this
scaffold. The argparse spec is the contract downstream plans consume — registering ALL Phase 1
subcommands here means Plans 04/05/06/07 implement only their own `cli/commands/<name>.lua` module
without editing `cli/spec.lua`, which keeps those plans parallel (no shared-file wave conflict) and
prevents the scavenger-hunt anti-pattern where later executors reverse-engineer the command tree.

Output: a buildable `wez` binary skeleton, the central `cli/spec.lua` contract (full Phase 1 command
tree), vendored deps, the `tools/build.sh` luastatic pipeline, and `tools/lib/platform.sh` shared by
Plans 02 and 04. The DIAG requirement IDs are listed here because this plan provides their structural
foundation (the spec + JSON + dispatch); their observable behaviors are DELIVERED in Plans 05/06/07.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| network -> build host | `tools/build.sh` release-download fallback fetches a `wez` binary over the network when the Lua toolchain is absent — untrusted bytes become an executable placed on the user's PATH |
| process args -> CLI | command-line `arg[]` crosses into the Lua dispatcher; a crafted subcommand name must not allow arbitrary module loading |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | release-binary download fallback in `tools/build.sh` | mitigate | Pin the release tag/version being fetched; verify the downloaded binary against a published SHA-256 checksum before `chmod +x`; abort non-zero on checksum mismatch — never run an unverified download |
| T-01-02 | Elevation of Privilege | dispatch from `arg[]` to `cli/commands/<name>.lua` | mitigate | Resolve the subcommand only against the closed set registered in `cli/spec.lua` (allow-list); never build a `require` path directly from raw user input, preventing path-traversal module loads |
| T-01-03 | Information Disclosure | luastatic-built binary bundling vendored sources | accept | Vendored `argparse`/`dkjson` are public open-source single files; no secrets are baked into the binary |
| T-01-SC | Tampering | vendored `argparse.lua` / `dkjson.lua` provenance | mitigate | Both are pure-Lua single files committed with an upstream-provenance comment (no luarocks/npm install step → no Package Legitimacy Gate triggered); reviewer can diff against canonical upstream |
</threat_model>
