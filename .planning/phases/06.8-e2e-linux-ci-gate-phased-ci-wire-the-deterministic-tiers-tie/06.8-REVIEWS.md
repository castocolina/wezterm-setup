## 06.8-01

### Summary

The plan is well-grounded in existing scripts and correctly reuses the repository's build and E2E entry points. However, it cannot achieve a green CI gate as written: the selected pinned WezTerm value is not a downloadable release, and the global skip check rejects an intentional Linux skip. Several verification commands can also report success after underlying failures.

### Strengths

- The proposed `WEZ_BIN=./dist/wez` correction is accurate. `tools/build.sh:67-69` defines `dist/wez` as its output, while the current example incorrectly names `dist/wez-linux-x86_64` at `tests/e2e/README.md:19-22`.
- Reusing `make test`, `make build`, and `make e2e` preserves the repository's thin-glue boundary established in `Makefile:27-43` and `.github/workflows/release.yml:9-12`.
- The mux discovery design is grounded correctly. `tests/e2e/lib/mux.lua:72-89` checks `PATH` and then the resolved WezTerm binary's sibling directory.
- Requiring live markers is directionally sound. `tests/e2e/lib/skip.lua:44-58` clearly distinguishes `SKIPPED (reason=...)` from `LIVE-ASSERTED (...)`.
- Read-only permissions and a job timeout appropriately limit the impact of running PR-controlled code (`06.8-01-PLAN.md:131-140`).

### Concerns

- **HIGH: The pinned WezTerm provisioning target is not fetchable.** The plan requires `WEZTERM_TARGET=pinned` at `06.8-01-PLAN.md:150-156`. The pin is `20260604-145453` at `tools/lib/wezterm-release.sh:24-30`, but the same file says release URLs require the full tag including its short SHA at `tools/lib/wezterm-release.sh:129-141`. The audited version is actually `20260604-145453-eeb80972` at `.planning/decisions/wezterm-cli-surface.md:3`. A cold runner passes the incomplete value through `select_release` and directly into the download URL (`tools/bootstrap-wezterm.sh:250-260`, `tools/bootstrap-wezterm.sh:403-419`). Live GitHub API checks also returned 404 for both candidate 2026 tags. Existing evidence only proves reuse of a locally installed build, not clean installation. The first uncached CI run will fail before tests start.
- **HIGH: The global skip prohibition rejects an expected Linux result.** The plan rejects every `SKIPPED (reason=` line at `06.8-01-PLAN.md:170-178`, and repeats that assertion in Tasks 2 and 3. On Linux, `tests/e2e/tier1/keys_siblings_e2e_test.lua:78-97` intentionally emits exactly that marker for its deferred macOS-only layer and exits successfully. A direct execution during review reproduced the marker. Consequently, the proposed local proof and remote CI run cannot satisfy `no_self_skip`.
- **HIGH: The required fail-fast ordering is reversed.** Context D-04 requires unit tests before spending WezTerm provisioning time (`06.8-CONTEXT.md:42-47`), but the plan provisions and verifies WezTerm in steps 5-6 and does not run unit tests until step 8 (`06.8-01-PLAN.md:142-167`). The plan nevertheless claims unit failure avoids mux provisioning. `make test` only requires Lua 5.4 (`tools/run-tests.sh:28-31`), so the toolchain and unit tests can run before WezTerm provisioning.
- **HIGH: Task 2 and Task 3 verification can false-green.** Task 2 separates commands with semicolons and follows each failure-prone command with `echo` (`06.8-01-PLAN.md:257-259`), so failed tests, builds, or E2E runs do not determine the final shell status. Task 3 prints `CONCLUSION` but never asserts that it equals `success`, and it does not fail when the polling loop exhausts (`06.8-01-PLAN.md:307-309`). A failed run containing `LIVE-ASSERTED` and no skip marker can therefore pass the automated verifier.
- **HIGH: The remote verification is not correlated to the pushed commit.** Task 3 always selects the latest run on `main` (`06.8-01-PLAN.md:279-286`, `06.8-01-PLAN.md:301-308`). It never captures the pushed SHA or compares it with the run's `headSha`. A concurrent push or stale completed run could be accepted as evidence for this plan.
- **MEDIUM: The plan does not prove the skip gate's negative path.** The PRD requires that self-skip behavior be verified and that only real failures block (`docs/prds/e2e-testing-battery-v1.0-prd.md:242-246`). Tasks 2 and 3 exercise only a normal successful battery. Structural grep confirms that strings exist, but does not prove that an applicable Tier 2/3 skip fails while an expected platform skip remains allowed.
- **MEDIUM: Action tag security is overstated and workflow validation is too weak.** The threat model claims version tags prevent silent action replacement (`06.8-01-PLAN.md:327-331`), but tags are mutable; the existing workflow acknowledges that full commit-SHA pinning remains necessary (`.github/workflows/release.yml:55-56`). Task 1 also uses only `yq` and text checks (`06.8-01-PLAN.md:207-209`) despite `actionlint` being the established semantic workflow validator (`.github/workflows/release.yml:19-21`).

### Suggestions

- Establish a genuinely downloadable, immutable WezTerm artifact before implementing CI. Add a clean-prefix bootstrap probe and update the pin/bootstrap logic as a prerequisite.
- Require the specific expected Tier 2 and Tier 3 `LIVE-ASSERTED` labels, and reject `SKIPPED` only for those labels. Preserve the intentional macOS-only skip.
- Reorder the job to toolchain setup, `make test`, WezTerm cache/provisioning, mux verification, `make build`, then `make e2e`.
- Make every verifier fail closed with `set -euo pipefail`, explicit exit-code assertions, a completed-status assertion, and `test "$CONCLUSION" = success`.
- Capture `PUSHED_SHA="$(git rev-parse HEAD)"` and select the Actions run whose `headSha` exactly matches it.
- Add synthetic pass/fail fixtures for the marker-classification logic and run `actionlint` before pushing.
- Pin `actions/checkout` and `actions/cache` by full commit SHA, or accurately document mutable tags as accepted residual risk.

### Risk Assessment

**HIGH.** Two independent defects make the planned CI run fail deterministically: the invalid cold-install pin and the expected Linux `SKIPPED` marker. The verification commands can then obscure other failures or associate evidence with the wrong commit. The plan needs revision before execution.
