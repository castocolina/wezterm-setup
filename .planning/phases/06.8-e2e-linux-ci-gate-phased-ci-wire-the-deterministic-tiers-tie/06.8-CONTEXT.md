# Phase 06.8: E2E Linux CI Gate (phased CI) - Context

**Gathered:** 2026-09-08
**Status:** Ready for planning

<domain>
## Phase Boundary

Wire the deterministic E2E tiers (Tier 1 subcommands, Tier 2 scenes, Tier 3-registration
keybindings) into a GitHub Actions workflow that runs on Linux with a headless
`wezterm-mux-server`, so the battery gates every push and PR going forward. This phase
makes the tiers CI-*wired*, not CI-*enforced* — see D-04 (no branch protection yet). Tier 3
firing and Tier 4 visuals stay local/best-effort (06.9), untouched here.

</domain>

<decisions>
## Implementation Decisions

### WezTerm provisioning in the CI runner
- **D-01:** The runner provisions WezTerm via the existing `tools/bootstrap-wezterm.sh`,
  invoked with `WEZTERM_TARGET=pinned` (non-interactive) rather than the tool's own default
  (rolling `nightly`) — Claude's discretion call, made because a moving nightly target would
  make the E2E gate's pass/fail nondeterministic across runs on no code change of ours.
  Cache the downloaded WezTerm archive/install directory keyed on the pinned
  release identifier so unchanged runs don't re-download. — **Reversibility:** reversible —
  switching the cache key or the `WEZTERM_TARGET` value later is a one-line workflow edit,
  no downstream contract depends on it.
- **D-02:** Per `tests/e2e/README.md`'s existing contract, once a real `wezterm-mux-server`
  is resolvable (which D-01 guarantees in CI), Tier 2/3 print `LIVE-ASSERTED` and a self-skip
  becomes a hard failure — this phase does not change that contract, it only ensures the
  precondition (a resolvable mux) holds in CI so the gate is meaningful rather than a
  permanent self-skip.

### CI trigger scope
- **D-03:** The workflow triggers on both `push` (to the default branch) and `pull_request`
  — matches the standard "validate before merge, also cover direct pushes" gate pattern.
  This is a NEW workflow file (e.g. `.github/workflows/ci.yml`), separate from the existing
  tag-triggered `.github/workflows/release.yml` (build+publish only, never touched by this
  phase). — **Reversibility:** reversible — trigger list is a one-line YAML edit.

### Scope: unit tests included
- **D-04:** `make test` (the unit suite, `tools/run-tests.sh`) runs in the SAME workflow as
  `make e2e`, as an earlier step (fail fast on unit failures before spending the mux-provisioning
  time on e2e). This slightly exceeds the PRD's literal Phase 3 wording ("wire T1+T2+T3-reg"),
  but leaving unit tests fully uncovered by CI while gating on the (slower, heavier) e2e battery
  would be an odd gap — user confirmed this extension explicitly rather than Claude assuming it.

### Branch protection
- **D-05:** The workflow runs and reports (pass/fail visible on PRs and commits) but is NOT
  wired into a GitHub branch-protection "required status check" in this phase — solo-dev repo,
  no PRs from other contributors yet, so a required check adds process friction without a
  present need. Enabling it later is a GitHub repo-settings change, not a workflow-file change
  — no code dependency on this decision. — **Reversibility:** reversible — a repo-settings
  toggle at any later point, no workflow/code change needed.

### Claude's Discretion
- Exact WezTerm provisioning mechanics (D-01: bootstrap-wezterm.sh flags, cache key shape,
  cache action version) — user deferred this whole area to Claude ("You decide").
- Workflow file name/location, job name, step ordering within the single job (beyond
  "unit tests before e2e" per D-04).
- Whether `dist/wez` (dev launcher) or a freshly `make build`-produced luastatic binary is
  the `WEZ_BIN` target for the e2e run in CI — `tests/e2e/README.md` already documents CI
  should override `WEZ_BIN` to the freshly built binary (not the dev launcher), so this
  should follow that existing documented convention, not be re-decided.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `tools/run-e2e.sh` — the battery orchestrator; CI's e2e step is just
  `WEZ_BIN=<built-binary-path> make e2e`, no new test-runner logic needed.
- `tools/run-tests.sh` — the unit-suite runner (`make test`); same, just invoke it.
- `tools/bootstrap-wezterm.sh` — full WezTerm provisioning already implemented
  (download/verify/extract/symlink), sudo-free, user-path only — exactly what a CI runner
  needs and already exercises today via a human running it, just never via a CI job.

### Established Patterns
- D-01 boundary (see `release.yml`'s own header comment): "this workflow is PURE glue... no
  install/version/update decision in YAML — delegated to `tools/*.sh`". This phase's new
  workflow must follow the identical boundary — no bash logic inlined in the YAML beyond
  invoking the existing `tools/`/`make` entry points.
- `tests/e2e/lib/mux.lua`'s `resolve_mux_server` looks up `wezterm-mux-server` on `PATH`
  first, then as a sibling of the resolved `wezterm` binary — whatever provisioning step
  D-01 implements just needs `wezterm`/`wezterm-mux-server` reachable by ONE of those two
  paths; it does not need to engineer a new discovery mechanism.

### Integration Points
- New workflow file under `.github/workflows/` (name TBD at planning time — Claude's
  discretion), triggered per D-03, running on `ubuntu-latest` (matching `release.yml`'s
  Linux-only-for-v1 convention), invoking: provision WezTerm (D-01) → `make test` (D-04) →
  `make build` (to produce the binary `make e2e` should target, per README's documented CI
  convention) → `WEZ_BIN=<built binary> make e2e`.

</code_context>
