No blocking correctness/security defects were found in the diff itself — the
D-02 skip-classification logic in `tools/ci-classify-e2e-output.sh` was traced
against every fixture in `tests/ci_classify_test.lua` and behaves as specified,
and the `ci.yml` pipeline's explicit `set +e` / `PIPESTATUS` / classify-exit
handling is correct. The issues below are robustness, portability, and
internal-consistency gaps: a locale-fragile error-string match reintroduced in
the exact code path this phase's own CI regression fix targets, a fresh-install
exemption that cannot distinguish "never existed" from "coincidentally
skeleton-shaped, backup since deleted," an un-pcall'd `require` fallback that
can crash instead of degrading gracefully, a step-ordering violation of the
workflow's own stated D-04 invariant, a `set`-flags footgun in
`ci-resolve-wezterm-cache-key.sh` (empirically reproduced), and a permission
test that is not root-safe.

## Warnings

### WR-01: Locale-dependent ENOENT string match reintroduces the exact class of bug this phase's fix targets

**File:** `cli/commands/install_state.lua:106-113` (`read_target_or_seed`) and `cli/commands/install_state.lua:132-147` (`M.backup`)

**Issue:** Both the "seed a missing target from `DEFAULT_CONFIG_SKELETON`" path
and the "a missing backup source is a no-op success" path detect "file does not
exist" by substring-matching the literal English text `"No such file or
directory"` against the error message `io.open` returns:

```lua
if err and err:find("No such file or directory", 1, true) then
  return DEFAULT_CONFIG_SKELETON
end
```

That message is produced by libc's `strerror(ENOENT)`, which is
locale-dependent (`LC_MESSAGES`). I verified this concretely:

```
$ LANG=fr_FR.UTF-8 lua5.4 -e 'os.setlocale("","all"); local f,e=io.open("/no/such/file","r"); print(e)'
/no/such/file: Aucun fichier ou dossier de ce nom
```

Under the *default* Lua/luastatic runtime (no `os.setlocale` call), the process
stays in the `C` locale and the message is always the English string — so this
does not fire today. But it is one `os.setlocale` call away (in this file, a
future dependency, or a future feature) from silently regressing exactly the
06.8-01 CI bug this phase fixed: a real ENOENT would then be misclassified as a
"real I/O error" (`M.run` prints `"cannot read ...: <localized message>"` and
exits 1) instead of the intended "nothing to preserve, proceed as a fresh
install" no-op. Prefer checking the third return value of `io.open` (the errno,
`ENOENT` is portable across the two returns already available in Lua 5.4)
instead of parsing a human-readable, locale-variable string.

**Fix:**
```lua
local function read_target_or_seed(path)
  local data, err, errnum = read_all(path)
  if data then return data end
  if errnum == 2 then -- ENOENT, portable, locale-independent
    return DEFAULT_CONFIG_SKELETON
  end
  return nil, err
end
```
(and thread the same `errnum` check through `M.backup`; `read_all` already
exposes the errno as `io.open`'s third return value — currently discarded.)

### WR-02: `gate_backup_exists` fresh-install exemption cannot distinguish "never existed" from "real content, backup since deleted"

**File:** `cli/commands/doctor.lua:196-217`

**Issue:** The exemption compares the file with its managed block stripped
back out against the exact literal `install_state.DEFAULT_CONFIG_SKELETON`:

```lua
local original = install_state.restore_original_text(text)
if original == install_state.DEFAULT_CONFIG_SKELETON then
  return gate(true, "timestamped backup exists",
    "fresh install seeded from scratch — nothing pre-existed to back up")
end
```

If a real user's pre-existing `wezterm.lua` happens to be byte-identical to the
seeded skeleton (a very plausible shape for a brand-new WezTerm user:
`local config = wezterm.config_builder(); return config`), and its real backup
file is later lost (moved, cleaned up, filesystem issue), `wez doctor` will
report "OK — nothing to back up" even though a real backup obligation was
unmet. This is a byte-content coincidence, not a provenance check — the gate
has no way to know whether the skeleton-shaped content is because
`install_state` seeded it (no backup owed) or because the user wrote the same
five lines themselves (backup was owed and is now missing).

**Fix:** Track provenance explicitly instead of inferring it from content
equality — e.g. have `install_state.inject()` write a small sentinel/marker
(or a zero-byte "fresh-seed" flag file) beside the target only on the
ENOENT-seed path, and have the doctor gate check for that marker instead of
comparing file bytes.

### WR-03: `dkjson` fallback `require` is not `pcall`-guarded

**File:** `cli/commands/keys.lua:545-548`

**Issue:**
```lua
local ok, json = pcall(require, "cli.vendor.dkjson")
if not ok then
  json = require("dkjson")
end
```
Every other failure path in this file (`run()`'s live-capture failure,
`load_our_bindings` failure) reports a clean, actionable message via
`io.stderr:write(...)` and returns a controlled exit code. If BOTH the
dotted (`cli.vendor.dkjson`) and bare (`dkjson`) require paths fail (e.g. a
corrupted/partial install, or a future refactor that moves the vendor file),
this second `require` throws an uncaught Lua error, and `wez keys --json`
crashes with a raw Lua traceback instead of a controlled, user-facing error.

**Fix:**
```lua
local ok, json = pcall(require, "cli.vendor.dkjson")
if not ok then
  local ok2, json2 = pcall(require, "dkjson")
  if not ok2 then
    io.stderr:write("wez keys: could not load the vendored JSON encoder (dkjson)\n")
    return 1
  end
  json = json2
end
```

### WR-04: Step order in `ci.yml` violates the workflow's own stated D-04 invariant

**File:** `.github/workflows/ci.yml:27-29, 73-80`

**Issue:** The file header states as a hard invariant:

> D-04: unit tests (make test) run strictly BEFORE any WezTerm-related step —
> a unit regression fails fast without spending any mux-provisioning time.

But the actual step order is:
```
Checkout
Install Lua toolchain
Install wezterm-gui runtime deps (Linux)   <- WezTerm-related, per its own header comment
Unit tests (make test)
```
The "Install wezterm-gui runtime deps (Linux)" step (lines 73-75) — whose own
header comment explicitly frames it as existing "because the prebuilt
wezterm-gui binary... dynamically links against XCB/xkbcommon runtime libs" —
runs an `apt-get update && apt-get install` BEFORE `make test`. This
contradicts the documented ordering guarantee: a network-flaky `apt-get` (or a
future regression that makes this step slow) now delays the fail-fast unit
test signal the D-04 comment promises, and a future contributor reordering
steps based on the header comment's stated invariant would be reordering
around a false premise.

**Fix:** Either move "Install wezterm-gui runtime deps (Linux)" to after
"Unit tests (make test)" (it is only needed once `wezterm-gui` is fetched
later), or correct the D-04 comment to scope the invariant to "any step that
fetches/provisions the WezTerm *binary itself*" so the documented contract
matches the actual step order.

### WR-05: `set -uo pipefail` in `ci-resolve-wezterm-cache-key.sh` is silently overridden by sourcing `bootstrap-wezterm.sh`

**File:** `tools/ci-resolve-wezterm-cache-key.sh:27,34`

**Issue:** The script deliberately opts out of `-e` (`set -uo pipefail`, no
`e`), presumably so `latest_nightly_datestamp || true` idioms compose
predictably. But line 34 sources `bootstrap-wezterm.sh`, which itself declares
`set -euo pipefail` at its own top — and `set` options declared inside a
*sourced* script mutate the calling shell's option state (sourcing runs in the
same shell, unlike executing a subprocess). I reproduced this directly:

```
$ cat outer.sh
#!/usr/bin/env bash
set -uo pipefail
echo "before source: $-"
. ./inner.sh              # inner.sh contains: set -euo pipefail
echo "after source: $-"
false                     # unguarded
echo "unreachable"
$ bash outer.sh
before source: huB
after source: ehuB        # note the added 'e'
                           # (the final echo never runs — script aborted on the unguarded `false`)
```

Nothing downstream in `ci-resolve-wezterm-cache-key.sh` is currently unguarded,
so this has no live effect today, but the header comment's claim about the
script's shell-option posture is false from line 34 onward, and any future
edit that adds an unguarded command after the `source` line will behave
differently (abort under `-e`) than the file's own `set -uo pipefail` framing
implies.

**Fix:** Either explicitly re-assert the intended posture after sourcing
(`set +e` right after line 34, with a comment explaining why), or drop the
pretense and declare `set -euo pipefail` up front to match what actually ends
up in effect.

### WR-06: CR-03 permission-denied regression test is not root-safe

**File:** `tests/cli/install_state_test.lua:425-431`

**Issue:**
```lua
write_file(unreadable, "-- unreadable\n")
assert(os.execute("chmod 000 '" .. unreadable .. "'"))
local ok, err = IS.backup(unreadable)
check("backup of a permission-denied EXISTING source returns nil+err (not false success)",
  not ok and type(err) == "string", tostring(err))
```
`chmod 000` only blocks reads for a process running as a *non-root* user. When
`make test` runs as `root` (a common shape for local reproduction in a root
Docker/toolbox container, or any CI image that runs as root), the read
succeeds despite `000` permissions, `IS.backup` returns a real backup path
(`ok` truthy), and this assertion fails — not because of a regression in
`install_state.lua`, but because the test's precondition (file is genuinely
unreadable) silently does not hold under root. This makes the regression test
non-deterministic across execution environments rather than a reliable gate.

**Fix:** Skip (with a loud, logged skip) when running as root, e.g.:
```lua
local is_root = (os.execute("[ \"$(id -u)\" = 0 ]") == true)
if is_root then
  print("  skip - CR-03 permission-denied backup test  (running as root; chmod 000 is not enforced)")
else
  ... existing assertions ...
end
```

## Info

### IN-01: `"No such file or directory"` literal duplicated across two functions

**File:** `cli/commands/install_state.lua:109` and `:138`

**Issue:** The same magic string used to detect ENOENT is duplicated verbatim
in `read_target_or_seed` and `M.backup`. Beyond the locale fragility noted in
WR-01, the duplication itself is a small DRY violation — a future edit to one
copy (e.g. broadening the match) is easy to forget to apply to the other.

**Fix:** Factor into one shared predicate, e.g. `local function is_enoent(err)
return err and err:find("No such file or directory", 1, true) ~= nil end`
(or, better, the errno-based check from WR-01), and call it from both sites.
