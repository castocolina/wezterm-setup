<objective>
Add the `wez tab color <name|hex>` and `wez tab color reset` CLI surface (TAB-01), writing the
proven `"<color>:<title>"` tab-title prefix via `wezterm cli set-tab-title`. The accent then renders
through the Phase 3 formatter (Plan 03-01). This is the first half of the `wez tab` namespace —
`wez tab title` and the combined `--title` flag land in Plan 03-03.

The headline behavior is **read-modify-write (D-01)**: `wez tab color` preserves the tab's existing
title. It reads the current tab title from `wezterm cli list --format json` (the active pane's
`tab_id` identifies the active tab; that entry's `tab_title` is the current stored string — verified
present in the pinned WezTerm's JSON schema), parses the existing `"<color>:<title>"`, swaps only the
color, and writes the result back. Storage is **always** `"<color>:<title>"` with either side
empty-allowed (D-02): `wez tab color reset` writes `":title"` (accent cleared, title kept, D-04).

**Validate-before-emit (D-06):** an unknown color exits non-zero with NO read and NO write
(no half-applied state), mirroring `wez pane color`'s gate.

**Target (D-05):** current tab only. Keep the `tab_id` resolution separate from the write sink so a
future `--tab-id` (Phase 4 scenes) drops in without touching the pure builders — mirror pane.lua's
D-05 seam. No `--tab-id` surface ships in this phase.

**On `depends_on: ["03-01"]`:** this is END-TO-END OBSERVABILITY ordering, not a build/test
dependency — 03-02's own automated tests (validate_color/parse_stored/merge_title + the spec parse)
and its `wezterm cli list | grep tab_title` manual repro are formatter-independent and pass without
03-01. The ordering exists so the written accent is visually confirmable through 03-01's formatter
before this plan's behavior is signed off.

Output: new `cli/commands/tab.lua` + `cli/commands/tab_test.lua`; `cli/spec.lua` gains the `tab`
namespace with the `color` subcommand.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user CLI args -> `wezterm cli set-tab-title` | `args.value` (color) is validated to a closed name set or a strict hex shape before use; it is never the title text in this plan |
| `wezterm cli list` JSON -> tab.lua parser | The JSON is produced by the local WezTerm the user already trusts; still decoded defensively (dkjson, no eval) and tolerant of missing fields |
| merged title string -> shell argv | The merged `"<color>:<title>"` is passed to `set-tab-title` via a shell-quoted argument; in this plan the title half is the PRE-EXISTING stored title (read back), color half is validated — no free user text yet (that arrives in 03-03) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-0302-01 | Tampering | Command injection via the set-tab-title argument | mitigate | The argument is shell-quoted (`shquote`, reused from install_state.lua's proven single-quote escaper); color is validated to `[a-z]+`-names or `#%x%x%x`/`#%x%x%x%x%x%x`; `os.execute` receives a fully-quoted string, no interpolation of raw user bytes |
| T-0302-02 | Tampering | Malformed/huge `wezterm cli list` JSON crashing or mis-targeting | mitigate | `read_current_tab` decodes under a guarded decode (dkjson returns nil on bad input), treats nil/absent `is_active`/`tab_title` as the empty-title degrade path, never indexes without a presence check |
| T-0302-03 | Elevation of Privilege | n/a — no sudo, no setuid, no filesystem writes | accept | This phase writes only to the running WezTerm's tab title via the user's own `wezterm cli`; no privileged operation exists |
| — | (network / secrets / auth) | n/a | accept | No network, no credentials, no secrets read or written in this phase — stated explicitly so the model is honest, not padded |
</threat_model>
