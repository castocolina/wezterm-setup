## Tests

### 1. Cold Start Smoke Test
expected: Rebuild + refresh (`make build`, `wez update`) succeed; a fresh WezTerm session loads the new config/wezterm-setup bundle with NO Lua errors; `wez doctor` exits 0 on a clean install.
result: PASS (happy path) — fresh session loaded clean; no Lua errors reported.

### 2. Tab color decouple + active-pane-wins (D-02/D-03/D-04)
expected: `wez tab color cyan` shows a CYAN tab accent with NO literal `cyan:` text in the tab title. With two panes in one tab set to different colors (`wez pane color green` / `wez pane color purple`), the tab accent FOLLOWS the focused pane as you switch focus.
result: PASS as designed — but the user flagged the *design itself*: active-pane-wins clobbers an explicit tab color because both write the single `WEZTERM_TAB_COLOR` var. Recorded as deferred design gap G-2 (not a 06.1 defect — behaves per locked D-02).

### 3. Clean-pane cwd (D-07/D-08)
expected: `wez scene launch dev` from a repo directory opens all panes IN that repo directory with NO visible `cd <path>` line in the scrollback; the git pane shows that repo's status.
result: PASS after fix — initial launch leaked OSC garbage into scrollback (user-reported); fixed in bc1e2ba (clear folded into self-erasing printf). Re-verified clean.

### 4. Arrange — RotatePanes keys (D-12)
expected: In a multi-pane tab, `Alt+Shift+R` rotates panes clockwise and `Alt+Shift+E` rotates counter-clockwise; `Alt+Shift+Z` still toggles zoom. No config-load error from the new bindings.
result: PASS (happy path) — bindings load without error.

### 5. Search overlay (item 8)
expected: `Ctrl+Shift+F` opens WezTerm search; `Ctrl+R` cycles match type (case-sensitive / case-insensitive / regex).
result: PASS (happy path).

### 6. Color alpha accepted (D-09)
expected: `wez pane color '#1a204080'` does NOT error (the 8-digit `#RRGGBBAA` value is accepted, not rejected); it renders solid unless window transparency is enabled (documented caveat).

### 7. Refreshed dev + ai seed scenes (D-13/D-14, SCEN-04)

## Gaps

Two **design** gaps — NOT 06.1 defects (current behavior matches locked decisions
D-02/D-03/D-04). Both extend the same "finish the decoupling" theme 06.1 started
(color was decoupled from title; these decouple icon and tab-vs-pane color). Both
revise locked decisions, so they are out of 06.1 scope → captured for a follow-up phase.

- **G-1 — Icon is not its own attribute.** Icon is inferred from the title's first
  word (ICONS map → glyph prepended into `WEZTERM_TAB_TITLE`). Surprising/implicit
  (`shell` silently becomes 🐚). Fix: a dedicated `icon` attr in recipes + CLI
  (its own slot, like the old bash positional arg), decoupled from title; decide the
  fate of the first-word shortcut (recommend drop). Revises D-03/D-04.

- **G-2 — Tab color and pane color share one var.** `wez tab color` and
  `wez pane color` both write `WEZTERM_TAB_COLOR`, and the renderer paints the active
  pane's value (D-02), so an explicit tab color is clobbered by pane color. Confirmed
  OUR implementation, not a WezTerm limit. Fix: split into `WEZTERM_TAB_COLOR` (tab's
  own, stable) + `WEZTERM_PANE_COLOR` (per-pane accent); renderer precedence = explicit
  tab color wins, fall back to active pane only when the tab has none, and make that
  fallback an explicit opt-in flag (`adopt_active_pane_color`). Revises D-02.
