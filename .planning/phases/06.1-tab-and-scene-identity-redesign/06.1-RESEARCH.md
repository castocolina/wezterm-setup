**Researched:** 2026-06-15

## Summary

This is a **cleanup + extension** phase, almost entirely pre-decided in CONTEXT.md (D-01..D-15). The
job of this research is NOT to choose mechanisms — those are locked — but to pin down the **exact
WezTerm emulator API surface** the planner needs so tasks reference real flags/actions, and to map
each locked decision onto the **existing code that already does the analogous thing** (so the D-01
`/reducing-entropy` consolidation reuses rather than re-derives).

Every mechanism this phase needs is **already proven and present in the codebase or confirmed against
the live WezTerm**: OSC 1337 `SetUserVar` is implemented verbatim in `pane.lua` (`build_osc1337`,
base64 + BEL); `format-tab-title.lua` already reads `tab.active_pane.user_vars.WEZTERM_TAB_COLOR`
(D-02 active-pane-wins is *already the code path* — only the tab WRITE side still uses the
`<color>:<title>` prefix); `wezterm cli spawn`/`split-pane` both accept `--cwd` and `--percent`;
`RotatePanes`, `Search`, and `CopyMode CycleMatchType` are all real actions (the latter two are
*already WezTerm defaults* in the installed version). The only genuinely new color fact is the alpha
caveat (D-09).

**Primary recommendation:** Treat this phase as a refactor-with-extensions. Run `/reducing-entropy`
(D-01) to lift the duplicated color normalizer (`tab.lua` + `pane.lua` both have identical
`strip_alpha`/`normalize_color`/`validate_color`), the title resolver (already shared in
`cli/lib/title.lua`), and the spawn/OSC-emit path into shared `cli/lib/` modules. Then: switch
`wez tab color` to emit `WEZTERM_TAB_COLOR` via OSC (reusing `pane.lua`'s builder) instead of writing
the prefix; move scene cwd to `--cwd` at spawn time; stop stripping the 8th hex digit; add the
RotatePanes bindings; add a doctor core gate that greps the user's `wezterm.lua`. Behavior changes
get a live-WezTerm repro (the live emulator IS available here, so true integration tests via
`WEZTERM_INTEGRATION=1` are feasible — see Validation Architecture).

## Architectural Responsibility Map

The `wez` CLI is an **external process** to WezTerm (per `cli-language.md`) — it talks via `wezterm
cli` IPC and OSC escapes; it does NOT run inside WezTerm's Lua VM. So responsibilities split between
two runtimes that bundle separately.

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Tab color WRITE (`wez tab color`) | CLI / external process (`cli/commands/tab.lua`) | — | Emits OSC 1337 to the pane TTY; no in-VM access |
| Tab color RENDER (tab bar) | Config layer / in-VM (`config/wezterm-setup/format-tab-title.lua`) | — | Only the in-VM `format-tab-title` event can read `tab.active_pane.user_vars` and paint the bar |
| Pane color/title | CLI / external (`cli/commands/pane.lua`) | Config render (format-tab-title) | OSC 11 (bg) + OSC 1337 (accent/title) emitted to pane TTY |
| Scene spawn + cwd/size/focus | CLI / external (`cli/commands/scene.lua` + `cli/lib/scene.lua`) | — | Drives `wezterm cli spawn`/`split-pane --cwd/--percent`/`activate-pane` |
| Recipe parse + schema | CLI / pure core (`cli/lib/recipe.lua` + `cli/vendor/tinytoml.lua`) | — | No I/O; maps TOML → `run_new` args |
| RotatePanes / Search / CycleMatchType | Config layer / in-VM (`config/wezterm-setup/keybindings.lua` → `init.lua resolve_action`) | — | Key assignments resolved to `wezterm.action.*` inside the VM |
| Shadow-detection (doctor) | CLI / external (`cli/commands/doctor.lua`) | — | Greps the user's `wezterm.lua` text on disk; no VM access |
| Seed scenes refresh | CLI / pure data (`scenes/*.toml`) seeded by `cli/commands/seed_scenes.lua` | — | Copy-if-absent of `.toml` files |

**Tier correctness note for the planner:** the tab COLOR has a *split* responsibility — the WRITE is
external (CLI emits OSC) and the RENDER is in-VM (config reads the user var). These must be planned as
two coordinated edits in two separate Lua bundles. A change to one without the other silently breaks
the accent (this is exactly the bug class the phase fixes).

### Pattern 1: OSC 1337 SetUserVar (THE tab-color carrier — D-03)
**What:** Set a WezTerm user var by writing an OSC escape to the pane's TTY. The value is base64-encoded; the name is plain.
**When to use:** `wez tab color` now uses this for `WEZTERM_TAB_COLOR` (same channel panes already use).
**Already implemented** in `cli/commands/pane.lua` — REUSE verbatim (D-01), do not re-derive:
```lua
-- Source: cli/commands/pane.lua (verified present)  [VERIFIED: codebase]
function M.build_osc1337(varname, value)
  return "\27]1337;SetUserVar=" .. varname .. "=" .. base64_encode(value or "") .. "\7"
end
-- usage: emit(M.build_osc1337("WEZTERM_TAB_COLOR", normalized))
```
Official format confirms the shape (name plain, value base64, BEL/`\007` terminated):
```
printf "\033]1337;SetUserVar=%s=%s\007" name `echo -n value | base64`
```
`[CITED: wezterm.org/recipes/passing-data.html]`

**Targeting a specific pane:** there is **no `set-user-var` CLI subcommand** `[VERIFIED: wezterm cli --help + wezterm-cli-surface.md]`. The OSC must reach a specific pane's TTY. `pane.lua` writes to `io.write` (the current pane). For tab-color where the CLI is invoked inside the target pane, that is the active pane. For scenes (a different target pane id), the existing `scene.lua` pattern emits the escape via `wezterm cli send-text --pane-id <id> --no-paste` wrapping the bytes in a `printf '\nnn'` octal line (see Pitfall 2 — raw bytes via `send-text` are eaten by the shell's line editor). That `printf`-octal trick is the proven cross-shell path and must be reused for any pane-targeted user-var write.

### Pattern 3: spawn/split with cwd + percent (D-06/D-08)
**What:** Open a pane directly in a directory (no visible `cd`) and at a size fraction.
```bash
wezterm cli spawn --cwd <dir>                       # new tab, pane opens IN <dir>
wezterm cli split-pane --pane-id <id> --right --percent <1..100> --cwd <dir>
```
`--cwd` = "Specify the current working directory for the initially spawned program"; `--percent` = size as a percentage of available space. `[CITED: wezterm.org/cli/cli/spawn.html, wezterm.org/cli/cli/split-pane.html]`
**6.1 change:** `scene.lua` currently spawns flagless then sends commands. Add `--cwd <resolved>` to the spawn/split commands so the pane lands in the target dir with no `cd` line (D-08 clean pane). `size` percent maps onto `--percent` (the split step already uses `--percent`; per-pane `size` overrides the computed equal-share percent for that step).

### Anti-Patterns to Avoid
- **Writing tab color into the title string** — the whole point of the phase is to stop this. Tab title is pure text via `set-tab-title`; color is the user var.
- **Re-deriving the color palette / OSC builder / base64 in a new module** — violates D-01. `pane.lua` already has all three; the consolidation must MOVE them to `cli/lib/`, not copy them.
- **Spawn-then-`cd`** — leaves a visible `cd` line (D-08 bug). Use spawn `--cwd`.
- **Sending raw OSC bytes via `wezterm cli send-text`** — the shell line editor eats them (zle swallows, readline echoes garbage). Use the proven `printf '\nnn'` octal payload (Pitfall 2).
- **Adding the RotatePanes binding to `keybindings.lua` but not `init.lua resolve_action`** — `resolve_action` `error()`s on an unknown spec type, breaking config load.

## Common Pitfalls

### Pitfall 1: The shadowing inline `format-tab-title` handler (the actual bug being fixed)
**What goes wrong:** The prototype `wezterm.lua` defines its OWN `wezterm.on("format-tab-title", …)`. WezTerm fires ALL registered handlers but the LAST registered / a returning one wins — a user handler that parses `<color>:<title>` (or ignores user vars) shadows the managed renderer, producing the `cyan:` literal / no-color / no-cwd symptoms.
**Why it happens:** `wezterm.on` appends handlers; there is no "replace". A duplicate handler silently overrides.
**How to avoid:** D-05 removes the inline handler from the prototype; D-11 doctor greps the user's `wezterm.lua` for a `format-tab-title` registration (and duplicate keybindings) and FAILS the core gate loudly.
**Warning signs:** tab shows a literal `color:` prefix, or the accent never applies despite `wez tab color` succeeding.

### Pitfall 2: Raw OSC bytes via `send-text` are eaten by the shell
**What goes wrong:** Writing `\27]1337;…\7` through `wezterm cli send-text` reaches the pane's PTY = the shell's stdin. zsh's zle silently swallows the control bytes; bash's readline echoes the printable tail as garbage. The color never applies.
**Why it happens:** `send-text` targets the shell line editor, not the terminal's output parser.
**How to avoid:** Emit via a `printf '\nnn'` octal-escaped line (the shell EXECUTES printf, whose OUTPUT carries the bytes to the terminal). This is already implemented in `scene.lua` (the octal `gsub` + `printf '...'` payload) — reuse it for any pane-targeted user-var write.
**Warning signs:** garbage like `11;#…1337;…` in the pane, or no color.

### Pitfall 3: Adding a key binding to `keybindings.lua` only
**What goes wrong:** `init.lua resolve_action` is a closed switch that `error()`s on an unknown `spec.type`. A new RotatePanes entry in `keybindings.lua` with no matching arm crashes config load (config-error window).
**How to avoid:** Add the `RotatePanes` arm to `resolve_action` in the SAME change. Add `DisableDefaultAssignment` entries (D-12) for any replaced default so `wez keys` stays truthful.
**Warning signs:** WezTerm pops a config-error window on reload.

### Pitfall 4: Expecting `#RRGGBBAA` alpha to render on the tab bar
**What goes wrong:** D-09 stops stripping the 8th hex digit, but WezTerm **ignores the alpha channel except for `selection_fg`/`selection_bg`** `[CITED: wezterm.org/config/appearance.html]`. An 8-digit hex on a pane/tab background renders as if opaque unless window transparency is configured.
**Why it happens:** WezTerm's color parser accepts the value (so it no longer breaks — the goal of D-09) but the compositor only honors alpha in specific places + with `window_background_opacity`.
**How to avoid:** Accept + store `#RRGGBBAA` (don't strip), but DOCUMENT that alpha only renders with window transparency (D-09 / D-18 caveat). The named palette stays the opaque DEFAULT.
**Warning signs:** user sets `#00ff0080` expecting a translucent pane and sees solid green — this is WezTerm behavior, not a bug.

### Pitfall 5: TOML comma inside a multi-field pane command
**What goes wrong:** `recipe.lua pane_table_to_spec` joins `cmd=…, color=…` and `scene.lua parse_pane_spec` splits on top-level commas — a comma INSIDE a command value mis-splits.
**Why it happens:** the string-spec round-trip (recipe → `--pane` string → parse) is comma-delimited.
**How to avoid:** The v1 limitation is documented in `recipe.lua` (the seeds never combine a comma'd command WITH color/title). Adding `cwd`/`focus`/`size` to the SAME comma-joined spec INHERITS this limitation. If the redesigned seeds (D-13/D-14) need a comma in a command alongside other fields, prefer a structured `run_new` entry point OR keep commands comma-free. Flag for the planner.
**Warning signs:** a recipe command with an embedded comma loses its tail or mis-parses a field.

## Security Domain

> `security_enforcement: true`, `security_asvs_level: 1`. This is a local single-user terminal CLI
> with no network/auth/session surface; the relevant ASVS category is input validation around the
> values that reach `os.execute`/`io.popen`/the spawned PTY.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | No auth surface (local CLI) |
| V3 Session Management | no | No sessions |
| V4 Access Control | no | Runs as the invoking user; no privilege boundary |
| V5 Input Validation | **yes** | Validate-before-emit (color/layout/cwd/focus/size); `shquote` single-quote escaper for every user-derived value reaching `os.execute`/`io.popen`; OSC values base64-encoded (neutralizes control bytes); path-traversal `guard_name` for recipe names |
| V6 Cryptography | no | None (base64 here is encoding, not crypto) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Shell command injection via a recipe/CLI value reaching `os.execute`/`io.popen` | Tampering / Elevation | `shquote` (`'…'` with `'\''` rewrite) — already applied in tab/scene/install_state; EVERY new cwd/command value MUST go through it |
| OSC escape injection / breakout (control bytes in a user var or title) | Tampering | base64-encode the OSC 1337 value (`build_osc1337` already does); never concatenate a command into an escape sequence — emit it as a distinct trailing line (T-04-02, already enforced in scene.lua) |
| Path traversal via a scene recipe name (`../../etc/...`) | Tampering / Info disclosure | `recipe.lua guard_name` rejects `/` and `..` BEFORE any `io.open`; resolved path is always `<scenes_dir>/<name>.toml` |
| cwd grammar shell evaluation (`$(...)` / backticks in a `cwd` value) | Elevation | The locked grammar FORBIDS `$(...)`; expansion is pure-Lua string handling (`~`, `$ENV`, `.`/`..`) — NO shell eval. Validate-before-emit rejects unsupported forms |
| Malformed TOML causing a Lua traceback (info leak) | DoS / Info disclosure | `recipe.lua` wraps `toml.parse` in pcall and translates the raised error to a clean "could not parse TOML at line N" (T-05-02) |
| Doctor reading the user's `wezterm.lua` | Info disclosure | Doctor only READS + greps text; it does NOT execute the user's wezterm.lua (T-06-02 — only the managed init.lua is loaded under pcall) |

**Security note for the new cwd path (D-08):** the `--cwd` value is passed to `wezterm cli spawn`
as an argument — it MUST be `shquote`'d like every other user-derived value, and the pure cwd-grammar
resolver MUST reject `$(...)`/backticks per the lock rather than passing them to a shell.
