# Phase 2 — UI Design Contract

> Visual and interaction contract for `wez pane` (per-pane background color, opacity, title)
> rendered via WezTerm's tab bar and per-pane terminal background. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.

**Surface type:** Terminal UI (WezTerm config + CLI), not web/GUI. There is no HTML/CSS,
component library, typography scale, spacing system, or responsive layout. The UI surface
consists of:

1. **WezTerm tab-bar** — rendered by a Lua `format-tab-title` event handler returning an
   array of `{Background, Foreground, Text}` styled runs.
2. **Per-pane terminal background** — set via OSC 11 escape, scoped to the emitting pane's
   terminal (each pane is its own terminal instance).
3. **Pane/tab titles** — plain text + emoji glyphs, rendered inside tab-bar runs.

Sections of the standard template that do not apply to this surface (Spacing Scale,
Typography, Registry Safety) are marked **N/A** with the reason. Sections that map to
terminal-UI equivalents (Color, Copywriting, State Distinction, Label Format) are filled
concretely with the proven values from `02-CONTEXT.md`.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — pure Lua inside WezTerm, zero external dependencies |
| Preset | not applicable |
| Component library | none — `format-tab-title` returns raw styled runs (Background/Foreground/Text), no widget toolkit |
| Icon library | none — Unicode emoji glyphs only, via the icon-name shortcut map (`docker`→🐳, `rust`→🦀, `git`→🔀, ~40 names total per `wez-tab _weztab_icon`, ported in Phase 2) |
| Font | inherited from the user's WezTerm `font` config — Phase 2 does not set or override font face/size |

## Spacing Scale

**N/A** — there is no CSS box model. The only "spacing" concerns are:
- A single leading/trailing space inside each tab-bar text run for visual breathing room
  (e.g. `" 1: name "`, `" ●-> "`), matching the proven prototype's existing format strings.
- No new spacing tokens are introduced by Phase 2; reuse the exact padding already present
  in the ported `format-tab-title` string templates from `../wezterm-setup_/config/wezterm.lua`.

## Typography

**N/A** — WezTerm tab-bar text uses the terminal's configured font; there is no font-size,
weight, or line-height scale to declare. The only typographic distinction in this phase is
**bold vs. non-bold** (see Label/Format Contract below), which is a terminal text attribute,
not a font-size/weight token.

## Color

This is the core visual contract for Phase 2. All hex values below are **locked from the
proven prototype** (`../wezterm-setup_`) and embedded in `02-CONTEXT.md <code_context>`.
Do not invent new values; port these exactly.

### 10 Named Color Profiles

Each profile has **two color pairs**: a muted per-pane OSC-11 background (dark, applied to
the focused pane's terminal background) and a tab-bar accent pair (background + foreground,
applied to the tab-bar segment for that pane/tab).

| Profile | Pane OSC-11 background (muted) | Tab-bar background | Tab-bar foreground |
|---------|--------------------------------|---------------------|---------------------|
| red | `#1f1617` | `#5f1e1e` | `#f0c8c8` |
| orange | `#1f1916` | `#5f3a1e` | `#f0d8c8` |
| yellow | `#1c1c16` | `#5f5f1e` | `#f0f0c8` |
| green | `#161c17` | `#1e5f2e` | `#c8f0d0` |
| teal | `#151b1a` | `#1e4f4a` | `#c8f0e8` |
| cyan | `#161c1c` | `#1e5f5f` | `#c8f0f0` |
| blue | `#161a1f` | `#1e3a5f` | `#c8ddf0` |
| navy | `#14151c` | `#1a2040` | `#c8cce0` |
| purple | `#1a161f` | `#3f1e5f` | `#d8c8f0` |
| pink | `#1f1619` | `#5f1e4a` | `#f0c8e0` |

### Default (no color set / after `reset`)

| Role | Value | Usage |
|------|-------|-------|
| Default tab-bar background | `#333333` | Tab segment background when no pane/tab color is set |
| Default tab-bar foreground | `#c0c0c0` | Tab segment text color when no pane/tab color is set |
| Default pane background | WezTerm theme default (no OSC 11 override) | `wez pane color reset` clears the OSC-11 override entirely — does not set a hardcoded hex; the terminal falls back to its configured theme background |

### Color Role Mapping (60/30/10 equivalent for terminal UI)

The 60/30/10 split is reinterpreted for a terminal surface as: **base terminal surface /
tab-bar chrome / per-pane accent**.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (~60%) | WezTerm theme default background (unchanged by Phase 2) | The pane content area for panes with no color set — Phase 2 never touches this for unconfigured panes |
| Secondary (~30%) | `#333333` / `#c0c0c0` (default tab-bar bg/fg) | Tab-bar chrome for tabs/panes with no color assigned |
| Accent (~10%) | One of the 10 profile pairs above, selected per-pane via `wez pane color <name>` | Reserved for: (1) the focused pane's terminal background (muted OSC-11 hex), (2) that pane's tab-bar segment background+foreground (accent pair) — and ONLY these two surfaces. Accent never bleeds into other panes' backgrounds or other tabs' bar segments. |
| Destructive | not applicable — Phase 2 has no destructive actions (see Copywriting Contract) | n/a |

### Contrast / Legibility

All 10 tab-bar fg/bg pairs above are **dark-background + light-foreground** combinations
(background luminance roughly 0x1e–0x5f per channel, foreground roughly 0xc8–0xf0 per
channel) — this gives a contrast ratio well above WCAG AA (4.5:1) for normal text, consistent
with the default `#333333`/`#c0c0c0` pair already in use. No new pair may invert this
relationship (i.e., never light-bg + dark-fg) — port the table above verbatim, do not
recompute or "improve" any of the 10 pairs.

The muted per-pane OSC-11 backgrounds are deliberately near-black with a faint color cast
(luminance roughly 0x14–0x1f per channel) so that standard terminal foreground text (white,
gray, ANSI colors) remains legible inside a colored pane without per-pane foreground-color
changes. Phase 2 does not change any pane's text/ANSI foreground colors — only OSC 11
(background).

## State Distinction (terminal-UI equivalent of interaction states)

**Primary visual anchor:** when a pane has a color set, its OSC-11 background tint and the
corresponding tab-bar accent segment are the primary visual anchor; the bold/white active-tab
indicator is the secondary anchor that MUST remain legible over any accent color.

WezTerm tabs render as styled segments in the tab bar; "hover" in the traditional sense does
not apply (no mouse-hover state is part of this contract — WezTerm tab bars are click/key
driven). The states that matter:

| State | Visual treatment |
|-------|-------------------|
| **Active tab** | Bold white text (`Foreground: White`, `Intensity: Bold` or equivalent), regardless of any pane/tab accent color underneath — the active tab must always be visually distinct from inactive tabs (ROADMAP Phase 3 success #4 carries this forward; Phase 2 must not regress it for the existing default formatter) |
| **Inactive tab** | Dim/non-bold text using the accent pair's foreground color (if a pane/tab color is set) or the default `#c0c0c0` (if not) |
| **Pane focused, color set** | Pane terminal background shows the muted OSC-11 hex (PANE-04: this must persist, not flicker, when focus moves to this pane and back) |
| **Pane unfocused, color set** | Per OSC 11 semantics, the background tint is a property of that pane's terminal and is **independent of focus** — the colored background is visible regardless of which pane currently has focus (PANE-04 success #3: "no flicker or reset on focus change" applies to BOTH the OSC-11 pane background AND the tab-bar accent/title) |
| **No color set (default)** | Pane background = WezTerm theme default; tab-bar segment = `#333333`/`#c0c0c0` |
| **`wez pane color reset`** | Pane background returns to WezTerm theme default (OSC-11 override cleared); tab-bar segment returns to default `#333333`/`#c0c0c0` (user var cleared) — this is the "restore to default appearance" affordance for PANE-02 |

## Label / Title Format Contract (PANE-03, PANE-04)

Locked from the proven prototype's tab-bar format string. Port verbatim.

### Tab label structure

```
<index>: <name><active-indicator>
```

- **Index prefix**: `N: ` where `N` is the 1-based tab index (e.g. `1: `, `2: `).
- **Name**: the tab's title — by default WezTerm's auto-derived title (running program /
  cwd), OR the pane's custom title if one is set (see override rule below).
- **Active indicator**: ` ●-> ` appended (or otherwise composited per the prototype's exact
  string) when the tab is the active tab. Inactive tabs omit this indicator.
- **Right-truncation**: tab labels that exceed the available tab-bar width are truncated
  from the right (ellipsis or hard cut per the prototype — port the existing truncation
  logic, do not redesign it).

### Active vs. inactive text styling

- **Active tab**: bold, white foreground (`Intensity: Bold`, `Foreground: White`) —
  overrides the accent-pair foreground for legibility of the active indicator.
- **Inactive tab**: normal weight (non-bold), foreground = accent pair's foreground color if
  a pane/tab color is set, else default `#c0c0c0`.

### Title override rule (PANE-03 / PANE-04)

- A pane's custom title (`WEZTERM_TAB_TITLE` user var, set via `wez pane title "<text>"`)
  **overrides the tab's displayed title while that pane is focused/active within the tab**.
- `wez pane title docker "compose up"` → tab-bar shows `🐳 compose up` (icon-name shortcut
  expanded to its emoji glyph + space + remaining text).
- If the first token of the title argument is NOT a recognized icon name, the entire input
  is treated as literal title text (no icon prepended).
- Empty string / `wez pane title ""` (or `reset`, per CONTEXT D-04) clears the custom title
  user var — the tab-bar reverts to WezTerm's auto-derived title (the "default appearance"
  affordance, mirroring `wez pane color reset`).

### Pane-color vs. tab-color priority (cross-reference, locked in `tab-title-format.md`)

- If both a pane color and a tab color are set on the same tab, the **pane's** `WEZTERM_TAB_COLOR`
  user var takes priority for the tab-bar accent pair — Phase 2 only sets the pane-level var;
  Phase 3 introduces the tab-level var and the priority resolution logic in the formatter.
  Phase 2's `format-tab-title` handler must read the pane var and apply the corresponding
  accent pair from the table above when present.

## Opacity Contract (PANE-05, CONDITIONAL — spike-gated per D-03/D-06)

Per-pane opacity is **NOT proven**. Its visual contract is conditional on the Phase 2 spike
(`.tmp/h<NN>-<slug>/`) outcome:

| Spike outcome | Visual contract |
|---------------|-------------------|
| **IF per-pane translucency is achievable** (e.g. via `window:set_config_overrides` scoped per-pane, or an OSC variant) | `wez pane opacity 0.7` (or `--opacity 0.7` / alpha channel in `rgba()`/`#rrggbbaa`) renders **that pane's** background at 70% opacity, revealing whatever is behind the WezTerm window (desktop/other windows). All OTHER panes and the tab bar remain fully opaque. The muted OSC-11 background hex (table above) is composited at the requested alpha. |
| **ELSE (not achievable — expected per kitty precedent)** | The alpha component of any input (`rgba()` alpha, `#rrggbbaa` last byte, or a separate `--opacity`/`opacity` argument) is **silently stripped before the OSC-11 escape is emitted** — the pane renders fully solid using the muted background hex from the table above (alpha discarded, RGB unchanged). A **one-time warning is printed to stderr** the first time an opacity input is received in a session, informing the user that per-pane opacity is not supported and the color was applied without transparency. The **OS-window opacity is never modified** under any circumstance (explicitly rejected per D-03). |

**Affordance for both branches:** `wez pane color <name|hex>` with an alpha component (or
`wez pane opacity <value>`) must produce a **visibly different pane background** than the
same command without alpha — either translucent (if proven) or solid-with-warning (if not).
The user must never see "nothing happened."

## Copywriting Contract

Phase 2 has a small, CLI-facing copy surface (stderr messages, completions) — no GUI dialogs,
toasts, or empty-state screens exist for a terminal config.

| Element | Copy |
|---------|------|
| Primary CTA | N/A — no GUI call-to-action; the "primary action" is the CLI invocation itself: `wez pane color <name>` (set color) |
| Empty state heading | N/A — no empty-state screen. Closest equivalent: a pane with no color/title set shows WezTerm's default appearance (default tab-bar pair `#333333`/`#c0c0c0`, theme-default pane background, auto-derived title) — this IS the empty state, and it requires no copy |
| Empty state body | N/A — see above |
| Error state | Invalid color input (D-01 validate-before-emit): print to stderr, e.g. `error: unknown color "fuschia" — expected one of: red, orange, yellow, green, teal, cyan, blue, navy, purple, pink, or a hex value (#rgb / #rrggbb / #rrggbbaa)` and exit non-zero **before** any OSC escape is written (no half-applied state) |
| Destructive confirmation | None — Phase 2 has **no destructive actions** requiring confirmation. `wez pane color reset` and `wez pane title ""` are reversible (re-running `wez pane color <name>` / `wez pane title "<text>"` re-applies state) and are documented as restore-to-default operations, not destructive ones — no confirmation prompt needed |
| Opacity unsupported warning (conditional, see Opacity Contract) | `warning: per-pane opacity is not supported by your WezTerm version — color applied without transparency` (printed once per session to stderr, non-fatal) |
