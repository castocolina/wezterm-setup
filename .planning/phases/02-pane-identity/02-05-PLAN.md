<objective>
Wire dynamic Tab-completion for the `pane` surface (D-16): add `pane-colors` and `pane-icons`
contexts to `wez __complete` (`cli/commands/complete.lua`), and extend the generated zsh/bash
completion scripts (`cli/commands/completions.lua`) so `wez pane color <Tab>` and
`wez pane title <Tab>` call those contexts for dynamic candidates. Static subcommand/flag
completion for `pane`, `color`, `title`, `reset`, `--opacity` already flows automatically from
`cli/spec.lua` registration (done in 02-03/02-04) via the existing spec-walking generator --
this plan does not duplicate that; it only adds the dynamic layer plus the nested-subcommand
dispatch the dynamic layer needs.

Purpose: PANE-04 success criterion #4 requires completion for named color profiles, `reset`,
`title` (icon-name shortcuts), and `--opacity` to all be tab-completable. Without this plan,
`wez pane color <Tab>` and `wez pane title <Tab>` complete nothing (the existing generators only
emit top-level subcommand flags, never per-subcommand dynamic values).

Output: `cli/commands/complete.lua` gains `pane-colors` and `pane-icons` providers sourced from
the single canonical color/icon table established by 02-03/02-04. `cli/commands/completions.lua`
gains a second-level `pane color` / `pane title` case in both `gen_zsh` and `gen_bash` that calls
`wez __complete pane-colors` / `wez __complete pane-icons`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| shell (zsh/bash completion) -> `wez __complete <context>` | The shell's Tab-completion machinery invokes `wez __complete pane-colors` / `wez __complete pane-icons` as a subprocess and consumes its stdout as candidate tokens during interactive expansion |
| `wez __complete <context>` -> canonical color/icon tables | `complete.lua` reads fixed Lua tables (no user input) to build candidate lists |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-05-01 | Tampering | `cli/commands/complete.lua` CONTEXTS dispatch | accept | `pane-colors`/`pane-icons` contexts are closed-dispatch keyed lookups; `args.context` is a fixed string supplied by the generated completion script, never raw user keystrokes -- no path for arbitrary context injection |
| T-02-05-02 | Information Disclosure | `wez __complete pane-colors` / `pane-icons` output | accept | candidates are a fixed/derived list of color and icon names already public in pane.lua/format-tab-title.lua; nothing sensitive is emitted |
| T-02-05-03 | Tampering | generated zsh/bash completion scripts | mitigate | per T-07-02 pattern, `compadd`/`compgen -W` only ever receive `[%w_-]` tokens written via `io.write(token .. "\n")` in complete.lua -- no raw arg is eval'd, and the generated shell code never interpolates candidate values directly (it always shells out to `wez __complete`, keeping candidate data out of the generated script's static text) |
| T-02-05-04 | Denial of Service | `wez __complete pane-icons` (iterating the icon-name map) | accept | the icon-name map is a small (~40 entry) compile-time-fixed table; iteration cost is negligible and cannot be influenced by user input |
</threat_model>
