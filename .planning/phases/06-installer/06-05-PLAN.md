<objective>
Ship INST-09: the `wez update` subcommand that checks for and applies updates without retyping the remote
URL. It re-invokes the **SAME shared launcher** (`tools/install.sh` from Plan 04) the `curl|bash` one-liner
uses — ONE entry point, ONE update flow, NO divergent second path (P6-D11). It refreshes the `wez` binary,
the managed config assets, and (when a newer `nightly` is available) WezTerm, all under P6-D09's rules
(sudo-free, never touch a system install, update-in-place only for the user-path managed install) and
P6-D05's trust model (inherited from the launcher).

Per the D-01 boundary, `update.lua` is a THIN Lua command: the ONLY logic that lives in Lua is the
version-comparison DECISION — and that decision is SPLIT into two DISTINCT freshness comparators (Warning 4:
do NOT conflate them, because they compare different things):
  (i) **`wez` BINARY freshness** — compare `M.VERSION` (the semver / release tag the binary was stamped
      with, e.g. `0.1.0`) against the latest published `wez` RELEASE tag. This is a SEMVER/tag comparison,
      NOT a YYYYMMDD datestamp (`wezterm_version_datestamp` is for the WezTerm nightly only and must NOT be
      used here).
  (ii) **WezTerm EMULATOR freshness** — compare the installed WezTerm's 8-digit `YYYYMMDD` datestamp
      against the latest-nightly want-datestamp; this comparison is DELEGATED to 06-06
      (`resolve_want_datestamp`/`wezterm_datestamp_ge`), consuming Plan 01's ratified Open-Q1 query.
Each comparator gets its own comparator function + its own fixtures. ALL fetch/unpack/binary-self-replace is
DELEGATED to the shared launcher — `update.lua` shells out to it (the same one the one-liner runs), never
re-implementing download/verify/place logic.

Self-replace safety (RESEARCH Pattern 4): the running `wez` cannot be overwritten in place. The swap (done
by the launcher glue, not Lua) downloads the new binary to a temp file in the SAME directory as the live
`wez`, `chmod +x`, then atomic `mv -f` over it — `rename(2)` only swaps the directory entry; the old inode
survives for the still-running process. NEVER `rm`-then-write (ETXTBSY / no-binary window). HARD CONSTRAINT
P6-D09: update-in-place applies ONLY to the project-managed user-path install (`~/.local/bin/wez` /
`~/.local/bin/wezterm`). The system-install guard CALLS 06-06's reusable `wezterm_install_is_user_path()`
predicate (the real predicate factored in 06-06 — NOT a re-mirror of `detect_and_reuse:83`): if the active
`wez`/WezTerm resolves OUTSIDE `~/.local` (the verified real case: apt `wezterm-nightly` in `/usr/bin`,
root-owned), it is NEVER sudo'd/overwritten — `update.lua` detects (via the predicate) and messages. Clear
no-op message when both are already current.

Completion (D-16): register `update` in `cli/spec.lua`'s three places (CATEGORIES, SUBCOMMANDS,
build_parser) exactly like `seed-scenes`, so `wez update` tab-completes with NO script edit (the
completion generator walks the spec).

Purpose: a self-update front door so users (and the installer's update-in-place path) refresh through one
trusted flow instead of re-pasting the remote URL.
Output: `cli/commands/update.lua` (NEW thin command with the SPLIT comparators), `cli/spec.lua` (MODIFIED —
`update` registered), `tests/cli/update_test.lua` (NEW decision tests for BOTH comparators), and the
`spec_test.lua` registration assertion extended.
