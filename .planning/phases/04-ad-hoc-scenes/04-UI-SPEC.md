# Phase 4 — UI Design Contract

> Visual and interaction contract for `wez scene new`. This is NOT a web/GUI phase — there is no
> HTML/CSS/component library. The "UI" surface is (1) the **terminal visual output**: the
> multi-pane tab WezTerm renders after materialization (layout geometry, per-pane background
> colors, tab accent + title, per-pane titles), and (2) the **CLI textual surface**: the shape,
> help text, error messages, and validation behavior of `wez scene new` itself. This contract
> locks both, grounded in the palette and mechanisms already proven in Phases 2–3. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.

## Layout Geometry Contract
*(Reinterpretation of "Spacing Scale" for a terminal multi-pane tab — pixel spacing does not
apply; the equivalent contract is split-percentage geometry per layout at N panes.)*

Each layout must scale to **arbitrary N** (D-02) — no fixed canonical pane count, no minimums
guard. N = number of `--pane` entries (D-01). The split **percent math is this phase's
design surface**; the table below is the prescriptive default the executor implements.

| Layout | Geometry rule (N panes) | Split direction sequence |
|--------|------------------------|---------------------------|
| `tall` | 1 main pane at **50%** width (left) + (N-1) panes stacked in the remaining 50% (right), each getting `100/(N-1)`% height | First split: vertical (left/right) at 50%. Remaining splits: horizontal, each new split takes `100/(remaining)`% of the current bottom area so all stacked panes end equal height |
| `tall:mirrored` | Same as `tall`, mirrored — main pane at **50%** width on the **right**, (N-1) stacked panes on the **left** | Same sequence as `tall`, `--left`/`--right` swapped |
| `grid` | Roughly-square `ceil(sqrt(N))` columns × `ceil(N / cols)` rows; last row may have fewer panes (left-aligned, no empty placeholders) | Row-major: split each row top-to-bottom first (horizontal splits at `100/rows`%), then split each row into its columns (vertical splits at `100/cols`%) |
| `horizontal` | N panes side-by-side, each `100/N`% width | N-1 sequential vertical splits, each new split takes `100/(remaining)`% of the current rightmost area so all panes end equal width |

**N=1 special case (all layouts):** no split occurs — the single pane fills the tab. This is the
common path for D-10's "current tab has exactly 1 pane → reuse it as pane 1" when the scene also
requests only 1 pane (degenerate but valid).

**Equal-share formula invariant:** for any layout, sequential splits MUST use `100/(remaining
panes including this one)`% so the final result is N panes of equal size within their
row/column — never a fixed 50/50 that leaves trailing panes shrinking geometrically. This is the
authoritative tie-breaker for "exact split percent" left open in 04-CONTEXT.md Claude's
Discretion.

**Exceptions:** none. If N is large enough that `grid` produces a visually degenerate result
(e.g. 1 column), that is an accepted consequence of "layouts just scale" (D-02) — no special-case
override flag ships this phase (D-12).

## Color Contract
*(Reinterpretation of "Typography" + "Color" — the terminal-visual identity is entirely carried
by the 10-color palette proven in Phase 2/locked in `tab-title-format.md`. No font sizes/weights
apply.)*

### The 10 color profiles (locked, reused verbatim — no new colors this phase)
`red`, `orange`, `yellow`, `green`, `teal`, `cyan`, `blue`, `navy`, `purple`, `pink` — case-insensitive,
autocompletable, identical set for `--pane … color=` and the tab-level color flag.

| (default, no color set) | `#333333` | `#c0c0c0` |

### Priority / resolution rules (locked, reused — no new precedence this phase)
- **Per-pane color > tab color** (TAB-04, `tab-title-format.md`). A scene that sets a tab color
  AND a per-pane `color=` on the same pane renders that pane with its OWN color while it is
  active; the tab-bar accent for OTHER panes in the same tab still shows the tab color.
- **Active-tab distinction** (TAB-05: `●->` indicator + bold) is rendered regardless of accent —
  unaffected by scene styling.
- The scene sets BOTH levels (D-05): a tab-level color+title for the whole scene, AND per-pane
  color+title for each pane that requests one. Panes with no `color=`/`title=` get neither —
  they inherit the tab accent / auto-title (D-07) only.

### Auto pane title (D-07)
- A pane with no explicit `title=` is titled from its startup command (reuses the Phase 2
  pane-title path, via `cli/lib/title.lua` `resolve_title`/`resolve_title_str`).
- A pane with no startup command (`--pane shell`, D-04) and no `title=` gets NO auto title — it
  stays the WezTerm default (active-pane shell name), per "as if nothing happened" (D-09).
- Explicit `title=<value>` overrides the auto title and goes through the SAME icon-name
  resolution as `wez pane title` / `wez tab title` (the 22-icon map in `cli/lib/title.lua`,
  `reset` keyword clears to "").

### D-09 — "visually clean pane" contract (the terminal-visual acceptance bar)
After `wez scene new` completes, each pane must look **exactly as if the user had typed the
startup command into a freshly opened shell** — no visible escape-sequence residue (no raw
`\033]11;...\033\\` or `\033]1337;...\007` bytes printed to the pane), no stray blank lines from
injection, and the command's own output is the first thing visible after the shell prompt.
Mechanism (quiet emission via `printf` with no extra newline, and/or a `clear` after injection
but before the startup command runs) is the planner's/executor's choice — but THIS is the
observable success bar the executor's manual repro must demonstrate per layout.

## Copywriting Contract
*(Reinterpretation for CLI-textual UX — "Primary CTA" = the canonical invocation shape; "Empty
state" = the no-`--pane`-provided case; "Error state" = validate-before-emit messages;
"Destructive confirmation" = N/A, this phase has no destructive actions.)*

| Element | Copy / Contract |
|---------|------|
| Primary CTA (canonical invocation) | `wez scene new --layout <tall\|tall:mirrored\|grid\|horizontal> --pane '<spec>' [--pane '<spec>' ...] [--color <name>] [--title "<text>"]` — `--layout` and at least one `--pane` are required; `--color`/`--title` set the tab-level identity (D-05) |
| `--pane` value grammar | Bare value = command (`--pane 'docker stats'`). Keyword `shell` = plain interactive shell, no command sent (D-04). `key=value` comma-separated form for styling: `--pane 'cmd=docker stats, color=teal, title=stats'` — `cmd=`, `color=`, `title=` all optional, order-independent (D-06). If `cmd=` is absent and the value is not `shell` and contains no `=`, the whole value is treated as the command (bare form, backward-compatible with D-03) |
| Empty state (no `--pane` given) | `wez scene new --layout grid` with zero `--pane` flags is a **usage error**, not a silent default. Error to stderr: `error: wez scene new requires at least one --pane (got 0)` — exits non-zero before any `spawn`/`split-pane` call (validate-before-emit, mirrors Phase 2 D-01) |
| Error: unknown `--layout` | `error: unknown layout '<value>' — expected one of: tall, tall:mirrored, grid, horizontal` — stderr, exit non-zero, before any spawn |
| Error: unknown `color=` / `--color` value | `error: unknown color '<value>' — expected one of: red, orange, yellow, green, teal, cyan, blue, navy, purple, pink` — stderr, exit non-zero, before any spawn (mirrors Phase 2 D-01 / Phase 3 D-06) |
| Error: malformed `--pane` key=value | `error: invalid --pane value '<value>' — unknown key '<key>' (expected cmd, color, title)` — stderr, exit non-zero, before any spawn |
| Validate-before-emit (overall contract) | ALL `--pane` values and `--color` are parsed and validated for EVERY pane BEFORE the first `wezterm cli spawn`/`split-pane` call. A scene either builds completely or makes zero changes — no partially-built tab left behind on a validation error |
| Success output (stdout) | On success, print nothing beyond what the user's own commands produce in their panes — `wez scene new` itself stays silent on stdout (terminal stays "clean" per D-09; no `Scene created!`-style banner). If a non-TTY/CI affordance is wanted later, that is a new decision, not this phase's default |
| Focus pane after build | The **main pane** of the layout (the `tall`/`tall:mirrored` large pane; pane 1 for `grid`/`horizontal`) is activated (`activate-pane`) after all panes are styled and commands sent. This is the sensible default for the open "which pane is focused" discretion item — executor may override with evidence from the manual repro |
| Destructive confirmation | none — this phase has no delete/overwrite/reset actions. (D-10's "drop the current pane" fallback path, if chosen over reuse, is an internal materialization detail, not a user-facing destructive action requiring confirmation — the user's own pane content was already visible/active and they invoked the command that replaces it) |

## Materialization Contract (terminal-visual — where the scene appears)
*(No template section maps directly to this; included because it is the dominant "where does the
UI show up" decision for this phase — D-10/D-11/D-12, all locked.)*

| Current tab state | Result |
|---|---|
| Exactly 1 pane | Build the scene **in the current tab**, absorbing the current pane as pane 1 (reuse preferred — keeps its cwd; drop-and-recreate acceptable). Final pane count = exactly N (never N+1) |
| ≥2 panes | Spawn a **new tab in the same OS window** and build the scene there; the existing multi-pane tab is left untouched |
| Either case | **Never** a new OS window (D-12). **No override flags** this phase (`--new-tab`/`--here` are explicitly deferred, not shipped) |
