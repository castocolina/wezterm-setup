`ydotool` has no window-targeting concept on Wayland (every injected event goes to whatever
window holds OS focus, system-wide), and `wmctrl`/native-Wayland tooling cannot see a

`wmctrl -l` on this box — empirically confirmed during planning). Firing a real chord without
first PROVING focus targets the right window, and without proving the window under test is
running the SAME keybindings a real user gets, would be exactly the "probably works" assumption
this project's input-injection-safety discipline forbids.

## Round-1 review findings this revision fixes (see Review Dispositions Ledger at the bottom)
The prior version of this plan shipped a scratch config that never loaded
`config/wezterm-setup/init.lua` (so it would have exercised WezTerm stock defaults, not the
product), referenced two nonexistent public symbols on `mux.lua` (`mux.shquote`,
env-prefix building), let a `SKIPPED` verdict silently satisfy Task 1's "done" criteria on a
box already proven XWayland-capable, built a non-unique WM_CLASS tag from a bare `os.time()`,
left `M.probe()`'s own internal session lifecycle un-pcall-guarded, had a live
time-of-check/time-of-use gap between focus-verification and the actual keypress, printed
diagnostic values in `<verify>` without ever asserting on them, and never mentioned the
hypothesis/probe workflow this project's own CLAUDE.md mandates. All of these are fixed below.

## The resolved mechanism (not a documented-but-unverified assumption)
WezTerm's `enable_wayland = false` config key forces its GUI window onto XWayland (the SAME knob
`tests/e2e/lib/mux.lua`'s scratch config already sets for the headless mux, just for a different
reason there). An XWayland window IS visible to X11 window tools — confirmed empirically during
planning: `wmctrl -l` sees the "Xwayland Video Bridge" bridge window (proving XWayland windows
register with KWin's X11-facing window management), while native Wayland surfaces (this session's
own terminal) are invisible to it. `wezterm --config-file <path> start --always-new-process
--class <unique-tag> --cwd <launch> --position 0,0` (real, documented CLI flags — confirmed live
via `wezterm --help` and `wezterm start --help` during planning: `--config-file` is a TOP-LEVEL
flag before the `start` subcommand, not a `start`-level one) tags the forced-XWayland window with
a caller-chosen WM_CLASS/app_id and pins it to a fixed screen position, so `xdotool search --class
<unique-tag>` locates it deterministically and every capture/geometry-dependent assertion (this
plan's and Plan 03/04's) sees a repeatable window position — never "whichever window is topmost"
and never a WM-dependent placement. `xdotool windowactivate --sync <id> getactivewindow` (a SINGLE
chained invocation — see the TOCTOU note below) then raises+focuses it and reports back the
now-active window id, compared against `<id>` as an EXPLICIT PASS/FAIL gate BEFORE every fired
chord (not just once at the start) — this is the concrete, automatable focus-verification step
CONTEXT.md's critical-focus-area requires. Once verified, a SEPARATE `xdotool key --clearmodifiers`
invocation (no `--window` flag — deliberately: `xdotool key --window <id>` exists and was
considered, but per `xdotool key --help` it delivers the event via a synthetic `XSendEvent` to a
specific window rather than through the XTEST extension, and many modern toolkits — including
WezTerm's — legitimately ignore synthetic `XSendEvent` keystrokes for the same reason a
malicious app cannot inject trusted input; using bare `xdotool key` with NO window argument
instead uses XTEST to synthesize a real hardware-equivalent keypress to whatever currently holds
real X focus, which was JUST proven correct) fires the actual chord, exercising WezTerm's real
key-dispatch layer end-to-end (never `wezterm cli send-text`, which would bypass the thing being
tested).

**TOCTOU note (HIGH finding, resolved not hidden):** the verify-then-fire pipeline cannot be
fully atomic from userspace. This plan narrows the race to the minimum achievable without a
compositor-level API: `windowactivate --sync <id>` and the confirming `getactivewindow` are
chained into ONE `xdotool` invocation (zero process-launch gap between activation and
confirmation — xdotool's own window-stack mechanism, documented in `xdotool search --help`'s
"WINDOW STACK" reference, makes this possible). The `key` invocation cannot be safely folded into
that SAME chain — doing so would push the `getactivewindow` result onto xdotool's internal window
stack and silently change `key`'s target semantics from "whatever currently holds real focus" to
an explicit `--window`-style target (the exact behavior being deliberately avoided above) — so
`key` remains one, unavoidably separate, immediately-following invocation. A THIRD, quick
`getactivewindow`-only call runs immediately AFTER firing to detect (not prevent) a focus change
that happened concurrently; a mismatch there hard-errors the case as failed rather than trusting
an unverifiable fire. This residual gap is recorded and accepted in the threat model below, not
pretended away.

## Known residual risk (flagged, not silently patched)
On a PURE-Wayland compositor with no XWayland available at all, this mechanism has no fallback —
`ydotool` alone offers no verifiable focus story on Wayland (confirmed in CONTEXT.md's Claude's
Discretion section and re-confirmed live during planning: `xdotool getwindowfocus getwindowname`
returns an empty name for the native-Wayland session on this exact box, evidencing that xdotool's
X11 view of a Wayland session is unreliable for anything OTHER than an XWayland-forced window it
is deliberately told to look for). Task 1 below therefore gates Tier 3 Firing's self-skip on
XWayland-resolvability specifically (an `xdotool`-resolvable, `--class`-tagged window), not merely
on "xdotool is on PATH" — a host where the forced-XWayland window itself never appears self-skips
loudly rather than firing blind. If Task 1's empirical build-out finds even THIS mechanism
unreliable (e.g., `getactivewindow` never stabilizes on the target id across repeated runs), that
is a genuine phase-blocking finding — see the escalation clause in Task 1's action, not a silent
downgrade — and per the must_haves above, on THIS specific box (proven XWayland-capable) that
escalation is the ONLY route by which a SKIPPED verdict is acceptable.
