# Phase 06.9: E2E Tier 3 (Firing) + Tier 4 (Visuals) — Context

**Gathered:** 2026-09-08 (D-03 corrected 2026-09-08 — see note inline)
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the GUI/visual gap locally (PRD Phase 4). `make e2e-setup` provisions OS input-injection
tools (xdotool/ydotool on Linux, cliclick on macOS) + screenshot tools and handles the
permission grants each platform needs. Tier 3 *firing* injects real OS-level chords and
asserts the mux effect (opt-in via `WEZ_E2E_INPUT=1`, clean self-skip when absent). Tier 4 is
a hybrid snapshot-diff (automated, deterministic) + AI-vision (agent-performed, semantic)
check against committed per-platform baselines with a manual-approve flow. Everything in this
phase is best-effort/local/non-blocking — it explicitly stays out of CI (06.8's CI scope is
locked and not reopened here).

</domain>

<decisions>
## Implementation Decisions

### Tier 4 "AI-vision" mechanism
- **D-01:** `make e2e` never calls an external vision API. The deterministic, automatable
  half of Tier 4 is snapshot-diff (fresh capture vs. committed baseline, similarity-threshold
  comparison — see D-04). The semantic/"AI-vision" half (legible titles, no escape leak, clean
  focused pane, tint distinction, emoji alignment, active/inactive tab distinction — PRD
  Appendix A.4) is performed by whichever coding agent is running the review, not scripted
  into the bash test. This directly reuses the precedent set in Phase 06.5-04 (D-09 firing
  verdict): a screenshot is captured, then an agent reads and judges it — no vision API,
  no new runtime dependency. — **Reversibility:** reversible — the judging mechanism can be
  swapped later without touching the capture/diff logic underneath it.
- **D-02:** A new project skill (working name `e2e-visual-review`, exact name at planner's
  discretion) encapsulates the agent-performed half. Its prose instructs the agent to:
  1. Run the new `make e2e-visual` target (captures screenshots into a scratch dir per the
     A.4 checklist scenarios).
  2. Enumerate vision-capable models available in the CURRENT runtime, plus opencode's
     configured models (per `.planning/config.json`'s `workflow.cross_ai_command`, already
     wired in 06.8 to `opencode run --model xai/grok-4.6`) if opencode is reachable and not
     already the active runtime.
  3. Shortlist the best vision candidates and ASK THE USER which to use, with a suggested
     preference — never silently pick one.
  4. Run the semantic judgment with the user's chosen model, reporting each A.4 checklist
     item as pass/fail. **No numeric threshold applies to this checklist** — every item is
     either right or wrong; there is no partial-credit acceptance bar here.
  This is model/runtime-agnostic by design (mirrors the project's existing model-agnostic
  posture in `wez doctor`/`wez keys`) — it works the same whether the active session is
  Claude Code or opencode+grok-4.6/OpenAI.
- **D-03 (corrected):** The ONLY numeric acceptance bar in this whole area is on the SKILL
  ARTIFACT itself, not on the visual checklist: the newly-created `e2e-visual-review` skill
  must be validated by the existing global `skill-judge` skill
  (`~/.claude/skills/skill-judge/SKILL.md` — evaluates Agent Skill design quality against
  official specs) and must reach **≥90%** on that skill-quality score before the phase is
  considered done. **Correction note:** an earlier draft of this document (and the
  ONESHOT-AUTONOMOUS.md / ONESHOT-RULES.md files derived from it) mistakenly also applied a
  separate ≥90% target to the A.4 checklist pass rate. That was a misreading of the
  discussion — the user's actual ask was the skill-judge quality gate on the SKILL.md file
  ONLY. The checklist itself is evaluated item-by-item per D-02 above, with no numeric
  threshold of any kind.

### Manual baseline-approval flow
- **D-04:** Committed baseline images live at `tests/e2e/baselines/<os>/*.png` (plain PNGs,
  committed directly to git — no LFS/external storage, consistent with the project's
  dependency-averse philosophy and the small, bounded image count). `make e2e-visual
  --approve` promotes a freshly captured screenshot to become the new committed baseline,
  gated on the reviewing agent/model (per D-02) confirming it looks correct first.
- **D-05:** The fresh-capture-vs-baseline comparison uses a similarity/perceptual threshold
  (not byte-exact) — tolerates anti-aliasing and font-hinting rendering noise across runs on
  the same machine. Exact algorithm/threshold value is Claude's discretion at planning time.

### Input/screenshot tool provisioning
- **D-06:** `make e2e-setup` (the SAME existing target — no new target name) becomes the
  single consolidated dev-environment setup command for BOTH platforms. It installs
  everything a developer needs for Tier 3/4 locally: input-injection tool(s) + a screenshot
  tool, on whichever OS it runs.
- **D-07:** Installation is **Homebrew-first on BOTH platforms** (not just macOS) — falling
  back to the native package manager (dnf/apt/pacman) only when `brew`/`linuxbrew` is not
  present. Rationale (user-supplied): this dev machine is Bazzite, an atomic/immutable Fedora
  (rpm-ostree) — native `dnf install` doesn't persist cleanly (needs `rpm-ostree install` +
  reboot layering), whereas Homebrew on Linux (linuxbrew) installs into the user's home
  directory without touching the base OS image, and unifies the install logic across
  mac/Linux instead of branching per distro's native package manager.
- **D-08:** `make e2e-setup` FULLY AUTOMATES both Linux-specific wrinkles rather than just
  documenting them:
  1. **ydotool/uinput permission**: starts the `ydotoold` daemon and adds the invoking user
     to the `input`/`uinput` group as needed (may require sudo + a re-login/new-session for
     the group membership to take effect — the script should detect and clearly report this
     rather than silently failing).
  2. **Wayland compositor-specific screenshot tool**: detects the active compositor
     (wlroots-family e.g. Sway → `grim`; GNOME Wayland / KDE Wayland → their respective
     portal-based screenshot mechanism) and installs/selects the matching tool automatically,
     rather than requiring the user to pick.
  This is a deliberate departure from the macOS precedent (Accessibility/Screen-Recording
  grants stay a documented manual System Settings step, per the existing README placeholder)
  — the user explicitly asked for full automation on the Linux side specifically.
- **D-09:** macOS provisioning stays as previously scoped: `cliclick` via brew, `screencapture`
  needs no install (ships with macOS). The Accessibility + Screen Recording grants remain a
  documented manual step (OS-level permission dialog, cannot be scripted).

### CI interaction
- **D-10:** The 06.8 GitHub Actions workflow is NOT touched by this phase. Tier 3-firing and
  Tier 4 stay 100% local for now — self-skip correctness is proven by manual/local runs only,
  not exercised on a CI runner. Reopening 06.8's already-locked CI scope would blur the two
  phases' boundaries. — **Reversibility:** reversible — a future phase can add a
  self-skip-proof CI step without touching this phase's deliverables.

### Claude's Discretion
- Exact SKILL.md name for the visual-review skill (working name `e2e-visual-review`).
- Similarity-threshold algorithm and numeric value for baseline comparison (D-05).
- Exact scratch-dir layout for fresh captures (separate from the committed `tests/e2e/baselines/`
  tree) and the Tier 3 firing chord-to-effect assertion implementation per PRD Appendix A.3.
- Compositor-detection mechanism and the specific portal/tool used per Wayland compositor (D-08).
- ydotoold daemon-start and uinput-group-grant script mechanics, and how the
  "re-login needed" case is surfaced to the user without silently failing.
- **Known technical gap for the planner/researcher to resolve, not silently patch:**
  confirmed live on this machine (Bazzite, KDE Plasma, Wayland) that `ydotool` has NO
  window-targeting concept — every key/click event goes to whatever window currently has
  OS input focus, system-wide (unlike `xdotool key --window <id>` on X11, which doesn't
  apply here since this machine is Wayland, or macOS's `cliclick`). Tier 3-firing's window
  needs an explicit focus-activate-and-verify step before every injected keystroke; if that
  cannot be built with confidence on this compositor, that is a phase-blocking question for
  planning to raise, not something to ship assuming it "probably" targets the right window.

</decisions>
