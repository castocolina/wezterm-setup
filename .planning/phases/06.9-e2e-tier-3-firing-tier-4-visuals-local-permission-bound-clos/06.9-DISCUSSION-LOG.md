## Tier 4 "AI-vision" mechanism

| Option | Description | Selected |
|--------|-------------|----------|
| Snapshot-diff automated, AI-vision manual | make e2e-visual does deterministic diff; semantic checks stay a documented agent-performed step | ✓ |
| Call an external vision API automatically | Battery script calls a vision API directly, gated by API key | |
| You decide | Defer mechanism to Claude | |

**User's choice:** Started from the recommended option, then refined heavily:
- "I expected that if I asked an agent to run an e2e test, it would get involved in checking
  if the output was as expected... for your info, in opencode I have OpenAI models and also
  xai grok 4.6 available."
- Confirmed the shape: agent looks at screenshot, judges vs expectations, not a scripted API
  call.
- "How do we involve the agent? Maybe we need a skill for it — the skill's prose telling the
  agent to run the make target, where the images live, and how to evaluate them."
- Confirmed skill shape (run `make e2e-visual`, find screenshots, evaluate per A.4 checklist),
  and added: "we also need to add skill-judge as an expected part of the final plan, with a
  goal of reaching at least 90% score."
- On which model should judge: rejected pure "model-agnostic, no further ceremony" in favor of
  "the agent should list available models in the current runtime and opencode (if not already
  running in opencode), list them, pick best vision candidates, and ASK THE USER what they
  prefer before using one."
- Confirmed final two-part shape: (a) make target runs battery + captures screenshots,
  (b) skill wraps it, discovers models, asks user, judges with the chosen model — validated
  itself by `skill-judge` at ≥90%, and the visual-review result also targets ≥90%.

**Notes:** This area evolved substantially through discussion — the recommended option was a
reasonable starting point but the user's actual requirement (agent-driven, user-choice-of-model,
skill-judge-validated) was more specific than any single presented option. Captured fully in
CONTEXT.md D-01 through D-04.

| Option | Description | Selected |

| Check + print instructions only | No installs, safest | |
| You decide | Defer to Claude | |

**User's choice:** Rejected both as initially framed: "For dev environment I only need a
single target `setup-env` to install all needed for the developer, you decide what's needed
from CI, and everything must work on both Linux and macOS."

Follow-up — confirmed reusing the EXISTING `make e2e-setup` target name (not a new
`setup-env` name) as that single consolidated command.

Follow-up — package-manager choice: user explicitly overrode the "native package manager
with sudo" framing: "using sudo looks like you're restricting it to Linux only, I'd prefer
you try brew for the needed packages instead of the native Bazzite package manager." Locked:
brew-first on BOTH platforms, falling back to native package manager only if brew is absent —
rationale given: Bazzite is an atomic/immutable Fedora (rpm-ostree), so native `dnf install`
doesn't persist cleanly.

Follow-up — two remaining wrinkles (ydotoold daemon/uinput permission; Wayland
compositor-specific screenshot tool):
