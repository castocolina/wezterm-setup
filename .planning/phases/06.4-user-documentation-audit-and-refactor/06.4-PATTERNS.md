## Pattern Assignments

### Drift-check test (test, transform/assert) — D-08/D-09

**Analog:** `tests/cli/completions_test.lua` — it is the project's canonical example of a
**spec-driven** test that derives its expectation set from the REAL source surface (never a
hardcoded list) and asserts coverage. The drift-check is the inverse direction (documented →
exists) but uses the identical machinery: load the source module, enumerate its surface, assert
membership.

Secondary analogs:
- `tests/config/keybindings_test.lua` — shows how to load `keybindings.lua` as pure data from any CWD.
- `cli/spec_test.lua` — shows the `spec.build_parser()` + `pparse` acceptance/rejection idiom.

**Discovery/registration (no bespoke runner — D-08):** name the file `*_test.lua` under
`tests/` and `tools/run-tests.sh` discovers it automatically via
`find "${TEST_ROOTS[@]}" -type f -name '*_test.lua'` (run-tests.sh:50). `make test` →
`tools/run-tests.sh`. No edit to the runner or Makefile is required. A non-zero `os.exit`
fails the suite (run-tests.sh:124-129).

**Path-bootstrap pattern** (make `cli/...` + vendored deps requireable from any CWD) — copy from
`tests/cli/completions_test.lua` lines 12-19:
```lua
local this_dir = (arg and arg[0] or ""):match("^(.*)/[^/]-$") or "."
local repo_root = this_dir .. "/../.." -- tests/cli -> repo root
package.path = table.concat({
  repo_root .. "/?.lua",
  repo_root .. "/cli/vendor/?.lua",
  package.path,
}, ";")
```
(If the test lands directly under `tests/` rather than `tests/cli/`, adjust the `../..` depth — compare `tests/config/keybindings_test.lua:13-14` which uses `here .. "/../../config/wezterm-setup/?.lua"`.)

**check() assertion helper** — copy the count-and-report idiom from `completions_test.lua:21-30`
(or the stderr variant in `keybindings_test.lua:19-26` / `spec_test.lua:10-15`). All three share
the same shape: a `check(label, cond)` that increments pass/fail and prints, ending with
`os.exit(failed == 0 and 0 or 1)`.

**Derive-expectation-from-source proof** — the load-bearing pattern to copy. `completions_test.lua`
lines 61-65 build the expectation set from the live spec, NOT a literal list:
```lua
local visible = {}
for _, n in ipairs(spec.subcommand_names()) do
  if not hidden[n] then visible[#visible + 1] = n end
end
```
The drift-check inverts this: build the SOURCE set the same way, then iterate the
DOCUMENTED tokens and assert each is a member.

## Source surfaces the drift-check consumes (the three contracts from D-08)

These are the programmatic entry points; the drift-check enumerates them and the docs are
validated against them.

### 1. Command/flag surface — `cli/spec.lua`

Public surface (spec.lua:241-256, `return M` at 258):
- `M.subcommand_names()` → array of registered subcommand names (the same call the completion
  generator walks — `completions_test.lua:63`).
- `M.build_parser()` → argparse parser; use `parser:pparse(argv)` to test a documented
  `wez <cmd> --flag` invocation **accepts** (ok=true) or **rejects** (ok=false), exactly as
  `cli/spec_test.lua` does. Excerpt of the acceptance/rejection idiom (`spec_test.lua:19-22, 45-46`):
```lua
local function pparse(argv)
  local parser = spec.build_parser()
  return parser:pparse(argv)   -- (ok, result|errmsg), no process exit
end
-- documented flag must parse; a flag NOT registered there must fail:
local ok6 = pparse({ "tab", "color", "blue", "--icon", "node" })
check("--icon REJECTED on tab color", ok6 == false)
```
- `M.categories()` → name→category map (spec.lua:250).

This is the D-11 single-source: docs reference `--help`/completion for the exhaustive flag list;
the drift-check only asserts the specific commands/flags the prose DOES name parse cleanly.

### 2. Keybinding surface — `config/wezterm-setup/keybindings.lua`

Returns pure DATA (no wezterm global needed). Load it the `keybindings_test.lua:13-16` way:
```lua
local here = arg[0]:match("^(.*)/[^/]*$") or "."
package.path = here .. "/../../config/wezterm-setup/?.lua;" .. package.path
local kb = require("keybindings")
```
Surface to enumerate:
- `kb.keys` — array of `{ key, mods, action }` entries (keybindings.lua:62+). `key` carries a
  `mapped:` prefix (e.g. `mapped("w")`); strip it to compare against a documented chord — copy
  the `norm_key`/`norm_mods` canonicalizers from `cli/commands/keys.lua:29-46` (strip
  `^mapped:`, split mods on `|`, drop NONE, sort, rejoin) so `Ctrl+Shift+W` matches the data
  entry regardless of mod order.
- `kb.disabled_defaults` — `{ key, mods }` list (keybindings.lua:138-153).
- `kb.key_map_preference` (= `"Mapped"`, line 157).

The essential-chords table (D-12) names a SMALL set; the drift-check asserts each named chord
exists in `kb.keys` after normalization. `wez keys` remains the exhaustive runtime source.

### 3. Scene TOML schema — `cli/lib/scene.lua` (+ `cli/lib/recipe.lua`)

`scene.lua` returns `M` exposing the closed enumerations (single source of truth — D-16) and the
field parser:
- `M.LAYOUTS = { "tall", "tall:mirrored", "grid", "horizontal" }` (scene.lua:243) — the full layout
  reference for D-13; validated by `M.validate_layout(name)` (scene.lua:254).
- `M.COLOR_NAMES` (scene.lua:272) — the 10-profile palette; validated by
  `M.validate_color(name)` (scene.lua:288).
- `M.parse_pane_spec(spec)` → `{ cmd, color, title, cwd, focus, size, shell }` (scene.lua:135-165) —
  authoritative per-pane field set (`command`/`cmd`, `color`, `title`, `cwd`, `focus`, `size`,
  plus `icon` handled in recipe.lua:91-112). The result table keys ARE the documented field names
  the scene reference (D-13) must match.
- `cli/lib/recipe.lua` maps recipe tables → `--pane` spec; recipe.lua:91-112 enumerates the same
  field set incl. the per-pane `icon` extra field. Use this list to assert every field the scene
  doc tabulates is a real, parsed key (documented → exists).

Tab-level fields (layout / color / title / icon / cwd / follow_pane_color) round-trip through the
`wez tab` subcommands in `spec.lua` (validate via `pparse` as in surface #1) — so the tab-level
half of the scene reference is validated through the spec parser, the pane-level half through
`parse_pane_spec`/recipe field list.
