# Phase 06.4: User Documentation Audit and Refactor - Context

**Gathered:** 2026-06-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Audit every **user-facing** doc (README first, then `docs/`) against the shipped
v0.1.0 reality and the 6.1/6.2/6.3/6.5 redesign, then refactor — starting with
README via `/agent-md-refactor` + `/crafting-effective-readmes` — into a lean,
progressive-disclosure structure (lean hub README + focused `docs/` pages). A
**durable automated drift-check** asserts every documented command/flag/keybinding/
scene field exists in source. This is the LAST of the 6.x deltas, so docs describe
the final decoupled icon/color model, scene schema, install channels, and curated
`wez keys` output.

**Governing principle (maintainer, locked):** *document what the tool IS now, not
what it was.* Treat this as a fresh development — **no legacy/migration narrative**.
No "previously this worked differently" notes in the refreshed docs.

This phase clarifies HOW to audit/refactor what's already shipped. It does NOT add
new product capabilities, and it does NOT (by default) fix code — only documents it
(trivial gaps excepted, see D-09).

</domain>

<decisions>
## Implementation Decisions

### README architecture
- **D-01:** Target structure = **lean hub + focused docs pages**. README becomes a
  short overview + quickstart + a compact feature/keybinding summary; deep content
  moves to focused `docs/` pages (e.g. CLI guide, scenes, keybindings, install).
  *(Maintainer deferred the exact structure to Claude; this is Claude's call,
  consistent with the progressive-disclosure scope wording.)*
- **D-02:** **MANDATORY tooling** — use `/crafting-effective-readmes:crafting-effective-readmes`
  during BOTH execution and review of the README, and `/agent-md-refactor:agent-md-refactor`
  for the split (the latter is named in the ROADMAP scope). Both are required, not optional.
- **D-03:** **Remove the README "Status" section entirely** (the per-phase table that
  says "pre-release / phases 0–5 pending"). Do NOT replace it with a rewritten table
  (that just re-rots). Users who want roadmap state follow `.planning/ROADMAP.md`.
- **D-04:** **Move the "Development" section out** of README into a contributor-facing
  doc (e.g. `CONTRIBUTING.md` or `docs/development.md` — Claude picks the name). It's
  contributor-facing, not user-facing. "Why not a plugin?" + "Platform" framing may
  stay in README (condensed) at Claude's discretion.

### Audit scope boundary
- **D-05:** In-scope = **README + docs that describe CURRENT behavior**. Out of scope:
  CLAUDE.md and `.planning/*` (agent/planning artifacts maintained by other workflows).
- **D-06:** **Prune stale `docs/repro/*`** — they're dated dev hypothesis evidence
  (`h-*`), not user docs; some reference pre-6.1 behavior. Delete the superseded ones
  rather than updating them. (Aligns with the "what is, not what was" principle.)
- **D-07:** **`docs/migration-tab-color-decouple.md` → prune as a migration doc.** It's
  a pure "what was → what is" narrative about the legacy `color:title` encoding that
  6.2 already removed entirely. **EXCEPTION:** it also documents a still-current surface
  — the `wez doctor` "no shadowing tab-bar handler" core gate (D-11) + what to remove
  when it fires. Carry that **current troubleshooting nugget forward** into a current
  doc (e.g. a troubleshooting section / doctor doc); do not lose it. Only the migration
  framing is pruned.

### Drift-check
- **D-08:** **Durable automated drift-check test/script**, wired into `make test`
  (fits the project's co-located `*_test.lua` culture + the "verify before declaring
  done" rule). It parses `cli/spec.lua` (commands+flags), `config/wezterm-setup/keybindings.lua`
  (chords), and the scene schema, and asserts documented surface exists.
- **D-09:** **Direction = documented → exists ONLY.** The test fails if a doc references
  a nonexistent command/flag/keybinding/field. It does NOT enforce shipped → documented
  — *what* to document is a deliberate authoring choice (see D-10/D-11/D-12), not
  test-enforced completeness.
- **D-10:** **Code-gap disposition = fix trivial gaps inline, defer larger.** If the
  audit uncovers a documented-but-unimplemented surface or a genuine bug, and the fix
  is a one-line/trivial change, fix the code so the doc can be truthful; anything larger
  is captured as a deferred backlog item/bug, keeping the phase doc-scoped.

### Coverage depth
- **D-11:** **Docs are a task-oriented guide; `wez <cmd> --help` + completion is the
  exhaustive flag reference.** Document the common workflows + important flags (icon,
  color split, follow_pane_color, channels, update, uninstall); do NOT mirror every flag
  in prose — reduces spec.lua duplication and shrinks the documented→exists test surface.
- **D-12:** **Keybindings = short "essential chords" table + point to `wez keys`.** Keep
  the hand-maintained table small (so it's cheap to keep accurate and cheap for D-08 to
  validate), then direct users to `wez keys` for the complete, always-current curated
  list (the 6.5 curated-first output is now the trustworthy source of truth).
- **D-13:** **Scene TOML schema = FULL field reference** in a focused doc (e.g.
  `docs/scenes.md`). Complete tab-level + pane-level field table (layout/color/title/
  icon/cwd/follow_pane_color + `[[panes]]` command/color/title/icon/cwd/focus/size),
  each field's meaning + accepted values (incl. `#RRGGBBAA` alpha, the `cwd` grammar,
  `size`/`focus` semantics), plus worked example recipes. This is the richest 6.1/6.2
  surface and is the one place a full reference is warranted (the exception to D-11).

### Claude's Discretion

- Contributor-doc name/location for the moved Development content (D-04).
- Whether "Why not a plugin?"/"Platform" stay in README or move (D-04).
- Where the carried-forward doctor-shadowing troubleshooting nugget lands (D-07).
- Which specific `docs/repro/*` files are stale enough to prune (D-06).

<code_context>
## Existing Code Insights

### Reusable Assets
- `cli/spec.lua` (14 KB argparse contract) — machine-readable command/flag surface; the
  drift-check (D-08) can walk its `_commands`/`_options` the same way completion
  generation already does (Locked 01-07 D-16), so the check grows with the spec.
- `config/wezterm-setup/keybindings.lua` (returns key table as DATA, consumed by both
  `apply()` and `wez keys`) — parseable source for the keybinding drift-check + the
  short essential-chords table.
- `wez keys` (6.5 curated-first, trustworthy, low-noise) — the runtime source docs point
  users to instead of duplicating a drift-prone table (D-12).

### Established Patterns
- Co-located `*_test.lua` discovered by `make test` (since quick task 260613-dup) — the
  drift-check test (D-08) follows this convention, not a bespoke runner.
- "Verify before declaring done" — the drift-check IS the verification artifact for this
  phase (no "should be accurate" hand-waving).
- Single-source-of-truth discipline: `cli/spec.lua` is authoritative; docs reference it /
  `--help`, they don't re-specify it (D-11).

### Integration Points
- Drift-check hooks into `make test` / `tools/run-tests.sh`.
- README split produces new `docs/` pages + a moved contributor doc (CONTRIBUTING.md or
  docs/development.md) — both linked from the lean README hub.

</code_context>

    6.2 icon-is-its-own-attribute model; needs reworking to the `icon` attribute.
