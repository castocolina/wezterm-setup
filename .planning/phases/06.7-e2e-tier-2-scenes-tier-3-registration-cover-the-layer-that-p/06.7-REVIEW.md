# Phase 06.7: Code Review Report

**Reviewed:** 2026-06-25
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Reviewed the Tier 2 (live-mux scene) and Tier 3 (registration) e2e drivers, the
shared `mux.lua`/`platform.lua` libraries, the Makefile glue, and the
`run-e2e-prove.sh` break harness. I cross-checked the supporting modules
(`harness.lua`, `skip.lua`, `showkeys.lua`, and the real `scene.lua` /
`keybindings.lua` injection targets) to verify the load-bearing claims.

The break harness's awk injectors **do** match the real source (verified
`local CLEAR_SCROLLBACK_AND_VIEWPORT =` at `scene.lua:478` and
`-- default SpawnTab variant` at `keybindings.lua:140`), so the prover has teeth.
The mux isolation and `shquote` discipline are sound.

However, the Tier 3 registration driver contains a **logic bug that defeats its
own stated contract**: a failure detected by the always-run cross-platform layer
is silently discarded (file exits `0`) whenever `wezterm` is not runnable —
exactly the headless/CI environment where that layer is the only thing running.
A second data-integrity gap in the break harness can leave the user's *installed*
config corrupted if a backup copy fails.

## Critical Issues

### CR-01: Tier 3 registration test masks cross-platform failures on the live-skip path

**File:** `tests/e2e/tier3/registration_e2e_test.lua:137,155-158,215`
**Issue:**
The cross-platform layer (lines 117-133) runs unconditionally and is the D-07
contract that catches a curated PRD action with *no* binding in
`keybindings.lua` — the headline "silently dropped binding" defect. Its result is
captured at line 137:

```lua
local xplat_rc = h.footer()  -- "Capture it so a cross-platform FAIL still fails the file even if the live layer skips."
```

The file then gates the live layer:

```lua
skip.require_tool(wezterm_runnable, "tier3 show-keys registration", "...")
```

`skip.require_tool` calls `os.exit(0)` on the skip path (`tests/e2e/lib/skip.lua:55`).
So when `wezterm` is not runnable, the process exits `0` **before** line 215 is
ever reached — `xplat_rc` is never consulted. A cross-platform FAIL (e.g. a
curated action with no binding, or `chord_families` not covering an action) prints
`FAIL` to stdout but the file still exits `0`. That is a false green in exactly the
environment (CI / headless, no GUI wezterm on PATH) where the always-run layer is
the *only* thing that runs. The inline comment at line 136 promises the opposite
behavior, so the intent and the code disagree.

On the non-skip path the bug is masked by an unrelated accident: `h.footer()` never
resets `harness.lua`'s module-level counters, so the second `h.footer()` at line
215 is cumulative and already includes the cross-platform failures — making
`xplat_rc` dead/redundant there too. The variable only *matters* on the skip path,
which is the one path that never reads it.

**Fix:** Honor the captured result before gating:

```lua
local xplat_rc = h.footer()

-- A cross-platform FAIL must fail the file regardless of the live gate below,
-- including when the live layer self-skips (os.exit(0)).
if xplat_rc ~= 0 then os.exit(xplat_rc) end

skip.require_tool(wezterm_runnable, "tier3 show-keys registration", "...")
```

## Warnings

### WR-01: Cumulative, double-counted footer tally in the Tier 3 test

**File:** `tests/e2e/tier3/registration_e2e_test.lua:137,215`
**Issue:**
`harness.M.footer()` reads module-level `passed`/`failed` counters that it never
resets (`tests/e2e/lib/harness.lua:90,109-114`). The Tier 3 file calls `footer()`
twice — once at line 137 (cross-platform) and again at line 215 (final). The second
call reprints the cross-platform checks folded into the live totals, so the printed
"N passed, M failed" line at the end double-counts the cross-platform checks. This
is confusing in logs and, combined with CR-01, shows the whole `xplat_rc` mechanism
is mis-wired. After fixing CR-01, consider using `h.new()` instances (already
provided for "counter isolation across multiple require sites") so the two phases
report independent tallies.
**Fix:** Use a fresh `h.new()` instance for the cross-platform phase and another for
the live phase, or reset counters between phases, so each `footer()` reports only
its own checks.

### WR-02: Break harness can corrupt the user's installed config when the backup copy fails

**File:** `tools/run-e2e-prove.sh:106,188-189,193`
**Issue:**
The harness's central safety promise (T-06.7-20) is byte-for-byte restore of the
*installed* keybindings copy. But the backup creation is unchecked:

```sh
PROVE_TMP="$(mktemp -d "${TMPDIR:-/tmp}/wez-e2e-prove.XXXXXX")"   # line 106 — return not checked
...
INSTALLED_BACKUP="${PROVE_TMP}/installed-keybindings.bak"          # line 188
cp "${INSTALLED_KEYS}" "${INSTALLED_BACKUP}"                       # line 189 — return not checked
inject_keys
cp "${KEYS_FILE}" "${INSTALLED_KEYS}"                             # line 193 — overwrites the live config
```

`set -u` is on but `set -e` is deliberately off, so if `mktemp` fails (empty
`PROVE_TMP` → `INSTALLED_BACKUP=/installed-keybindings.bak`) or the backup `cp` at
line 189 fails for any reason (disk full, perms), execution still reaches line 193
and overwrites the user's installed `keybindings.lua` with the INJECTED-BREAK
version. The restore at line 207 (`cp "${INSTALLED_BACKUP}" "${INSTALLED_KEYS}"`)
and the EXIT trap both guard on `[ -f "${INSTALLED_BACKUP}" ]`, which is now false —
so the user's live config is left in the broken, regression-injected state with no
recovery. This is the exact data-integrity failure the safety section claims is
impossible.
**Fix:** Abort if `mktemp` fails, and verify the backup exists before mutating the
installed copy:

```sh
PROVE_TMP="$(mktemp -d "${TMPDIR:-/tmp}/wez-e2e-prove.XXXXXX")" || {
  echo "run-e2e-prove: FATAL — mktemp failed" >&2; exit 1; }
...
INSTALLED_BACKUP="${PROVE_TMP}/installed-keybindings.bak"
cp "${INSTALLED_KEYS}" "${INSTALLED_BACKUP}" || {
  echo "run-e2e-prove: FATAL — could not back up installed config; refusing to mutate it" >&2
  INSTALLED_BACKUP=""; exit 1; }
```

## Info

### IN-01: Misleading comment about when the mux PID is captured

**File:** `tests/e2e/lib/mux.lua:173-188`
**Issue:** The launch line `"%s %s >%s 2>&1 & echo $! > %s"` runs `echo $!`
synchronously in the same `/bin/sh -c`, so the pidfile is written before
`os.execute` returns — i.e. before the liveness poll. The comment at line 186-187
("Read the captured PID (after liveness so the file is written)") implies the file
isn't ready until after the poll, which is not how it works. Harmless, but the
rationale is wrong and could mislead a future maintainer.
**Fix:** Reword the comment to state the pidfile is written synchronously at launch;
the post-poll read is just ordering, not a dependency.

### IN-02: `math.random` is never seeded

**File:** `tests/e2e/tier2/scene_reuse_e2e_test.lua:222`, `tests/e2e/tier2/scene_newtab_e2e_test.lua:269`, `tests/e2e/lib/harness.lua:75`
**Issue:** Markers (`ZZ%d_%dZZ`) and `scratch_dir` suffixes use `math.random`
without `math.randomseed`, so Lua emits the same sequence every run. Uniqueness
holds *within* a run (calls advance the PRNG) and each case uses a fresh mux, so
this is not currently a correctness bug — but it is a latent collision risk if two
runs ever overlap on the same host within the same `os.time()` second.
**Fix:** Seed once at startup, e.g. `math.randomseed(os.time() + (os.clock()*1e6))`.

### IN-03: `WEZ_ABS` resolution block duplicated verbatim across both Tier 2 drivers

**File:** `tests/e2e/tier2/scene_reuse_e2e_test.lua:60-72`, `tests/e2e/tier2/scene_newtab_e2e_test.lua:69-81`
**Issue:** The repo-root/`WEZ_ABS` resolution is copy-pasted (the newtab file even
comments "Identical to the reuse driver"). The phase's own stated goal is to avoid
re-rolling shared plumbing (D-03); this resolver is shared plumbing that belongs in
`harness.lua` or `mux.lua`.
**Fix:** Hoist a `harness.abs_wez(repo_root)` helper and have both drivers call it.

### IN-04: `norm_cwd` comparison is brittle under symlinked temp dirs (macOS)

**File:** `tests/e2e/tier2/scene_reuse_e2e_test.lua:89-91,177`, `tests/e2e/tier2/scene_newtab_e2e_test.lua:95-98,225`
**Issue:** The CWD check compares `norm_cwd(p.cwd)` (the path wezterm reports,
typically fully resolved) against the raw `s.launch_dir`. If the scratch base is a
symlink (classically `/tmp` -> `/private/tmp` on macOS), wezterm reports the real
path while `launch_dir` is the unresolved one, and the D-08 cwd assertion fails
spuriously. Currently low-risk on Linux (real `/tmp`), but it is a macOS-parity
landmine for the deferred macOS run.
**Fix:** Canonicalize `launch_dir` once (e.g. `pwd -P` in the launch dir) before
comparing, so both sides are real paths.
