# Phase 06.2: Code Review Report

**Reviewed:** 2026-06-16
**Depth:** standard
**Files Reviewed:** 20
**Status:** issues_found

## Summary

Phase 6.2 (Identity Orthogonality) splits the tab/pane color carriers
(`WEZTERM_TAB_COLOR` vs `WEZTERM_PANE_COLOR`), promotes `icon` to its own
attribute (`WEZTERM_TAB_ICON`), and threads a per-pane / tab-level icon + a
`--follow-pane-color` opt-in through the scene/recipe pipeline. The two security
trust boundaries the project depends on are intact and were verified empirically:

- **OSC / escape-sequence injection** — every user/recipe-derived value flows
  through `color.build_osc1337`, which base64-encodes the payload. I confirmed
  with a malicious icon (`x\27]0;pwn\7`) and a multibyte emoji that the emitted
  bytes are pure base64 + a fixed varname/framing; no raw control bytes survive.
  The OSC `varname` is never user-controlled (all callers pass string literals).
  No new raw-string OSC emit path bypasses the encoder.
- **Shell-eval safety** — `tab.write_tab_title` and every `scene.lua`
  `os.execute`/`io.popen` argument is `shquote`'d. I verified an env-var-resolved
  cwd containing `; rm -rf /` stays inside single quotes after `shquote`, and the
  `cwd` grammar rejects `$(...)`/backticks before any emit. `{cwd}` is a pure-Lua
  token expansion (no shell). No `$(...)` shell eval path exists.
- **Carrier split (D-07)** — `pane.lua` writes only `WEZTERM_PANE_COLOR` (verified
  it never emits `WEZTERM_TAB_COLOR`); the tab's own color rides `WEZTERM_TAB_COLOR`
  on pane 1 in scenes / `tab color` only.
- **Path traversal** — `recipe.guard_name` rejects `/`, `..` (and any substring
  containing `..`) before any `io.open`.

All 20 files' test suites pass (532 assertions across 9 suites). No BLOCKER-class
defects found. The findings below are correctness/robustness gaps (mostly latent,
edge-case, or known-but-unguarded limitations) plus duplication notes.

## Warnings

### WR-01: Recipe field values containing a comma silently build a corrupt `--pane` spec that fails downstream

**File:** `cli/lib/recipe.lua:89-98` (`pane_table_to_spec`); fails in `cli/lib/scene.lua:152-203` (`parse_pane_spec`)
**Issue:** `pane_table_to_spec` joins multi-field panes into a single
comma-delimited string (`"cmd=" .. cmd .. ", color=" .. ...`). `parse_pane_spec`
later splits that string on top-level commas. Any field value that itself
contains a comma (e.g. a TOML `title = "a, b"` on a styled pane) produces a spec
like `cmd=vim, color=teal, title=a, b`. Round-tripping that back through
`parse_pane_spec` splits ` b` into a segment with no `=`, treats `b` as an
unknown key, and returns `(nil, "...unknown key 'b'...")`. The recipe loader
accepts the recipe as valid, then `run_new` aborts at parse time with a
misleading "unknown key 'b'" error attributed to the user's spec. This is
documented as "Pitfall 5 / v1 limitation" in the header comment, but it is
*unguarded*: there is no validation at map time, so a legitimate comma in a
recipe field becomes a confusing runtime failure (or, worse, silent field loss if
the fragment happens to look like a valid `key=value`).
**Fix:** Reject (or escape) commas in field values at map time so the failure is
a clear, attributable diagnostic instead of a downstream parse error:
```lua
local function assert_comma_free(field, value)
  if value and tostring(value):find(",", 1, true) then
    return nil, string.format(
      "error: scene recipe is invalid: %s value must not contain a comma "
      .. "(v1 --pane grammar limitation): '%s'", field, value)
  end
  return true
end
```
Call it for `color/title/cwd/icon`/`cmd` in `pane_table_to_spec` (or in
`load_and_map`) and surface the error through `load_and_map`. The proper long-term
fix (noted in the comment) is the structured `run_new` entry point that bypasses
string round-tripping entirely.

### WR-02: `${NAME}` brace-form cwd silently resolves to a broken literal path

**File:** `cli/lib/cwd.lua:69-70` (validate), `cli/lib/cwd.lua:120-123` (resolve)
**Issue:** The env-var grammar only matches the bare form `^%$([%w_]+)` — `$` must
be immediately followed by a word char. A braced reference like `${PWD}/x` does
NOT match, so (a) `validate` skips the "is the env var set?" check and returns
`true`, and (b) `resolve` falls through to the relative-path branch, producing
`launch_dir .. "/${PWD}/x"` — a literal directory name containing `${PWD}`. The
user wrote what looks like a valid shell-style variable, it passes validation, and
the pane silently opens in (or fails to open in) a nonexistent literal path. I
confirmed: `validate("${PWD}/x", {})` -> `true`; `resolve("${PWD}/x","/launch",{})`
-> `/launch/${PWD}/x`. Not a security issue (the value is `shquote`'d, never shell-
expanded), but a real correctness/UX trap.
**Fix:** Either support the brace form, or reject it explicitly so the failure is
visible. Minimal rejection in `validate`:
```lua
-- Reject the unsupported ${NAME} brace form up front (only $NAME is expanded).
if value:match("^%${") then
  return false, string.format(
    "error: invalid cwd '%s' — use $NAME (not ${NAME}); the brace form is not expanded", value)
end
```
Place it before the bare-`$NAME` check. (The same gap applies to a `$NAME`
embedded mid-string, e.g. `/a/$B/c`, which `resolve` also leaves literal — worth
deciding intentionally.)

### WR-03: `format_label` byte-truncation can split a multibyte glyph mid-codepoint

**File:** `config/wezterm-setup/format-tab-title.lua:139-146`
**Issue:** `format_label` truncates with `label:sub(1, limit)` where `limit =
max_width - 4`, on a label that now routinely begins with a multibyte icon glyph
(D-04 composes `icon .. " " .. title`). A byte-based cut lands inside a UTF-8
sequence on narrow tabs. I confirmed: `format_label(0, "🔥🔥🔥🔥🔥 ...", 14)`
returns a 10-byte string ending in `0x94` — a bare UTF-8 continuation byte
(invalid). The live handler re-applies `wezterm.truncate_right(label, max_width-4)`
(line 214) at the *same* width, so it receives the already-mangled bytes as input;
whether the broken trailing byte is cleaned depends on `truncate_right`'s
internals. The two truncation stages use mismatched units (bytes vs columns) at
the same limit, which is the defect.
**Fix:** Make `format_label` codepoint-aware, or (simpler) stop double-truncating:
have `format_label` build the full label and let the single codepoint-aware
`wezterm.truncate_right` in the handler do all truncation. If `format_label` must
truncate for the unit-test fallback, truncate on codepoints:
```lua
-- count UTF-8 codepoints, cut on a codepoint boundary
if limit > 0 and utf8.len(label) and utf8.len(label) > limit then
  label = label:sub(1, (utf8.offset(label, limit + 1) or (#label + 1)) - 1)
end
```

### WR-04: `read_topology` is called twice per scene launch with no consistency guard

**File:** `cli/commands/scene.lua:334` and `cli/commands/scene.lua:498`
**Issue:** `run_new` reads `wezterm cli list --format json` once for the
materialization decision (line 334) and again, later, purely to find the target
tab id for the title write (line 498) when `plan.target_tab_id` is nil (the
new-tab path). Between the two reads the mux state has changed (panes were spawned/
split). If the second read fails to find `pane_ids[1]` (race, mux quirk, or a pane
that moved), `target_tab_id` stays nil and the tab title is **silently dropped**
with no warning — the scene builds but the requested `--title` never applies.
**Fix:** Capture the tab id from the spawn that created pane 1 (the `spawn`/
`split-pane --format json` output, or a single topology read cached as state)
rather than re-reading and best-effort matching. At minimum, warn when the title
write is skipped so the silent drop is observable:
```lua
if target_tab_id == nil then
  io.stderr:write("warning: could not resolve the new tab id; --title not applied\n")
end
```

### WR-05: `decide_materialization` ignores the `WEZTERM_PANE` env var being unset/garbage and silently degrades to new-tab

**File:** `cli/commands/scene.lua:335`, `cli/lib/scene.lua:332-353`
**Issue:** `current_pane_id = tonumber(os.getenv("WEZTERM_PANE"))` yields `nil`
when the var is unset or non-numeric. `decide_materialization` then finds no
matching pane, `current_tab_id` stays nil, `tab_pane_count` counts panes whose
`tab_id == nil` (zero), so the result is `mode = "new-tab"`. That is a reasonable
default *when running outside a pane*, but it also masks the case of a genuinely
malformed `WEZTERM_PANE` inside a live session — the user expecting an in-place
"reuse" build silently gets a new tab instead, with no diagnostic. Combined with
the empty-topology degrade in `read_topology` (returns `{}` on any decode failure),
two independent "soft-degrade to new-tab" paths can hide a real environment
problem.
**Fix:** Distinguish "no session / not in a pane" (legitimate new-tab) from
"in a pane but WEZTERM_PANE is unreadable" and emit a one-line stderr note in the
latter so the behavior is auditable. Not a correctness blocker, but the silent
fallback violates the project's "verify, don't assume" posture.

## Info

### IN-01: `run_icon` / `--icon` emit logic is duplicated across `tab.lua` and `pane.lua` (D-01 spirit)

**File:** `cli/commands/tab.lua:189-196,209-212` and `cli/commands/pane.lua:113-120,134-136`
**Issue:** Both modules contain byte-identical icon-emit bodies
(`emit(build_osc1337("WEZTERM_TAB_ICON", title.resolve_icon(raw)))` plus the same
reset/`--icon` handling). D-01 mandates ONE shared implementation for
icon/color/title; the *resolver* (`title.resolve_icon`) is shared, but the
emit+reset+`--icon` orchestration is copy-pasted. Low risk (the shared resolver
is the security-relevant part), but it is exactly the kind of parallel copy D-01
exists to prevent — a future change to icon reset semantics must be made in two
places.
**Fix:** Hoist a shared `title.emit_icon(emit_fn, raw)` (or a helper in a small
shared command-lib) and call it from both `run_icon` bodies.

### IN-02: `shquote` and `decode_json` are duplicated in `tab.lua` and `scene.lua`

**File:** `cli/commands/tab.lua:84-96` and `cli/commands/scene.lua:64-96`
**Issue:** Both files define identical local `shquote` and `decode_json` helpers.
The `shquote` duplication is security-sensitive: if one copy is ever "improved"
and the other isn't, a quoting divergence could open an injection on one path.
The comments acknowledge the duplication ("same proven helper as ..."), which is a
smell, not a justification.
**Fix:** Move `shquote` and `decode_json` into a tiny shared `cli/lib/shell.lua` /
reuse the existing shared lib, and require it from both. This keeps the single
escaping rule truly single-sourced.

### IN-03: `merge_title` / `parse_stored` are dead in the steady-state path but still exported and exercised

**File:** `cli/commands/tab.lua:50-74`
**Issue:** Per the header (D-04) these survive "ONLY as migration helpers" and
"scene.lua still calls them until Plan 04" — but `scene.lua` (this phase) no
longer calls either (verified: the `<color>:<title>` encoding dependency is gone,
line 482-483 comment confirms). `merge_title` now has no production caller; only
`tab_test.lua:51` and the one-time `warn_legacy_prefix_once` (`parse_stored`)
keep them alive. The comment is now stale and the migration surface can likely be
retired.
**Fix:** Confirm no caller remains (`merge_title` appears truly unused) and remove
it plus its test, or downgrade the comment to "retained only for the one-time
`warn_legacy_prefix_once` parse." Reduces the migration cruft footprint.

### IN-04: `scenes/dev.toml` documents a `🛠` tab glyph that the recipe never produces

**File:** `scenes/dev.toml:24,28`
**Issue:** The comment (line 24) states the tab title becomes `"🛠 myproject"`, but
the recipe sets `icon = "build"` (line 28), which `title.ICONS.build` resolves to
`🔨` (hammer), not `🛠` (hammer-and-wrench). The shipped behavior is `🔨 myproject`.
Pure doc drift, but seed recipes are user-facing reference material and an
inaccurate example erodes trust in the docs.
**Fix:** Update the comment to `🔨 myproject` (or change `icon` to the literal
`🛠` glyph if that is the intended look).
