<objective>
Fix a real, currently-broken Lua-5.4+ portability bug found live on this Mac (`cli/lib/scene.lua`'s
`split_kv_segments` reassigns its own generic-`for` loop control variable, which Lua 5.4+ treats as
implicitly `<const>` — a hard compile error under this Mac's actual Lua 5.5.1, cascade-failing the
full unit suite), then harden the auto-verifier's own portability probes from loose NOTEs into real
PASS/FAIL gates, and correct the misleading `LUA_BIN=lua` guidance the runbook currently gives (that
`lua` is Homebrew's generic formula, now 5.5.x on this machine — a different major version, not a
safe stand-in for `lua5.4`).

Purpose: this is the tracer for the whole macOS Parity phase — it proves the project's actual source
and its own verification tooling both run correctly on real Mac hardware, on the very first commit,
before any install/build/CI expansion work lands on top of it.

Output: a real Mac unit-suite pass, a hardened `tools/verify-macos.sh` with durable portability
assertions, and accurate LUA_BIN guidance in both the runner script and the runbook.
</objective>

  <read_first>
    - `cli/lib/scene.lua` lines 30-51, the `split_kv_segments` private function. The generic-`for`
      loop `for segment in tostring(spec):gmatch("[^,]+") do` binds `segment` as the loop control
      variable; line 42 then does `segment = trim(segment)`, reassigning that same variable. Lua
      5.4's reference manual makes every generic-`for` control variable implicitly `<const>` — this
      compiles fine under Lua 5.3 and earlier, but is a hard `attempt to assign to const variable
      'segment'` compile error under Lua 5.4+ (confirmed live on this Mac's actual interpreter,
      Homebrew's plain `lua` formula, now Lua 5.5.1 — a strict superset of 5.4's const-loop-var rule).
    - `cli/lib/scene_test.lua` — confirms there is no dedicated unit test for `split_kv_segments`'
      output shape in isolation; its behavior is exercised indirectly through `parse_pane_spec`'s
      existing multi-segment/comma/space-trimming assertions, which is why fixing the compile error
      and re-running the existing suite green IS the regression guard (a reintroduction of the
      reassignment would immediately break `require("cli.lib.scene")` again under any 5.4+
      interpreter, Linux's system `lua5.4` included).
  </read_first>
  <files>cli/lib/scene.lua</files>
  <action>
    In `split_kv_segments` (around line 39), rename the generic-`for` loop's control variable from
    `segment` to `raw_segment` (`for raw_segment in tostring(spec):gmatch("[^,]+") do`), then
    introduce a NEW local variable named `segment` inside the loop body bound to the trimmed value
    (`local segment = trim(raw_segment)`), replacing the old reassignment line
    (`segment = trim(segment)`). Every line after that inside the loop body (the `segment:match(...)`
    call, the `trim(key)`/`trim(value)` calls, the two `segments[#segments + 1] = ...` branches)
    stays byte-identical — only the loop-variable identity changes, not the algorithm. Do not touch
    any other function in this file. This is the SAME fix shape the live-evidence dossier names
    explicitly: rename the loop variable, never mutate it.
  </action>
