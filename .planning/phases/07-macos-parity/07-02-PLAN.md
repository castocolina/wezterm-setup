<objective>
Make `tools/build.sh`'s luastatic single-binary path — the project's actual locked shipping
artifact (PROJECT.md: "packaging = vendored pure-Lua deps + luastatic single binary") — actually
work on macOS, then exercise it for real on this Mac. Live investigation this session found the
existing `pkg-config`-based header/library resolution cannot work on a stock Homebrew macOS install:
`pkg-config` itself is absent by default on this machine, and even where present, the Homebrew
`lua@5.4` keg ships its `.pc` file as `lua.pc` (not `lua5.4.pc`/`lua-5.4.pc`) with headers under
`include/lua/` (not `include/lua5.4/`) — none of which match `build_with_luastatic()`'s current
probe order or its `-I/usr/include/lua5.4` fallback. Until this plan, every macOS `tools/build.sh`
run has silently fallen back to the dev source-launcher (because `luastatic` itself was never
installed either), so the actual shipping build path has never been proven on real Mac hardware.

Purpose: close MACOS-PARITY-AND-FOLLOWUPS.md section C-1's Mach-O item with real evidence, and give
every later plan in this phase (the real `install_macos`, the real install/uninstall cycle, ad-hoc
codesign) a genuine static binary to build on instead of the non-shippable dev launcher.

Output: a macOS-portable `build_with_luastatic()`, and a real `dist/wez` Mach-O produced on this Mac.
</objective>
